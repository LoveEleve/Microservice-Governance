# 技术评审方法：问题 → 官方 → Microsphere → 结论

> 原则：**Microsphere 的实现不是正确性标准，只是候选答案。** 每个能力都必须先问“问题是什么、官方有没有、Microsphere 怎么做、边界在哪”，最后才决定我们怎么用。

## 五步法

| 步骤 | 要回答的问题 | 产出 |
|---|---|---|
| 1. 问题 | 它解决的具体场景/约束是什么？不用它会怎样？ | 一句话问题 + 反例 |
| 2. 官方基线 | Spring / Spring Boot / Spring Cloud / Nacos 等官方是否已实现？语义是什么？ | 官方类/扩展点/行为 |
| 3. Microsphere | 它挂在哪、补了什么、假设是什么？ | 扩展点 + 关键类 + 设计取舍 |
| 4. 正确性/边界 | 失败语义、幂等、顺序、去重、并发、兼容性、可观测性 | 风险清单 |
| 5. 我们的决策 | 用官方 / 用 Microsphere / 自己写；为什么 | 代码 Lab + 结论 |

## 示例：Multiple Service Registry / Union Discovery

| 维度 | 官方 Spring Cloud | Microsphere | 评审结论 |
|---|---|---|---|
| 一实例多注册 | 默认单个 `ServiceRegistry`，无内建多注册编排 | `MultipleServiceRegistry` 按 `Registration` 类型委托给多个 registry | 补空白，但**按类型分发**是硬前提 |
| 注册类型 | 各注册中心有自己的 `Registration` 子类 | `MultipleRegistration` 聚合多个 Registration | 两个 registry 用同一 Registration 类型时无法一一对应 |
| 发现聚合 | `CompositeDiscoveryClient`：按 order 取**第一个非空**列表 | `UnionDiscoveryClient`：**所有** client 实例做并集 | 语义不同：短路 vs 全量合并 |
| 去重 | 官方 Composite 不跨 client 去重 | Union 直接拼接，不保证实例唯一 | 多注册中心同时注册同一实例时可能重复 |
| 失败语义 | 单 registry，失败边界清楚 | `MultipleServiceRegistry` 逐个委托；中途失败可能“部分注册” | 需要幂等重试/对账；不能假设原子 |
| 注册事件 | 官方无细粒度注册生命周期事件 | AOP 发布 Pre/Registered/PreDeregistered/Deregistered | 适合观测，但事件与真实注册结果要区分 |
| Feign 刷新 | 官方配置刷新不重建 Feign 组件 | `@EnableFeignAutoRefresh` 监听配置变更重建组件 | 解决真实痛点；需验证刷新期间请求行为 |

## 结论模板

```text
问题：……
官方：有/无/部分；语义是……
Microsphere：补了什么，代价是……
正确性风险：……
我们的选择：……（Lab 路径）
```

> Lab 只证明“接线和 API 用法正确”，不证明生产正确性；生产结论必须补集成测试和故障演练。
