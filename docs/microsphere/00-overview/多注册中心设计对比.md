# 多注册中心设计对比：Spring Cloud / SCA / Dubbo / Microsphere

> 问题：一个服务实例同时注册到多个注册中心，消费者如何拿到合并后的实例列表？
> 结论先行：**“委托 + 聚合”是共同思想，但注册方向、合并语义、去重、元数据、失败边界完全不同；Dubbo 的实现值得单独学。**

## 1. 官方基线

### Spring Cloud

- 默认一个 `ServiceRegistry` / `AutoServiceRegistration`，没有多注册编排；
- `CompositeDiscoveryClient` 只做**读侧聚合**，且 `getInstances` 取**第一个非空**的 client 结果（短路），不是全量合并；
- 没有 `CompositeServiceRegistry`。

### Spring Cloud Alibaba

- `NacosServiceRegistryAutoConfiguration` 只创建一个 `NacosServiceRegistry` + `NacosAutoServiceRegistration`；
- Nacos 多集群/多命名空间是同一个注册中心内部的 HA/隔离，不是“多个注册中心产品”；
- 不提供多注册中心能力。

### Apache Dubbo

Dubbo 明确提供了 `dubbo-registry-multiple` 模块：

- `MultipleRegistry` / `MultipleRegistryFactory`
- `MultipleServiceDiscovery` / `MultipleServiceDiscoveryFactory`

支持 `service-registry`（提供者注册）与 `reference-registry`（消费者订阅）**分开配置**，这是比 Spring Cloud 更强的方向性设计。

### Microsphere

- `MultipleServiceRegistry`：按 `Registration` 类型委托到多个 `ServiceRegistry`；
- `MultipleRegistration`：聚合多个 Registration；
- `UnionDiscoveryClient`：所有 `DiscoveryClient` 实例并集；
- `EventPublishingRegistrationAspect`：注册生命周期事件；
- `@EnableFeignAutoRefresh`：配置变化重建 Feign 组件。

## 2. 设计点对比

| 维度 | Spring Cloud | SCA | Dubbo `dubbo-registry-multiple` | Microsphere |
|---|---|---|---|---|
| 多注册 | ❌ | ❌ | ✅ | ✅ |
| 注册方向 | 单 registry | Nacos | **service-registry / reference-registry 分离** | 所有 `ServiceRegistry` 一视同仁 |
| 配置模型 | Bean | Nacos 配置 | registry URL 列表 + `separator` | Spring Bean + Registration 类型 |
| 读侧聚合 | `CompositeDiscoveryClient` 第一个非空 | — | `MultipleServiceDiscovery` 全量并集 | `UnionDiscoveryClient` 全量并集 |
| 去重 | 不跨 client | — | `lookup` 结果 `distinct`；通知合并 | Union 不保证去重 |
| 空结果 | 第一个非空；全空返回空 | — | 处理 `EMPTY_PROTOCOL`，全空才通知空 | 直接拼接 |
| 注册元数据 | 无统一多注册元数据 | — | registry `attachments` 附加到 provider URL | `RegistrationMetaData` 跨 Registration 同步 |
| 服务发现元数据 | 各 client 自己负责 | Nacos | `MultipleServiceDiscovery` 的 `getLocalMetadata/getRemoteMetadata/lookup` 部分**不支持** | `ServiceInstance` 原样聚合；不去重 |
| 失败语义 | 单 registry | 单 registry | 逐个委托；无分布式事务，可能部分成功 | 逐个委托；无分布式事务，可能部分成功 |
| 扩展方式 | `DiscoveryClient` | Nacos starter | Dubbo SPI（RegistryFactory / ServiceDiscoveryFactory） | Spring Boot 自动配置 + Registration 类型 |
| 适用场景 | 单注册中心 | Nacos 单注册 | RPC 多注册/多订阅、注册与订阅分离 | Spring Cloud 多注册/发现聚合 |

## 3. 核心思想：一样吗？

**一样的一半：**

- 都是 **Composite / Delegating**：把多个底层注册中心组合成对上层的一个门面；
- 注册写操作广播到多个子实现；
- 读操作做聚合或选择；
- 都需要回答“部分失败怎么办、重复实例怎么办、元数据从哪来”。

**不一样的一半（也是要学的）：**

1. **Dubbo 把“提供者注册”和“消费者订阅”拆成两套 registry 集合**  
   `service-registry` 与 `reference-registry` 可以不同：提供者只注册到 A，消费者可以从 A+B 订阅。  
   Spring Cloud / Microsphere 没有这个方向性拆分，所有 `ServiceRegistry` 一起注册。

2. **Dubbo 的合并语义更细**  
   - `lookup` 结果去重；
   - 通知合并处理 `EMPTY_PROTOCOL`（一个注册中心空、另一个有实例时的语义）；
   - registry `attachments` 会附加到 provider URL，用于按注册中心做流量治理。

3. **Dubbo 明确承认边界**  
   `MultipleServiceDiscovery` 对 `getLocalMetadata/getRemoteMetadata/lookup` 有“不支持”分支，不假装全能力；Microsphere 的 Union 则是“能拼就拼”，重复/元数据冲突要调用方自己处理。

4. **Microsphere 的注册按 Registration 类型分发**  
   Nacos + Eureka 可区分（不同类型）；两个 Nacos（不同集群/命名空间）都是 `NacosRegistration`，类型相同，按类型分发无法区分。  
   这是 Microsphere 设计的硬边界，不是配置问题。

5. **失败模型都不是事务**  
   Dubbo 和 Microsphere 都是顺序委托，某个 registry 抛异常时可能“前面已注册、后面没注册”。  
   生产上必须补：幂等重试、对账、注册状态检查，不能假设多注册原子。

## 4. 我们能学到什么

- 多注册不是“for 循环调 register”这么简单，核心设计问题是：
  - **注册方向**（provider / consumer 是否分离）
  - **实例身份与去重**（同一个实例在多个注册中心如何识别）
  - **空/部分失败语义**
  - **元数据归属**（registry-specific metadata/attachments）
  - **读写一致性**（注册成功但订阅未生效、反之）
- Dubbo 的 `service-registry` / `reference-registry` 分离 + `attachments` 是值得借鉴的成熟设计；
- Microsphere 的 `MultipleServiceRegistry` + `UnionDiscoveryClient` 更贴近 Spring Cloud 生态，但类型分发、去重、部分失败需要额外评审；
- **官方也不等于正确**：Spring Cloud 的 Composite 短路、SCA 的单 Nacos、Dubbo 的“部分能力不支持”，都是明确取舍。

## 5. 待验证问题

1. 我们的场景是“双注册迁移”还是“永久多活”？前者可接受部分失败 + 对账，后者要求更强一致性；
2. 两个注册中心是否是不同类型（Nacos + Eureka）？如果是两个 Nacos 集群，Microsphere 的 Registration 类型分发不适用；
3. 同一实例在多个注册中心的 `instanceId` 是否一致？不一致时 Union 会重复；
4. 注册失败/注销失败如何补偿？是否需要注册状态对账任务？
5. 是否真的需要多注册，还是只需要“多订阅”（官方 Composite 可能够用）？

## 6. 证据

- Spring Cloud：`CompositeDiscoveryClient`、`ServiceRegistryAutoConfiguration`
- SCA：`NacosServiceRegistryAutoConfiguration`
- Dubbo：`dubbo-registry-multiple/MultipleRegistry`、`MultipleServiceDiscovery`
- Microsphere：`MultipleServiceRegistry`、`MultipleRegistration`、`UnionDiscoveryClient`
