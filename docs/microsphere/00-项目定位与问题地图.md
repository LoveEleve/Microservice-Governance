# 00 · 项目定位与问题地图

> **口径**：问题先行 → 官方基线 → 本项目实现 → 边界 → 决策。**Microsphere/Poly 不是正确性标准。**
> **一句话**：这个项目不是“又一个服务框架”，而是在 Spring Cloud / Spring Cloud Alibaba / Dubbo 生态的扩展点上，补齐服务治理空白，并提供可验证的实现与对照。
> **系列**：42 篇，见 [00-系列规划](00-系列规划.md)；功能地图见 [功能地图](00-overview/功能地图.md)。

---

## 0. 先看一条运行时治理链

一个服务实例上线，通常要同时回答：

```
注册：注册到哪个/哪些注册中心？
发现：消费者如何拿到多注册中心的实例？
配置：配置变更如何生效，失败如何回滚？
流量：选哪个实例，是否同区域，权重多少？
容错：超时/重试/熔断/限流怎么组合？
入口：网关如何动态路由，如何控制暴露面？
多活：机房故障怎么切，数据面跟不跟？
观测：注册/配置/路由/Zone 出问题，怎么定位？
```

这条链上的每一个问题，官方生态都有“基线能力”，但基线之间存在缝隙：

- Spring Cloud 默认单 `ServiceRegistry`；
- `CompositeDiscoveryClient` 是“取第一个非空”，不是全量合并；
- Spring Cloud Alibaba 只提供 Nacos 注册；
- 官方没有完整的多活 Zone 抽象；
- 配置刷新、Feign 组件重建、注册生命周期事件都缺少统一编排。

**本项目就是围绕这些缝隙做扩展，而不是替代官方。**

---

## 1. 项目是什么、不是什么

### 1.1 是什么

| 维度 | 事实 |
|---|---|
| 形态 | 一组独立的 Maven 扩展库，不是单体运行时 |
| 生态 | Spring Framework / Spring Boot / Spring Cloud / SCA / 数据访问生态 |
| 核心能力 | 多注册中心、统一发现、注册生命周期、配置动态化、LB、容错、网关、多活、可观测 |
| 数据面 | Redis 复制、MyBatis/Druid 增强、动态数据源、PolyData/PolyCache |
| 验证方式 | 源码 + 官方对照 + Lab/测试；不要求真实中间件全部启动 |

### 1.2 不是什么

- **不是注册中心/配置中心本身**：Nacos、Eureka 仍是外部系统；
- **不是 Service Mesh**：没有 sidecar/xDS 数据面；
- **不是完整治理平台**：没有控制台、租户、审计、计费；
- **不是 Spring Cloud 的替代品**：它是在官方扩展点上做增强；
- **不是“20 个仓库同等重要”**：核心、支撑、历史仓库要分层。

### 1.3 两条线

| 线 | 范围 | 写作 |
|---|---|---|
| A 服务治理 | 注册/发现、配置、LB、容错、网关、多活、观测 | 30 篇 |
| B 数据面 | Microsphere Redis/MyBatis/Druid/Dynamic + PolyData/PolyCache | 9 篇 |
| C 工程 | 测试、故障注入、面试收口 | 3 篇 |

> 规划统一，写作/简历分线；不把数据面混进“服务治理”简历。

## 2. 官方基线：先知道“官方已经做了什么”

| 能力 | 官方基线 | 基线边界 |
|---|---|---|
| 注册 | Spring Cloud `ServiceRegistry` / `AutoServiceRegistration` | 默认单注册中心 |
| 注册实现 | SCA `NacosServiceRegistry` | 只接 Nacos，无多注册编排 |
| 发现聚合 | `CompositeDiscoveryClient` | `getInstances` 取第一个非空，不合并全量 |
| 配置 | Spring Cloud Config/Refresh；SCA Nacos Config | 刷新粒度、回滚、刷新风暴需自行处理 |
| 负载均衡 | Spring Cloud LoadBalancer | Zone/权重/保护需组合扩展 |
| 容错 | Sentinel / Resilience4j | 规则来源、fallback、重试放大需治理 |
| 网关 | Spring Cloud Gateway | 动态路由、端点级控制需扩展 |
| 多活 | 无统一抽象 | Zone 定位、切流、数据面联动需自建 |
| 观测 | Micrometer / OpenTelemetry | 治理链路状态需自定义指标 |
| 数据访问 | Spring Data Redis / MyBatis / Druid | 多机房复制、动态数据源需扩展 |

**Dubbo 是重要对照**：它有多注册模块 `dubbo-registry-multiple`，并且把 `service-registry` 与 `reference-registry` 分开；这比 Spring Cloud 的单注册模型更接近生产多注册需求。

## 3. 问题地图

### 3.1 注册与发现

- 一个实例如何同时注册到 Nacos + Eureka？
- 两个 Nacos 集群（同 Registration 类型）如何区分？
- 部分注册失败、注销失败、实例重复、元数据冲突怎么处理？
- 官方 `CompositeDiscoveryClient` 的短路语义是否满足“全量合并”？

### 3.2 配置与动态化

- 配置变更如何进入 `Environment`？
- 属性级刷新 vs Bean/Feign 组件重建，边界在哪？
- 刷新风暴、旧值、回滚、灰度怎么处理？

### 3.3 负载均衡与多活

- 同区域优先如何避免“偏好致死”？
- 权重、就绪率、最小可用数如何共同决策？
- 切 Zone 时数据面（数据源/Redis）是否跟随？
- 切错/故障恢复如何秒级回滚？

### 3.4 容错

- 重试预算如何避免放大？
- 熔断半开、fallback、隔离边界怎么定义？
- 哪些失败可重试，哪些必须快速失败？

### 3.5 网关

- 动态路由刷新期间如何保证一致性？
- 服务发现接入、端点级控制、认证/限流/背压如何组合？

### 3.6 可观测性

- 注册成功了吗？配置生效了吗？流量切对了吗？
- 指标基数、采样、日志成本、告警降噪怎么控制？

### 3.7 数据面

- Redis 多机房复制如何保序、防回环、至少一次？
- 动态数据源如何热替换、隔离 ORM、兼容 ShardingSphere？
- 数据面的故障是否会影响服务治理判断？

### 3.8 工程与兼容

- Spring Boot / Spring Cloud / SCA 多版本如何兼容？
- 扩展库如何测试、灰度、回滚？
- 哪些是库的能力，哪些是接入方必须补的？

## 4. 项目结构：按能力，不按仓库

| 层 | 代表项目 | 作用 |
|---|---|---|
| 服务治理核心 | `microsphere-spring-cloud`、`microsphere-nacos`、`microsphere-configuration`、`dynamic`、`microsphere-gateway`、`microsphere-multiactive`、`sentinel`、`microsphere-resilience4j` | 治理主链 |
| 可观测 | `observability`、`logging` | 指标/日志/健康 |
| 基础 | `microsphere-java`、`microsphere-spring`、`spring-boot`、`microsphere-bom`、`microsphere-build` | 扩展机制/构建底座 |
| 数据面 | `microsphere-redis`、`microsphere-mybatis`、`microsphere-druid`、`dynamic`、PolyData/PolyCache | 数据访问/复制/动态数据源 |
| 历史/非主线 | `confucius-commons`、`java-enterprise` 等 | 不作为当前主线 |

> 20 个仓库不是 20 个同等章节；先抓核心治理链，再补数据面，最后按需看基础/历史。

## 5. 设计主线：扩展点 → 机制 → 边界

读这个项目，始终围绕三个问题：

1. **它挂在哪个扩展点？**
   - `AutoConfiguration.imports`
   - `EnvironmentPostProcessor` / `PropertySource`
   - `BeanPostProcessor` / AOP
   - `ServiceRegistry` / `DiscoveryClient`
   - `LoadBalancer` / `Gateway` / `Feign`
2. **它补了什么机制？**
   - 委托、聚合、事件、刷新、过滤、保护、重放。
3. **它的边界在哪？**
   - 部分失败、重复、顺序、一致性、容量、兼容、回滚。

> 学一个模式，理解多个仓库；不要按类逐个背。

## 6. 怎么读、怎么验证

1. **读 README + pom + 模块边界**：先知道它是什么；
2. **找官方基线**：官方有没有？语义是什么？
3. **找扩展入口**：AutoConfiguration / SPI / BPP / AOP；
4. **追一条主链**：注册、刷新、路由、Zone 切换；
5. **写最小 Lab**：只验证接线与 API，不要求真实中间件；
6. **记边界**：把失败/重复/规模问题记入 `06-production`；
7. **对照 Poly/Dubbo/官方**：同一问题的另一套实现。

---

## 7. 边界与风险

- Microsphere/Poly 是生产级项目，但**不同模块成熟度不同**；
- 多注册中心按 Registration 类型分发，有“同类型 Nacos 无法区分”的硬边界；
- Union 是拼接，不保证去重；
- 部分注册失败没有分布式事务；
- 配置刷新、Zone 切换、数据面一致性都需要额外验证；
- 数据面与治理面不能混为一谈。
