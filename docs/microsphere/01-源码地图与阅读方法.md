# 01 · 源码地图与阅读方法

> **口径**：按能力读，不按 20 个仓库平铺；先找扩展点，再看实现，最后用 Lab 和边界验证。
> **一句话**：这个项目的源码地图不是“仓库清单”，而是 **一条治理链 + 四条支撑线**；读法不是“从第一个类看到最后一个类”，而是 **问题 → 官方基线 → 扩展点 → 主链 → 边界**。
> **系列**：42 篇，见 [00-系列规划](00-系列规划.md)；定位见 [00 项目定位与问题地图](00-项目定位与问题地图.md)。

---

## 0. 先看一条请求会经过哪些模块

以“服务实例上线 + 消费者调用”为例：

```
Provider 启动
  → Spring Boot 自动配置
  → Microsphere Spring Cloud 多注册编排
  → Nacos/Eureka ServiceRegistry
  → 注册生命周期事件

Consumer 调用
  → DiscoveryClient / UnionDiscoveryClient
  → LoadBalancer（Zone/权重）
  → OpenFeign（可动态刷新）
  → 容错（Sentinel/Resilience4j）
  → Gateway（如果是入口流量）
  → Metrics/Logging/Tracing
```

这条链上的每一段，对应不同的 Maven 模块和扩展点。**地图的价值，是让你知道该跳到哪一段，而不是从 `microsphere-java` 第一行开始读。**

## 1. 源码分层：核心、支撑、数据面、历史

| 层 | 项目 | 作用 | 阅读优先级 |
|---|---|---|---|
| **服务治理核心** | `spring-cloud`、`microsphere-nacos`、`microsphere-configuration`、`dynamic`、`microsphere-gateway`、`microsphere-multiactive`、`sentinel`、`microsphere-resilience4j` | 注册/发现、配置、LB、容错、网关、多活 | P0 |

| **数据面** | `microsphere-redis`、`microsphere-mybatis`、`microsphere-druid`、`dynamic` + PolyData/PolyCache | Redis 复制、SQL/连接池、动态数据源 | P1（B 线） |

> **核心判断**：这一段是否参与“服务上线→发现→调用→治理→观测”的运行时闭环？不参与，就不是主线。

## 3. 阅读方法：五遍读法

### 第 1 遍：读边界（README + pom + modules）

- 这个仓库解决什么问题？
- 有哪些 Maven 模块？哪些是 API、哪些是自动配置、哪些是测试？
- 依赖了哪些官方库/其他 Microsphere 仓库？

> 目标：不读代码，先画出“模块边界 + 依赖方向”。

### 第 2 遍：找官方基线

- 官方是否已有同能力？
- 官方语义是什么？（例如 `CompositeDiscoveryClient` 取第一个非空）
- 本项目的差异点在哪？

> 目标：避免把“官方能力”误认为“本项目贡献”。

### 第 3 遍：找扩展入口

按优先级：

1. `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
2. `META-INF/spring.factories`
3. `@AutoConfiguration` / `@Configuration` + `@Conditional*`
4. `BeanPostProcessor` / `BeanFactoryPostProcessor`
5. `ApplicationListener` / `@EventListener`
6. SPI：`ServiceLoader` / Dubbo/Spring 扩展文件

> 目标：知道“它从哪里挂进去”，而不是从工具类开始读。

### 第 4 遍：追一条主链

每个仓库只追 1–2 条主链：

- 注册：`AutoServiceRegistration` → `ServiceRegistry.register` → 事件；
- 发现：`DiscoveryClient.getInstances` → 聚合/过滤 → LB；
- 配置：`PropertySource` → `Environment` → 刷新事件；
- 网关：`RouteDefinitionLocator` → 路由 → 谓词/过滤器；
- 多活：`ZoneLocator` → `ZoneContext` → LB/数据面；
- 数据面：代理/拦截器 → 复制/重放/热替换。

> 目标：一条链走通，胜过读 50 个类。

### 第 5 遍：写 Lab + 记边界

- 最小 Lab：只验证接线/API，不要求真实中间件；
- 边界：部分失败、重复、顺序、一致性、容量、兼容；
- 对照：官方、Dubbo、Poly 的另一套实现；
- 记录：`06-production` 只记内部缺陷，不进简历。

## 4. 三条阅读线

### A 线：服务治理

```
spring-cloud（注册/发现/Feign）
  → nacos（注册实现）
  → configuration/dynamic（配置）
  → multiactive（Zone）
  → sentinel/resilience4j（容错）
  → gateway（入口）
  → observability/logging（观测）
```

### B 线：数据面

```
redis（SDR 代理/复制）
  → mybatis（SQL/Executor）
  → druid（连接池）
  → dynamic（动态数据源）
  → PolyData（子上下文/热替换/分片）
  → PolyCache（命令复制/重放）
```

### C 线：基础底座

```
microsphere-java / microsphere-spring / spring-boot
  → 按需查，不从头通读
```

## 6. 八个坑

1. **从 `microsphere-java` 第一行开始读**：基础工具不是治理主线，容易迷路。
2. **按仓库平铺**：20 个仓库不是 20 章；按能力链读。
3. **把官方能力当本项目贡献**：先看官方基线。
4. **只看自动配置类**：不看 `@Conditional` 和 `spring.factories`，会误判生效条件。
5. **只追读路径**：写路径（注册/刷新/切换）才是治理核心。
6. **不做对照**：Dubbo/Poly/官方往往有另一种设计。
7. **不写 Lab**：只看代码，无法验证接线和边界。
8. **不记边界**：把实现当标准答案，面试深挖会露馅。
