# 02 · 五步评审法：问题 → 官方 → Microsphere → 边界 → 决策

> **口径**：Microsphere/Poly 是候选答案，不是正确性标准。每篇源码分析都必须能回答“官方有没有、本项目补什么、哪里会坏、我们怎么选”。
> **一句话**：五步评审法不是读书笔记模板，而是**技术决策模板**——用来判断一个实现值不值得用、该怎么改、能不能写进简历。
> **系列**：42 篇，见 [00-系列规划](00-系列规划.md)；方法索引见 [技术评审方法](00-overview/技术评审方法.md)。

---

## 0. 先看一个真实评审：多注册中心

问题：一个服务实例要同时注册到 Nacos 和 Eureka，消费者要拿到两边实例的并集。

| 步骤 | 结论 |
|---|---|
| 问题 | 双注册迁移/多注册中心；部分失败、重复实例、注销漂移 |
| 官方 | Spring Cloud 默认单 `ServiceRegistry`；`CompositeDiscoveryClient` 取第一个非空；SCA 只接 Nacos；Dubbo 有 `dubbo-registry-multiple` |
| Microsphere | `MultipleServiceRegistry` 按 Registration 类型委托；`UnionDiscoveryClient` 全量并集 |
| 边界 | 同类型 Nacos 无法区分；Union 不去重；部分注册无事务；`Composite` 短路语义不同 |
| 决策 | 异构注册中心可用；双 Nacos 需扩展 registry identity；生产要补对账/失败处理 |

这就是五步法：**不是“这个类怎么写的”，而是“这个设计是否成立”。**

---

## 1. 第一步：问题

### 1.1 问题必须具体

不要写“服务治理”“多注册中心”这种大词，要写成场景：

```
一个服务实例要同时注册到 A/B 两个注册中心；
A 成功、B 失败时，实例状态是什么？
消费者拿到 A+B 的实例后，同一实例出现两次怎么办？
```

### 1.2 问题模板

| 项 | 内容 |
|---|---|
| 场景 | 谁在什么条件下做什么？ |
| 约束 | 一致性/可用性/延迟/兼容/成本 |
| 不解决会怎样 | 故障/数据错/不可运维 |
| 成功标准 | 可观测、可回滚、可验证 |

> 问题不清，后面的源码分析一定跑偏。

---

## 2. 第二步：官方基线

### 2.1 三件事必须查

1. **版本**：Spring Boot/Cloud/SCA/Dubbo 的版本语义可能不同；
2. **API**：官方类/扩展点是什么；
3. **语义**：不是“有没有”，而是“怎么行为”。

### 2.2 示例

| 能力 | 官方基线 | 关键语义 |
|---|---|---|
| 注册 | Spring Cloud `ServiceRegistry`/`AutoServiceRegistration` | 默认单注册中心 |
| 发现聚合 | `CompositeDiscoveryClient` | `getInstances` 取第一个非空 |
| Nacos | SCA `NacosServiceRegistryAutoConfiguration` | 只创建 Nacos 注册 |
| 多注册 | Dubbo `dubbo-registry-multiple` | `service-registry`/`reference-registry` 分离；`lookup` 去重 |

> 官方基线不是“官方一定对”，而是“先知道默认行为”，再判断扩展是否改变了语义。

---

## 3. 第三步：Microsphere 实现

### 3.1 只问四个问题

1. **挂在哪**：AutoConfiguration / BPP / AOP / SPI / Listener？
2. **补什么**：委托、聚合、事件、刷新、过滤、保护？
3. **假设是什么**：Registration 类型、实例 identity、配置模型？
4. **代价是什么**：复杂度、兼容性、失败语义、运维成本？

### 3.2 示例：MultipleServiceRegistry

- 挂载：`ServiceRegistryAutoConfiguration.MultipleConfiguration`；
- 机制：`MultipleRegistration` 按 Registration 类型建 map，`MultipleServiceRegistry` 按类型委托；
- 假设：不同注册中心使用不同 Registration 子类型；
- 代价：同类型 Nacos 无法区分；部分失败无事务；Union 不去重。

> 这一段要能画出“扩展点 → 关键类 → 数据流”，不能只贴类名。

---

## 4. 第四步：正确性与边界

固定检查 8 个维度：

| 维度 | 要问什么 |
|---|---|
| 失败 | 部分失败/超时/不可达时，状态是什么？ |
| 重复 | 重复注册/重复注销/重复消费是否幂等？ |
| 顺序 | 注册/注销/配置变更的顺序是否重要？ |
| 一致性 | 本地状态与注册中心/配置中心是否一致？ |
| 去重 | 同一实例多注册中心出现两次怎么办？ |
| 规模 | 容量、热点、长尾、成本？ |
| 迁移 | 双写、灰度、回滚、对账？ |
| 安全/兼容 | 鉴权、版本、依赖冲突？ |

### 示例结论

- `MultipleServiceRegistry` 顺序委托：A 成功、B 失败 → 部分注册；
- `UnionDiscoveryClient` 拼接：同一实例可能重复；
- `CompositeDiscoveryClient` 短路：与 Union 的全量语义不同；
- 同类型 Nacos：按 Registration 类型分发失效。

> 边界不是“缺点清单”，是**设计成立的条件**。

## 6. 反模式

1. **源码行号崇拜**：只贴行号，不解释设计；
2. **README 当真相**：README 可能滞后于代码；
3. **单仓库视角**：不看官方/Dubbo/Poly 对照；
4. **把官方能力当项目贡献**：例如“集成 Sentinel”不是你的设计；
5. **只写 happy path**：没有失败、重复、顺序、容量；
6. **用未实测的数字写简历**：延迟/可用性必须有证据；
7. **把缺陷清单当简历**：简历写能力，缺陷台账内部用；
8. **没有决策**：分析完不知道用哪个，等于没分析。

---

## 7. P7/P8 怎么用

P7/P8 面试不会只问“这个类干嘛”，会问：

- 为什么官方不这么做？
- 你的扩展改变了什么语义？
- 部分失败怎么办？
- 迁移/回滚怎么做？
- 规模上来后哪里先坏？
- 你凭什么说它对？

五步评审法就是把这些问题的答案提前写好。
