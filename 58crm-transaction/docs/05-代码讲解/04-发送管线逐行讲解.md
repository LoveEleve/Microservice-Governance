# 发送管线：逐行源码讲解

> 目标：说清事件从 `OutboxRecord` 到 Redis Stream 的每一步，以及失败时为什么这样处理。
> 机械 accessor 见 `01-生产端类与方法全解`。

## 4. `OutboxBuffer.put`

```java
public void put(OutboxRecord record) throws InterruptedException {
    long bytes = estimateBytes(record);
    if (bytes > maxBytes) {
        throw new MessageTooLargeException(...);
    }
    lock.lockInterruptibly();
    try {
        while (messageCount >= maxMessages || byteCount + bytes > maxBytes) {
            notFull.await();
        }
        ArrayDeque<OutboxRecord> queue =
            queues.computeIfAbsent(record.bizCode(), ignored -> new ArrayDeque<>());
        if (queue.isEmpty()) {
            ready.addLast(record.bizCode());
        }
        queue.addLast(record);
        messageCount++;
        byteCount += bytes;
        notEmpty.signalAll();
    } finally {
        lock.unlock();
    }
}
```

逐段：

1. `estimateBytes`

```text
估算 payload/payloadRef 的字节数
```

2. `bytes > maxBytes`

```text
单条永远放不进去
抛异常，让 Scanner 转 DEAD
不能 await 死锁
```

3. 加锁

```text
所有队列、计数、ready 都由同一把锁保护
```

4. 容量等待

```text
条数超限或字节超限 -> notFull.await()
```

5. 选择队列

```text
bizCode=lead -> queues["lead"]
```

6. 从空变非空

```text
ready.addLast(bizCode)
```

7. 入队

```text
queue.addLast
messageCount++
byteCount += bytes
```

8. 唤醒 Sender

```text
notEmpty.signalAll()
```

输出：

```text
成功 -> 消息进入对应 bizCode 队列
满 -> 阻塞直到有空间
超大 -> MessageTooLargeException
```

## 5. `OutboxBuffer.poll(Set)`

```java
public OutboxRecord poll(Set<String> bizCodes, Duration timeout) {
    while (true) {
        Iterator<String> iterator = ready.iterator();
        while (iterator.hasNext()) {
            String bizCode = iterator.next();
            if (!bizCodes.contains(bizCode)) {
                continue;
            }
            queue = queues.get(bizCode);
            if (queue == null || queue.isEmpty()) {
                iterator.remove();
                continue;
            }
            record = queue.removeFirst();
            if (queue.isEmpty()) {
                iterator.remove();
            }
            ...
            return record;
        }
        // 没有自己负责的 ready 队列 -> 等待
    }
}
```

关键：

```text
只处理 assignedBizCodes
跳过不属于自己的队列
队列空时从 ready 移除
每次减 count/bytes 并 signal notFull
```

输出：

```text
有消息 -> 返回 OutboxRecord
超时 -> null
线程中断 -> InterruptedException
```

## 6. `OutboxBuffer.drain`

```java
public int drain(String bizCode, List<OutboxRecord> target, int maxElements) {
    queue = queues.get(bizCode);
    while (drained < maxElements && !queue.isEmpty()) {
        record = queue.removeFirst();
        messageCount--;
        byteCount -= estimateBytes(record);
        target.add(record);
        drained++;
    }
    if (queue.isEmpty()) ready.remove(bizCode);
    notFull.signalAll();
    return drained;
}
```

输出：

```text
实际取走条数
```

## 7. `OutboxScanner.scanOnce`

```java
List<LocalMessage> candidates = repository.findRelayCandidates(scanBatch);
for (LocalMessage candidate : candidates) {
    if (!inFlight.add(candidate.msgId())) {
        continue;
    }
    try {
        registry.require(candidate.bizCode());
        buffer.put(OutboxRecord.from(candidate));
        accepted++;
    } catch (UnknownBizCodeException ex) {
        reject(candidate);
    } catch (MessageTooLargeException ex) {
        reject(candidate);
    } catch (InterruptedException ex) {
        inFlight.remove(candidate.msgId());
        throw ex;
    }
}
```

逻辑：

1. 按注册 bizCode 轮询，每业务线有 perBizLimit
2. `inFlight.add` 去重

```text
已在 buffer/发送中 -> 跳过
```

3. 校验 bizCode
4. 放入 buffer
5. 未知/超大 -> `reject`

```text
inFlight.remove
markFailedBatch(maxRetries=1)
-> DEAD
```

输出：

```text
本轮成功放入 buffer 的条数
```

## 8. 公平轮转与 LB 参考

参考 Spring Cloud LoadBalancer 的 `LazyWeightedServiceInstanceList`：

```text
active  : 当前轮还有配额的队列
expired : 本轮已选过的队列
active 空 -> active/expired 互换
```

我们不实现权重，只取它的公平调度思想。

在我们的 `OutboxBuffer.poll(Set)` 中：

```text
从 ready 取一个 bizCode
如果队列还有消息
-> 移到 ready 队尾
如果队列空了
-> 从 ready 移除
```

这和所有队列权重都为 1 的 active/expired 轮转等价：

```text
lead 很热
quota 少量
order 偶尔

不会出现：
  lead 永远占 ready 头部
  quota/order 永远轮不到
```

测试：

```text
hotQueue_doesNotStarveOtherAssignedQueues
```

## 9. `SenderAssignment.assign`

```java
List<String> sorted = new ArrayList<>(bizCodes);
sorted.sort(String::compareTo);
int shardCount = Math.min(senderThreads, sorted.size());

for (int i = 0; i < sorted.size(); i++) {
    int shard = i % shardCount;
    assignments.computeIfAbsent(shard, ignored -> new LinkedHashSet<>())
               .add(sorted.get(i));
}
```

例子：

```text
biz: contract, customer, lead, order, quota
threads=3
shardCount=3

i=0 contract -> 0
i=1 customer -> 1
i=2 lead     -> 2
i=3 order    -> 0
i=4 quota    -> 1
```

输出：

```text
Map<shard, Set<bizCode>>
```

## 10. `OutboxSender.sendOnce`

核心步骤：

```text
1. buffer.poll(assignedBizCodes, linger)
2. 继续在 assigned 队列聚合，直到 batchSize 或 deadline
3. 拦截器 onSend
4. partitioner 分组
5. publishOrSplit
6. finally 移除 inFlight
```

### 聚合

```java
OutboxRecord first = buffer.poll(assignedBizCodes, config.linger());
...
while (batch.size() < config.batchSize()) {
    remaining = deadline - now;
    next = buffer.poll(assignedBizCodes, Duration.ofNanos(remaining));
    if (next == null) break;
    batch.add(next);
}
```

为什么不是只等第一条 bizCode：

```text
一个 Sender 负责多个 bizCode
只等 lead 会让 quota 积压
```

### 身份保护

```java
Map<String, OutboxRecord> originalByMsgId = ...
List<OutboxRecord> originals = originalsOf(records, originalByMsgId);
```

原因：

```text
拦截器可以改 payload
但不能改 msgId/bizId/status
状态回写要用原始记录
```

### 状态回写

```java
publisher.publish(stream, fields);
repository.markSentBatch(toLocalMessages(originals), nextRetryAt);
```

顺序：

```text
先 XADD 成功
再 INIT -> SENT
```

不能反过来。

## 11. `publishOrSplit`

```java
try {
    publisher.publish(stream, fields);
} catch (RuntimeException ex) {
    if (records.size() == 1) {
        publishFailed(originals, nextRetryAt, ex);
        return 0;
    }
    int middle = records.size() / 2;
    sent += publishOrSplit(records[0..middle], ...);
    sent += publishOrSplit(records[middle..], ...);
    return sent;
}
```

作用：

```text
整批失败 -> 二分
最终定位单条 poison
好消息继续成功
坏消息单独失败
```

注意：

```text
如果是 Redis 整体不可用
二分会产生较多重试更新
后续应区分连接级失败
```

## 13. `OutboxProducer.start`

```java
scannerExecutor = single schedule thread
senderExecutor = fixed pool(senders.size)
scannerExecutor.scheduleWithFixedDelay(scanSafely, 0, scanInterval)
for sender: senderExecutor.submit(() -> sendLoop(sender))
```

线程：

```text
1 个 Scanner
N 个 Sender
N = min(senderThreads, bizCodeCount)
```

## 14. `OutboxProducer.close`

```text
running=false
scannerExecutor.shutdownNow
senderExecutor.shutdownNow
awaitTermination(5s)
interceptors.close
```

## 15. `OutboxProducerFactory.create`

```java
assignments = SenderAssignment.assign(registry.bizCodes(), config.senderThreads());
for (assigned : assignments.values()) {
    senders.add(new OutboxSender(..., assigned));
}
return new OutboxProducer(scanner, senders, ...);
```

推荐的另一个入口：

```text

```

避免调用方把 `scanBatch` 配错。

## 16. `OutboxInterceptorChain`

```java
OutboxRecord current = record;
for (interceptor : interceptors) {
    try {
        next = interceptor.onSend(current);
        if (next != null) current = next;
    } catch (RuntimeException ex) {
        log.warn(...);
    }
}
return current;
```

语义：

```text
顺序执行
前一个结果传下一个
异常隔离
null 不覆盖
```

## 17. `RedisStreamPublisherAdapter.publish`

```java
List<Object> results = redisTemplate.executePipelined(session -> {
    for (fields : records) {
        opsForStream().add(StreamRecords.string(fields).withStreamKey(stream));
    }
});
if (results.size() != records.size()) throw ...
for (result : results) if (result == null) throw ...
```

输出：

```text
全部命令执行 -> 返回
结果数不对/空 -> 抛异常
```

注意：

```text
pipeline 不是原子事务
部分成功可能发生
重试后消费方仍要幂等
```
