# C-001.2 代码讲解：OutboxRelay 与批量 ACK

> 读完你能做什么：说清生产方如何把 MySQL 消息投到 Redis，以及消费成功后如何用一次批量 ACK 收敛状态。

## 1. 本步范围

```text
已做：
  RedisListQueue / RedisListQueueAdapter（批量发送/拉取）
  QueueEnvelope
  OutboxRelay
  MessageAck / MessageAckService
  LocalMessageAckService
  MybatisLocalMessageRepository
  批量 ACK 测试

未做：
  MessageConsumer 的批量消费流程
  消费方 t_consume_record
  消费方 lease
  实际 HTTP ACK Controller
```

## 2. 链路

```text
t_local_message(INIT)
  → OutboxRelay
  → QueueEnvelope
  → Redis List tx:queue:{bizCode}
  → 消费方（C-001.3）
  → 批量 ACK
  → t_local_message(CONSUMED)
```

## 3. 类清单

| 类 | 作用 |
|---|---|
| `QueueEnvelope` | Redis 中传输的消息信封 |
| `RedisListQueue` | 队列接口 |
| `RedisListQueueAdapter` | LPUSH/BRPOP 适配器 |
| `OutboxRelay` | 扫 MySQL，投 Redis，标记 SENT |
| `OutboxRelayScheduler` | 10ms 窗口调度，单批 256，峰值可连续多批 |
| `MessageAck` | 单条 ACK：bizId + msgId |
| `MessageAckService` | 批量 ACK 接口 |
| `LocalMessageAckService` | 批量 ACK 实现 |
| `MybatisLocalMessageRepository` | Relay 查询 / SENT / ACK 更新 |

## 4. 为什么信封要带 payload

只带 `msgId`：

```text
消费方拿到 msgId
→ 按 msgId 查生产方库？
→ 跨服务数据库访问，不允许
```

所以信封带：

```text
bizId
msgId
eventKey
eventType
payload / payloadRef
```

消费方拿到后：

```text
写自己的 t_consume_record
→ 本地重试
```

## 5. Relay

```java
public int relayOnce(int limit) {
    List<LocalMessage> candidates = repository.findRelayCandidates(limit);
    Map<String, List<LocalMessage>> byBizCode = group(candidates);

    int relayed = 0;
    Instant nextRetryAt = Instant.now().plus(retryAfter);
    for (Map.Entry<String, List<LocalMessage>> entry : byBizCode.entrySet()) {
        List<QueueEnvelope> envelopes = entry.getValue().stream()
                .map(QueueEnvelope::from)
                .toList();
        queue.enqueueBatch(entry.getKey(), envelopes);
        repository.markSentBatch(entry.getValue(), nextRetryAt);
        relayed += envelopes.size();
    }
    return relayed;
}
```

关键点：

```text
同业务线合并成一个 batch
一次 Redis pipeline 写入，不是逐条 LPUSH
一次批量 UPDATE 标记 SENT
失败整批不推进，重复由消费方幂等兜底
```

## 5.1 批量发送

```java
void enqueueBatch(String bizCode, List<QueueEnvelope> envelopes);
```

实现：

```text
ObjectMapper 先序列化整批
Redis executePipelined
每条 leftPush
```

不是：

```text
for message:
  LPUSH
  等 Redis 返回
```

## 5.2 批量拉取

`RedisListQueue` 已经提供：

```java
List<QueueEnvelope> dequeueBatch(
    String bizCode,
    int maxCount,
    Duration timeout);
```

实现顺序：

```text
先 RPOP count 非阻塞批量取
队列为空 → 阻塞等第一条
再 RPOP 补足剩余
```

消费方 C-001.3 会使用这个接口做批量消费。

## 5.3 10ms 合并窗口

```java
OutboxRelayScheduler scheduler = new OutboxRelayScheduler(
    relay,
    Duration.ofMillis(10),
    256,
    4);
scheduler.start();
```

含义：

```text
每 10ms 触发一次
单批最多 256 条
一个窗口最多连续跑 4 批
```

为什么需要窗口：

```text
高频单条 relay 会放大 Redis 往返
10ms 合并后按业务线一次 pipeline
```

窗口和批量的关系：

```text
窗口 = 什么时候触发
批量 = 一次处理多少
pipeline = 一次网络往返写多少
```

## 6. 为什么 SENT 还需要重投

Redis List 没有 ACK：

```text
消费者刚 BLPOP 就崩溃
→ Redis 里没了
→ MySQL 还是 SENT
→ 超时后重投
```

重投窗口：

```text
SENT + next_retry_at
```

到时间仍未 ACK：

```text
Relay 再投一次
```

## 7. 为什么 ACK 必须批量

单条 ACK：

```text
每条消息一次 RPC
8W QPS = 8W RPC/s
不可接受
```

批量 ACK：

```text
500 条一批
8W / 500 = 160 RPC/s
```

所以接口是：

```java
int ackBatch(List<MessageAck> acks);
```

不是：

```java
void ack(String msgId);
```

## 8. ACK 更新规则

```sql
UPDATE t_local_message
SET status = 'CONSUMED'
WHERE biz_id = ?
  AND msg_id IN (...)
  AND status = 'SENT';
```

条件更新保证：

```text
重复 ACK 不会改坏状态
已 CONSUMED 不会被改回
未知 msgId 不会误更新
```

## 9. ACK 失败

```text
消费成功
→ ACK 失败
→ 生产方仍 SENT
→ 超时重投
→ 消费方 t_consume_record=CONSUMED
→ 跳过业务
→ 再次批量 ACK
```

结果：

```text
业务不重复
状态最终 CONSUMED
```
