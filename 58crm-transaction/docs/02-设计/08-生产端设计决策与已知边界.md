# 生产端设计决策与已知边界

> 读完你能做什么：知道为什么这样设计、放弃了什么、生产上还要补什么。

## 1. 为什么用 MySQL Outbox

问题：

```text
业务表提交成功
消息还没写
→ 业务成功、通知丢失
```

解决：

```text
业务表 + t_local_message(INIT)
同一个 MySQL 本地事务
```

因此：

```text
业务回滚 -> 消息不存在
业务提交 -> 消息一定存在
```

## 2. 为什么用 Redis Stream 而不是 List

List：

```text
没有 ACK
没有 PEL
没有消费组 offset
```

Stream：

```text
XREADGROUP
XACK
PEL
XCLAIM/XAUTOCLAIM
```

所以 Stream 更符合“至少一次 + 可恢复”的语义。

## 3. 为什么生产方不保存 CONSUMED

Stream 的消费确认由：

```text
XACK
PEL
```

维护。

生产方保留 `CONSUMED` 需要消费方批量 ACK RPC：

```text
每批回写生产方 MySQL
增加网络/数据库压力
```

因此：

```text
SENT 是生产方终态
消费结果由消费者和 Stream PEL 负责
```

## 4. 为什么一个 bizCode 一个内存队列

```text
按业务线隔离
一条线积压不拖死其它线
Sender 可固定归属
批量聚合更稳定
```

不按 msgId/bizId：

```text
msgId 太散
bizId 队列数量爆炸
```

## 5. 为什么有字节容量

只限制条数不够：

```text
50k × 64KB = 3.2GB
```

所以同时限制：

```text
bufferCapacity
bufferCapacityBytes
```

超大消息：

```text
直接 DEAD
不阻塞 Scanner
```

## 6. 为什么 Sender 分片

单 Sender：

```text
所有队列一个线程
阻塞式 Redis pipeline
8W 峰值可能成为瓶颈
```

分片：

```text
线程数 = min(senderThreads, bizCodeCount)
一个 bizCode 只归一个 Sender
```

不会：

```text
线程数 > 队列数
多个线程抢同一队列
```

## 7. 为什么 10ms + 256

```text
10ms = 合并窗口
256 = 单次 pipeline 上限
```

目的：

```text
减少 Redis 往返
控制单批延迟和内存
```

## 8. Pipeline 不是原子事务

Redis pipeline：

```text
不是全部成功/全部失败
可能部分执行
连接可能中途断开
```

因此：

```text
失败重试
可能重复 XADD
消费方必须幂等
```

## 9. 为什么失败要二分拆批

如果整批失败：

```text
一条 poison 消息
→ 整批 256 条全部重试
→ 好消息被拖死
```

二分拆批：

```text
好消息继续成功
坏消息单独失败
```

## 10. 顺序性

不承诺：

```text
全局 FIFO
跨 bizCode 顺序
失败重试后的严格顺序
```

可以做到：

```text
同一 bizCode 正常路径下按队列顺序发送
```

如果下游需要业务顺序：

```text
事件带 version/occurredAt
下游按版本收敛
或按 bizId 串行
```

## 11. 幂等

至少一次：

```text
XADD 重试
markSent 失败重发
进程崩溃重扫
```

消费方必须：

```text
msgId 幂等
bizKey 幂等
```

## 12. 已知边界

```text
没有消费端
没有 XACK/PEL 代码
没有真实 Redis 故障演练
没有 Sender/队列指标
没有 Spring Boot Starter
没有 Nacos 配置加载
没有 XTRIM 策略
没有全局顺序
```

## 13. 生产前必须补

```text
指标：扫描量、发送量、失败、积压、延迟
告警：buffer 深度、DEAD、Stream 长度
故障演练：Redis 断连、重启、主从切换
容量：8W 峰值压测
配置：Nacos/环境变量
```

## 14. 一句话

```text
MySQL 保证不丢
Stream 提供 ACK/PEL
Buffer/Sender 解耦并背压
消费方和 XACK 负责最终消费
```
