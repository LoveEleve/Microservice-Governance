## D-001 MySQL 是正本

```text
业务表 + t_local_message 同事务
Redis 丢失不能影响最终恢复
```

## D-002 使用 Redis Stream，不用 List

```text
List 没有 ACK / PEL / consumer group offset
Stream 有 XREADGROUP / XACK / XPENDING / XCLAIM
```

## D-003 一个业务线一个 Stream

```text
tx:stream:{bizCode}
一个业务线一个消费组
不做多下游 fan-out
```

## D-004 生产方 SENT 不是消费成功

```text
SENT = XADD 已成功
消费成功 = XACK + t_consume_record
```

## D-005 DONE 由对账组件推进

```text
对账确认消费方 CONSUMED
→ t_local_message SENT -> DONE
```

DONE 不能由发送成功直接写。

## D-006 保存 stream_entry_id

```text
XADD 返回 entryId
→ t_local_message.stream_entry_id
→ 对账判断 Stream 中是否还存在
```

## D-007 Sender 按 bizCode 分片

```text
shardCount = min(senderThreads, bizCodeCount)
一个 bizCode 只属于一个 Sender
```

## D-008 ready 队列公平轮转

参考 Spring Cloud LoadBalancer 的 active/expired 思路：

```text
取完一条
如果队列还有消息 -> 移到队尾
如果队列空了 -> 移除
```

无权重时等价于每个队列 remainder=1。

## D-009 两个 10ms 独立

```text
Scanner 10ms：扫描 MySQL
Sender 10ms：linger 批量窗口
```

Scanner 一次最多 `scanBatch` 条，不是一条一条 sleep。

## D-010 发送失败不是立即 DEAD

```text
失败 -> INIT + retry_count + next_retry_at
超限 -> DEAD
DEAD 人工重放 -> INIT
不能直接 DEAD -> SENT
```

## D-011 索引候选

查询：

```sql
WHERE status = 'INIT'
  AND (next_retry_at IS NULL OR next_retry_at <= NOW())
ORDER BY created_at
LIMIT ?
```

现有：

```text
idx_status_retry(status, next_retry_at)
```

问题：

```text
status 等值可以利用
next_retry_at 是范围
created_at 排序可能 filesort
```

候选：

```text
(status, next_retry_at, created_at)
```

或用两条查询：

```text
status=INIT AND next_retry_at IS NULL
status=INIT AND next_retry_at <= now
```

需要 EXPLAIN 验证，不能只凭索引数量判断。
