## D-011 索引候选

查询：

```sql
WHERE status = 'INIT'
  AND (next_retry_at IS NULL OR next_retry_at <= NOW())
ORDER BY created_at
LIMIT ?
```

现有：

```text
idx_status_retry(status, next_retry_at)
```

问题：

```text
status 等值可以利用
next_retry_at 是范围
created_at 排序可能 filesort
```

候选：

```text
(status, next_retry_at, created_at)
```

或用两条查询：

```text
status=INIT AND next_retry_at IS NULL
status=INIT AND next_retry_at <= now
```

需要 EXPLAIN 验证，不能只凭索引数量判断。

## D-012 INIT 扫描索引问题（重点）

当前查询：

```sql
WHERE status = 'INIT'
  AND (next_retry_at IS NULL OR next_retry_at <= NOW())
ORDER BY created_at
LIMIT ?
```

问题：

```text
status = 'INIT' 是等值条件
next_retry_at IS NULL 和 <= NOW() 是两个范围
ORDER BY created_at 在范围条件之后
```

MySQL 索引可以处理：

```text
status 等值
next_retry_at 的 IS NULL / range
```

但 `created_at` 排序很可能需要 filesort，因为：

```text
next_retry_at 已经是范围
范围列后面的 created_at 不能稳定用于全局排序
```

`IS NULL` 本身可以利用索引，InnoDB 二级索引会保存 NULL 项；
但 `IS NULL OR <= NOW()` 的组合会让优化器选择 range/index merge/filesort，不能假设一个联合索引同时完成过滤和排序。

### 候选方案 A

```sql
(status, next_retry_at, created_at)
```

能帮助过滤，但排序仍可能 filesort。

### 候选方案 B：拆查询

```sql
-- 首次投递
WHERE status='INIT' AND next_retry_at IS NULL
ORDER BY created_at

-- 到期重试
WHERE status='INIT' AND next_retry_at <= NOW()
ORDER BY next_retry_at, created_at
```

应用层合并两批，按 next_retry_at/created_at 排序。

### 候选方案 C：归一化时间字段（推荐评估）

发布时不再让 `next_retry_at` 为 NULL，而是：

```text
next_retry_at = created_at
```

查询变成：

```sql
WHERE status = 'INIT'
  AND next_retry_at <= NOW()
ORDER BY next_retry_at
LIMIT ?
```

索引：

```text
(status, next_retry_at)
```

这样：

```text
status 等值
next_retry_at 范围 + 排序使用同一列
不需要 OR
不需要对 created_at 额外排序
```

需要：

```text
发布时写 next_retry_at
历史数据迁移 NULL -> created_at
确认排序语义从 created_at 变为 next_retry_at
```

### 结论

```text
不要只加索引就认为解决
必须先 EXPLAIN / EXPLAIN ANALYZE
重点看：
  type
  key
  rows
  filtered
  Extra: Using filesort / Using index condition
```

## D-013 扫描源头饥饿（严重，已实现无分片修正）

当前 `findRelayCandidates`：

```sql
WHERE status='INIT'
  AND (next_retry_at IS NULL OR next_retry_at <= NOW())
ORDER BY created_at
LIMIT 1000
```

如果最早写入的 1 万条都是：

```text
bizCode = lead
```

则每轮扫描只返回 lead：

```text
Buffer 中只有 lead 队列
quota/order 没有数据
Sender 的 ready 轮转没有对象可轮
```

这不是 Sender 公平性问题，是 Scanner 取数公平性问题。

### 已实现修正（无分片）

```text
findRelayCandidatesByBizCode
Scanner 维护 bizCode cursor
每个 bizCode 每轮 perBizLimit
next_retry_at 首次发布 = created_at
```

剩余：

```text
每业务线 buffer 上限
分片阶段方案
```

### 解决方向

```text
按 bizCode 分组扫描
每个 bizCode 每轮有扫描配额
```

例如：

```sql
-- 对每个 registry.bizCodes()
WHERE biz_code = ?
  AND status = 'INIT'
  AND next_retry_at <= NOW()
ORDER BY next_retry_at, created_at
LIMIT perBizLimit
```

Scanner 用 round-robin 维护起始 bizCode，保证：

```text
lead 再多，也不能吃掉所有扫描名额
quota/order 每轮至少有机会
```

还需要：

```text
每业务线 buffer 上限
  lead 不能把全局 buffer 占满

索引
  (biz_code, status, next_retry_at, created_at)

分片注意
  biz_code 不是分片键，按 bizCode 扫描会广播到所有分片
```

候选 SQL：

```sql
SELECT ...
FROM t_local_message
WHERE biz_code = ?
  AND status = 'INIT'
  AND next_retry_at <= NOW()
ORDER BY next_retry_at, created_at
LIMIT ?
```

## D-014 时间统一使用 UTC

本机 JVM 是 Asia/Shanghai，MySQL 容器是 UTC。
如果使用 `LocalDateTime.now()`：

```text
Java 写入 13:05
MySQL NOW() = 05:05
next_retry_at 看起来在未来 8 小时
Scanner 查不到
```

修正：

```text
生产代码 LocalDateTime.now(ZoneOffset.UTC)
Instant -> LocalDateTime.ofInstant(instant, ZoneOffset.UTC)
数据库时间统一 UTC
```

这是实际验证出来的 Bug，不是理论问题。

## D-015 TC 不发现 RM

```text
错误：TC 查 Nacos 找业务服务，配置 participant serviceName
正确：RM 在 branch register 时提供 callback endpoint
      TC 按 endpoint 调 Confirm/Cancel
```

原因：

```text
依赖方向必须是客户端依赖服务器
服务器不应依赖客户端服务名/地址
```

这是 DTM 风格，不是 TC 主动服务发现 RM。


## D-016 TC 不连接所有 RM

```text
错误：每个 RM 连接所有 TC
问题：连接数膨胀、注册表分散、TC 扩容要全量重连
```

推荐：

```text
RM 在 register 时提供 callback endpoint
TC 任意实例按 endpoint 调用 Confirm/Cancel
```

这是 DTM 风格。
TC 不发现 RM，不配置业务方 serviceName。
第一版不在 TC 内做 stream owner 转发。
