# 核心模型

> 读完你能做什么：说清 MySQL、Redis、TCC、Outbox 各负责什么，以及生产方和消费方为什么不能共用一个状态表。

## 1. 一句话

```text
MySQL 是账本
Redis 是传送带
TCC 管资源预占
Outbox 管已确认事实的通知
```

## 2. TCC

```text
Try     ：预占资源
Confirm ：确认，写最终结果
Cancel  ：释放预占
```

TCC 状态只在 MySQL：

```text
t_tcc_global
t_tcc_branch
t_branch_barrier
```

Redis 不参与：

```text
全局事务状态
分支事务状态
空回滚/悬挂判断
Confirm/Cancel 决策
```

## 3. Outbox 的边界

生产方只负责：

```text
业务表更新
+ t_local_message(INIT)
同一个 MySQL 事务 COMMIT
```

生产方状态：

```text
INIT    未投递
SENT    已投递
DEAD    重投超限
```

生产方不知道：

```text
哪个消费者拿走了
消费者是否处理成功
消费者租约是否过期
```

## 4. 消费方的边界

消费方是另一个服务，使用自己的数据库：

```text
t_consume_record
t_idempotent
t_message_attempt
```

消费者流程：

```text
BLPOP
→ 写自己的 t_consume_record(PROCESSING, lease)
→ 业务处理
→ 更新自己的 t_consume_record(CONSUMED)
```

续约：

```text
消费者更新自己数据库的 lease_until
不请求生产方数据库
```

## 5. 消息链路

```text
生产方业务事务
  → t_local_message(INIT)
  → Relay
  → Redis List
  → 消费方 BLPOP
  → t_consume_record(PROCESSING)
  → 业务 handler
  → t_consume_record(CONSUMED)
```

Redis List 信封：

```text
bizId + msgId + eventKey + eventType + payload/payloadRef
```

只放 `msgId` 不够，因为消费方无法按 `bizId` 路由到分片。

## 6. 消息模型

```text
一条事件 → 一个业务线 List → 一个逻辑消费者
```

不使用消费者组，不做多下游 fan-out。  
需要多个下游时，由上游拆成多条事件。

## 7. 状态归属

生产方：

```text
INIT / SENT / DEAD
```

消费方：

```text
PROCESSING / CONSUMED / DEAD
```

不要把消费方的 `PROCESSING/CONSUMED/lease_until/consumer_id` 放进生产方表。

## 8. 故障语义

```text
业务事务失败 → 没有消息
Redis 丢消息 → 生产方 SENT 超时重投
消费者刚取走就崩溃 → 生产方重投
消费者处理中崩溃 → 消费方 lease 过期重试
重复投递 → msg_id + biz_key 幂等
Confirm 超时 → 协调器重试
Cancel 先到 → SUSPENDED，空回滚
Try 后到 → 拒绝
```

## 9. 关键边界

```text
Redis 只做可丢、可重放的队列
TCC 资源必须在 MySQL
payload 不能只在 Redis
生产方不存消费租约
消费方不远程写生产方库
外部不可逆动作不走 TCC
```
