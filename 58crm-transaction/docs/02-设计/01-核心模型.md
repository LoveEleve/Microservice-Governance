# 核心模型

> 读完你能做什么：说清 MySQL、Redis Stream、TCC、Outbox 各负责什么，以及生产方和消费方为什么不能共用一张状态表。

## 1. 一句话

```text
MySQL 是账本
Redis Stream 是带 ACK 的传送带
TCC 管资源预占
Outbox 管已确认事实的通知
```

## 2. TCC

```text
Try     ：预占资源
Confirm ：确认，写最终结果
Cancel  ：释放预占
```

TCC 状态只在 MySQL：

```text
t_tcc_global
t_tcc_branch
t_branch_barrier
```

Redis 不参与：

```text
全局事务状态
分支事务状态
空回滚/悬挂判断
Confirm/Cancel 决策
```

## 3. Outbox 生产方

```text
业务表更新
+ t_local_message(INIT)
同一个 MySQL 事务 COMMIT
```

生产方状态：

```text
INIT    未投递
SENT    已 XADD 到 Stream
DEAD    XADD/重投超限
```

生产方不知道：

```text
哪个消费者拿走了
消费者是否 XACK
消费者租约
```

## 4. 发送链路

```text
OutboxScanner
  → OutboxBuffer（有界）
  → OutboxSender
      → InterceptorChain
      → Partitioner
      → Serializer
      → RedisStreamPublisher
```

窗口/批量：

```text
10ms linger
单批最多 256
按 bizCode 分组
一次 XADD pipeline
```

## 5. 消费链路

```text
XREADGROUP
→ t_consume_record(PROCESSING)
→ 业务处理
→ t_consume_record(CONSUMED)
→ XACK
```

消费方状态：

```text
PROCESSING
CONSUMED
DEAD
```

消费者崩溃：

```text
未 XACK
→ PEL
→ XPENDING
→ XAUTOCLAIM（Redis 7）
→ 新 consumer 重试
```

## 6. 消息模型

```text
每个业务线一个 Stream：
  tx:stream:{bizCode}

每个业务线一个消费组：
  tx-group-{bizCode}

一个逻辑消费者组
不做多下游 fan-out
```

Stream 的消费组是 ACK/offset 机制，不是“同一事件广播给多个下游”。

## 7. 故障语义

```text
业务事务失败 → 没有消息
XADD 失败 → 状态保持 INIT
Redis 丢数据 → MySQL 重放
消费者崩溃 → PEL + XCLAIM/XAUTOCLAIM
重复投递 → msgId + bizKey 幂等
Confirm 超时 → 协调器重试
Cancel 先到 → SUSPENDED，空回滚
Try 后到 → 拒绝
```

## 8. 关键边界

```text
MySQL 是正本
Stream 是传输层，不是正本
TCC 资源必须在 MySQL
payload 不能只在 Redis
生产方不存消费租约
消费方不远程写生产方库
外部不可逆动作不走 TCC
```
