# 核心模型

> 读完你能做什么：说清 MySQL、Redis、TCC、Outbox 各负责什么，以及一条消息怎么走。

## 1. 一句话

```text
MySQL 是账本
Redis 是传送带
TCC 管资源预占
Outbox 管已确认事实的通知
```

## 2. TCC

```text
Try     ：预占资源
Confirm ：确认，写最终结果
Cancel  ：释放预占
```

TCC 状态只在 MySQL：

```text
t_tcc_global
t_tcc_branch
t_branch_barrier
```

Redis 不参与：

```text
全局事务状态
分支事务状态
空回滚/悬挂判断
Confirm/Cancel 决策
```

## 3. Outbox

业务变更和消息在同一个 MySQL 本地事务：

```text
业务表更新
+ t_local_message(INIT)
COMMIT
```

Relay：

```text
扫 INIT
→ LPUSH tx:queue:{bizLine}
→ SENT
```

消费者：

```text
BLPOP
→ PROCESSING + lease
→ 业务处理
→ t_idempotent
→ CONSUMED
```

## 4. 消息模型

```text
一条事件 → 一个业务线 List → 一个逻辑消费者
```

不使用消费者组，不做多下游 fan-out。  
需要多个下游时，由上游拆成多条事件。

## 5. 状态

TCC 全局：

```text
INIT → TRYING → TRY_SUCCESS → CONFIRMING → CONFIRMED
                    └──────→ CANCELLING → CANCELLED
```

消息：

```text
INIT → SENT → PROCESSING → CONSUMED
                  └──────→ INIT（重试）
超限 → DEAD
```

## 6. 故障语义

```text
业务事务失败 → 没有消息
Redis 丢消息 → MySQL 重放
消费者崩溃 → lease 过期重投
重复投递 → msg_id 幂等
Confirm 超时 → 协调器重试
Cancel 先到 → SUSPENDED，空回滚
Try 后到 → 拒绝
```

## 7. 关键边界

```text
Redis 只做可丢、可重放的队列
TCC 资源必须在 MySQL
payload 不能只在 Redis
外部不可逆动作不走 TCC
```
