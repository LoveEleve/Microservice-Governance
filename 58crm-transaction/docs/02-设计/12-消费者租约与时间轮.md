# 消费者租约与时间轮

> 目标：10W QPS 级别下，Worker 卡死、长任务、并发抢占都能收敛。  
> 原则：业务方只写 handler；续约、超时、fencing、告警由框架完成。

## 1. 问题

多 worker 并发消费：

```text
worker-1 领取 m-1
lease_until = 30s

worker-1 业务卡住 60s
lease 过期

worker-2 领取 m-1
worker-1 还活着
→ 两个 worker 同时执行业务
```

不能靠：

```text
Thread.stop()        破坏锁/连接/事务
无限续约             卡死线程永久占任务
只靠 lease           旧 worker 仍可能提交
```

## 2. 三层机制

```text
Lease       防止并发领取
Renewal     证明 worker 还活着
Fencing     阻止过期 owner 提交
```

### Lease

`t_consume_record`：

```text
status = PROCESSING
owner_token = UUID
lease_version = N
lease_until
max_deadline
```

### Renewal

后台 `LeaseRenewer` 扫描 in-flight，批量延长 lease。

### Fencing

Worker 提交业务事务时：

```sql
UPDATE t_consume_record
SET status='CONSUMED'
WHERE msg_id=?
  AND status='PROCESSING'
  AND owner_token=?
  AND lease_version=?
  AND lease_until > NOW()
```

影响行数为 0：

```text
任务已被接管
→ 业务事务回滚
→ 旧 worker 不能提交
```

## 3. 时间轮设计

10W QPS 不能：

```text
每条消息 new Timer
每个任务一个 ScheduledFuture
每个任务一个线程
```

使用 **分桶时间轮**：

```text
tick = 1s
wheelSize = 512
lease = 60s
renewAfter = 20s
maxProcessing = 5min
```

结构：

```text
Bucket[0]  -> [task, task, ...]
Bucket[1]  -> [...]
...
Bucket[511]
```

每个任务只存：

```text
msgId
ownerToken
leaseVersion
consumerId
workerId
maxDeadline
```

不是每个任务一个线程，也不是每个任务一个 Timer。

## 4. 续约流程

```text
Worker claim
→ register in-flight
→ wheel.schedule(msgId, renewAfter)

Wheel tick
→ 取出到期 bucket
→ 批量 SELECT/UPDATE lease
→ 成功任务重新 schedule
→ 失败任务 unregister + 告警
```

批量 SQL：

```sql
UPDATE t_consume_record
SET lease_until = ?
WHERE msg_id IN (...)
  AND status='PROCESSING'
  AND owner_token = ?
  AND lease_version = ?
```

不能：

```text
for 每条消息:
  UPDATE lease
```

## 5. 卡死处理

```text
Worker 执行超过 maxProcessing
→ wheel 取出 deadline 任务
→ 停止续约
→ in-flight 标记 LOST
→ Future.cancel(true)
→ 告警
→ lease 到期后其他 worker 接管
```

旧 worker 后来恢复：

```text
提交时 owner_token/version 已变
→ 0 行
→ 回滚
```

如果 handler 不响应中断：

```text
不能安全 kill
→ 隔离线程
→ 告警
→ 必要时重启实例
→ 旧 worker 仍无法提交
```

## 6. 外部副作用

数据库可以回滚，外部副作用不能：

```text
发短信
调第三方
写搜索
```

所以外部动作必须：

```text
带 bizKey 幂等
放到 Outbox/补偿
不要直接裸调
```

## 7. 时间轮容量

假设：

```text
10W QPS
平均处理 2s
in-flight ≈ 20W
```

时间轮只保存任务引用，不保存完整 payload：

```text
20W 个 task 对象
```

续约：

```text
每 20s 续一次
20W / 20s = 1W 次更新/s
```

必须批量：

```text
每批 500~1000
按 msg_id 分片
```

如果处理时间 5s：

```text
50W in-flight
续约 2.5W 次/s
```

需要：

```text
consumer 实例分片
t_consume_record 分片
批量 UPDATE
监控续约延迟
```

## 9. 启动顺序

```text
1. 创建 group
2. 启动 LeaseWheel
3. 启动 WorkerPool
4. 启动 AckBatcher
5. 启动 Persister
6. 最后启动 Puller
```

关闭：

```text
1. 停止 Puller
2. 排空队列
3. 停止 Persister/Worker
4. flush ACK
5. 停止时间轮
```

## 11. 验收

```text
长任务持续续约
完成前不丢 lease
卡死超过 maxProcessing 停止续约
旧 worker 提交失败
新 worker 接管
重复业务被幂等拦截
续约批量更新
时间轮不创建大量线程
```


## 12. Owner Epoch 与重领导警

lease 只能表示“现在有没有 owner”，不能表示“被换过几次 owner”。

增加字段：

```text
owner_token      本次领取的唯一 token
owner_epoch      领取代数，每次 claim +1
claim_count      被领取次数
last_claim_at    最近领取时间
```

### Claim

```sql
UPDATE t_consume_record
SET status='PROCESSING',
    owner_token=?,
    owner_epoch=owner_epoch+1,
    claim_count=claim_count+1,
    last_claim_at=NOW(),
    lease_until=?
WHERE msg_id=?
  AND status='READY'
```

每次领取：

```text
owner_epoch + 1
```

包括：

```text
另一个实例领取
本实例重启后领取
lease 过期后重新领取
```

### Commit / Fencing

```sql
UPDATE t_consume_record
SET status='CONSUMED'
WHERE msg_id=?
  AND status='PROCESSING'
  AND owner_token=?
  AND owner_epoch=?
  AND lease_until > NOW()
```

旧 owner 的 epoch 已过期：

```text
影响行数 = 0
→ 业务事务回滚
```

### 告警

```text
owner_epoch > 1
claim_count > 1
max_processing_exceeded
lease_lost
```

告警语义：

```text
不是“消息重复”本身
而是“发生了崩溃/超时后的重新领取”
需要研发确认业务幂等是否覆盖
```

### 不引入尝试表

不设计：

```text
t_consume_attempt
```

原因：

```text
每条消息每次尝试一行
10W QPS 下写入放大
历史数据膨胀
排障价值可由日志/指标补足
```

保留：

```text
t_consume_record.owner_epoch
t_consume_record.claim_count
t_consume_record.updated_at
```

错误信息：

```text
日志 / metrics / trace
不落交易表
```

排障使用：

```text
结构化日志
traceId / msgId / owner_epoch
metrics
告警
```

如果后续审计要求完整尝试轨迹：

```text
写 ClickHouse / Loki / 日志平台
不要写交易主库
```

## 13. 必须接受的语义

```text
旧 owner 宕机
→ 新 owner 重新执行
→ fencing 只能阻止旧 owner 提交
→ 不能阻止新 owner 再执行一次
```

所以：

```text
至少一次
业务幂等
重领导警
人工确认
```

不能承诺：

```text
宕机后 exactly-once
```
