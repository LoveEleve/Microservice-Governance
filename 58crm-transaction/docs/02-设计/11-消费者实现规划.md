# 消费者实现规划

> 目标：在 Redis Stream 上实现可恢复、可扩展、至少一次的消费端。  
> 本文只做规划，不写实现。

## 1. 边界

```text
一个业务线
一个 Stream
一个 consumer group
多个应用实例作为 consumer
每个实例有 Puller / 队列 / Persister / Worker / AckBatcher
```

明确不做：

```text
不保证全局顺序
不保证同一 Stream 内并发 worker 的处理顺序
不做多下游 fan-out
不做消费端跨服务 RPC
```

## 2. 运行时链路

```text
Redis Stream
  tx:stream:{bizCode}
        │
        ▼
Puller
  XREADGROUP COUNT 500 BLOCK 1000
        │
        ▼
PerStreamBuffer（有界）
        │
        ▼
Persister
  批量 INSERT t_consume_record(READY)
        │
        ▼
Business Worker Pool
  READY -> PROCESSING
  业务表 + t_consume_record(CONSUMED) + t_idempotent
  COMMIT
        │
        ▼
Ack Batcher
  XACK entryId...
```

失败：

```text
Puller 拉取后崩溃
  → PEL + XCLAIM

Persister 前崩溃
  → 内存队列丢
  → PEL 重新领取

Persister 后崩溃
  → t_consume_record READY
  → 本地恢复

Worker 崩溃
  → PROCESSING + lease 过期
  → 重新 READY

XACK 失败
  → CONSUMED + PEL 重投
  → 幂等跳过 + 补 XACK
```

## 4. 表结构

### `t_consume_record`

```sql
CREATE TABLE t_consume_record (
    msg_id VARCHAR(64) PRIMARY KEY,
    biz_id VARCHAR(64) NOT NULL,
    stream_entry_id VARCHAR(64) NOT NULL,
    consumer_id VARCHAR(64),
    status VARCHAR(16) NOT NULL,
    owner_token VARCHAR(64),
    owner_epoch BIGINT NOT NULL DEFAULT 0,
    claim_count INT NOT NULL DEFAULT 0,
    lease_until DATETIME,
    retry_count INT NOT NULL DEFAULT 0,
    next_retry_at DATETIME,
    payload MEDIUMTEXT,
    payload_ref VARCHAR(256),
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    KEY idx_status_lease (status, lease_until),
    KEY idx_status_retry (status, next_retry_at)
);
```

要求：

```text
payload 或 payload_ref 至少一个非空
msg_id 唯一
READY/PROCESSING -> lease
CONSUMED/DEAD -> 不再领取
```

### `t_idempotent`

```sql
CREATE TABLE t_idempotent (
    msg_id VARCHAR(64) PRIMARY KEY,
    biz_key VARCHAR(128) NOT NULL,
    status VARCHAR(16) NOT NULL,
    created_at DATETIME NOT NULL,
    UNIQUE KEY uk_biz_key (biz_key)
);
```

业务表、`t_consume_record(CONSUMED)`、`t_idempotent` 必须同一本地事务。

## 5. 启动顺序

```text
1. 绑定配置
   consumer.enabled
   consumer.biz-codes
   consumer.pull.count
   consumer.pull.block
   consumer.workers
   consumer.ack.batch-size

2. 校验 Registry
   bizCodes 非空
   每个 bizCode 有 group/stream

3. 连接 Redis
   StringRedisTemplate

4. 为每个 Stream 创建 group
   XGROUP CREATE ... 0 MKSTREAM
   BUSYGROUP -> 成功

5. 创建每业务线组件
   StreamQueue
   Persister
   WorkerPool
   AckBatcher

6. 启动 PendingRecovery
   XPENDING + XAUTOCLAIM

7. 启动 Persister/Worker/Ack

8. 最后启动 Puller
   避免拉进来但下游未就绪

9. 启动指标
```

关闭顺序：

```text
1. Puller 停止拉取
2. 等待队列排空
3. Persister 停止
4. Worker 停止
5. AckBatcher flush
6. 关闭 Redis
```

## 6. 性能和扩展

### Puller

```text
COUNT = 500
BLOCK = 1000ms
一个业务线一个 Puller
```

不允许一个 Puller 串行拖多个业务线。

### Buffer

```text
每个 Stream 一个有界队列
容量 5000~10000
满了 Puller 阻塞
```

### Persister

```text
批量 INSERT 500
不要逐条 commit
```

### Worker

```text
每业务线独立线程池
core/max/queue 有界
慢业务不拖其他业务线
```

### ACK

```text
按 stream 分组
每 100ms / 200 条
批量 XACK
```

### 多实例

```text
同一个 group
consumerId 唯一
共享同一个消费方 DB
```

扩展：

```text
加实例 -> 加 consumer -> group 自动分摊
不需要 rebalance
PEL 归属 consumer
```

## 7. 顺序

默认：

```text
不保证业务处理顺序
```

原因：

```text
一个 Stream 多个 worker 并发
完成顺序不可控
```

需要顺序时：

```text
单业务线单 worker
或按 bizId hash 到固定 worker
或事件带 version，下游条件更新
```

## 10. 验收标准

```text
XREADGROUP 正常拉取
业务成功 -> CONSUMED -> XACK
业务失败 -> READY/DEAD
Worker 崩溃 -> lease 过期重试
ACK 失败 -> PEL 重投 + 幂等
多实例共享 group/DB
不保证全局顺序
```

## 11. 结论

```text
Puller 只负责 Redis 拉取
Persister 负责 durable inbox
Worker 负责业务 + 幂等 + CONSUMED
AckBatcher 负责批量 XACK
Recovery 负责 PEL/lease
多实例共享 group 和消费库
```
