# 分布式事务与 TCC 面试思维导图

> 基线：分布式事务通用理论 + 58CRM 当前实现；消息服务另见 `58CRM-消息服务.md`。
> 范围：一致性模型、2PC/3PC/XA、TCC、SAGA、AT、Outbox、幂等、补偿、选型、58CRM 落地。
> 用法：标题层级即节点层级；每个节点按“核心结论、核心原理、关键机制、面试要点”展开。

## 0. 分布式事务总览

### 0.1.1 分布式事务到底在解决什么？

- 核心结论：一次业务操作跨多个库/服务时，本地事务无法同时保证所有资源一起成功或一起撤销。
- 核心原理
  - 服务 A 提交成功、服务 B 失败，A 的本地提交无法回滚。
  - 网络超时导致结果未知，不能直接当成功或失败。
- 关键机制
  - 全局协调、资源预留或补偿、状态持久化、失败重试。
- 面试要点
  - 引入 MQ 不等于分布式事务，核心是跨资源状态如何收敛。

### 0.1.2 分布式事务先分清哪三件事？

- 核心结论：原子性、一致性、隔离性不是同一个问题。
- 核心原理
  - 原子性：多个资源要么都成功、要么都撤销。
  - 一致性：业务约束最终是否成立。
  - 隔离性：中间态会不会被其他事务看到。
- 关键机制
  - Outbox 主要解决业务与消息的原子性。
  - TCC 解决资源预留/确认/取消，但隔离性弱。
  - Saga 解决长流程补偿，但不保证隔离。
- 面试要点
  - 很多方案只解决其中一个，不能笼统说“保证一致性”。

### 0.1.3 CAP 和 BASE 怎么答？

- 核心结论：分区发生时，强一致和可用性需要取舍；BASE 是基本可用、软状态、最终一致。
- 核心原理
  - CAP 不是简单的“三选二”口号。
  - 分布式系统必须容忍分区，讨论重点是一致性/可用性取舍。
- 关键机制
  - 强一致、线性一致、可串行化、最终一致是不同强度。
  - 业务上常选择最终一致 + 补偿/对账。
- 面试要点
  - 不要背 CAP 定义，要能结合业务说取舍。

### 0.1.4 分布式事务的失败模型有哪些？

- 核心结论：真正难的是超时、重复、乱序、崩溃和旧请求晚到。
- 核心原理
  - 节点宕机、网络超时/丢包/重复、时钟漂移、协调者宕机、参与者宕机。
  - 超时后结果未知，不能假设对方没执行。
- 关键机制
  - 状态持久化、幂等键、重试、fencing、对账。
- 面试要点
  - 正常流程谁都能讲，故障恢复才是分水岭。

## 1. 2PC、3PC 与 XA

### 1.1.1 2PC 的两个阶段是什么？

- 核心结论：Prepare 询问所有参与者能否提交，Commit/Rollback 执行最终决定。
- 核心原理
  - Prepare：参与者执行本地事务但不提交，锁住资源，回复 Yes/No。
  - 全部 Yes 才 Commit，任一 No 就 Rollback。
- 关键机制
  - 协调者统一决策。
  - 参与者 Prepare 后持有本地锁。
- 面试要点
  - 能画出协调者、参与者、Prepare、Commit 四要素。

### 1.1.2 2PC 有什么问题？

- 核心结论：同步阻塞、协调者单点、部分提交导致不一致、性能差。
- 核心原理
  - Prepare 后参与者锁资源等待协调者。
  - 协调者宕机，参与者可能一直阻塞。
  - Commit 消息部分到达，出现数据不一致。
- 关键机制
  - 超时/恢复/启发式决策都很复杂。
- 面试要点
  - 2PC 是强一致协议，但代价是锁和阻塞。

### 1.1.3 3PC 改进了什么？

- 核心结论：增加 CanCommit/PreCommit，减少参与者长期阻塞，但没有根治分区不一致。
- 核心原理
  - 三阶段：CanCommit、PreCommit、DoCommit。
  - PreCommit 后参与者知道大家大概率能提交。
- 关键机制
  - 网络分区下仍可能不一致。
  - 工程复杂度更高。
- 面试要点
  - 3PC 是缓解，不是银弹。

### 1.1.4 XA 是什么？

- 核心结论：XA 是数据库/资源管理器层面的两阶段提交规范。
- 核心原理
  - TM 协调多个 XA Resource。
  - Prepare/Commit/Rollback 由数据库驱动参与。
- 关键机制
  - 强一致、锁粒度大、性能差。
  - 适合短事务、低并发、强一致场景。
- 面试要点
  - XA 不是业务 TCC，它锁的是数据库资源。

### 1.1.5 2PC/XA 什么时候能用？

- 核心结论：参与者少、事务短、并发低、强一致要求高时可以考虑。
- 核心原理
  - 锁持有时间可控。
  - 协调者/参与者故障可运维。
- 关键机制
  - 长事务、高并发、跨互联网通常不优先选。
- 面试要点
  - 说边界，不要一刀切说“2PC 已死”。

## 2. TCC 模型

### 2.1.1 TCC 的三个角色是什么？

- 核心结论：TM 发起全局事务，TC 维护状态并调度，RM 执行 Try/Confirm/Cancel。
- 核心原理
  - TM 调 Try，决定 commit/rollback。
  - TC 管 global/branch、超时、重试、回调。
  - RM 管本地资源、barrier 和三个业务动作。
- 关键机制
  - TC 不执行业务。
  - RM 不决定全局状态。
- 面试要点
  - 能区分 TM、TC、RM，不把三者混成一个服务。

### 2.1.2 TCC 三个阶段分别做什么？

- 核心结论：Try 预留、Confirm 转正、Cancel 释放。
- 核心原理
  - 库存：Try 冻结，Confirm 扣减冻结，Cancel 解冻。
  - 优惠券：Try 锁定，Confirm 核销，Cancel 释放。
- 关键机制
  - Try 只预占，不写终态。
  - Confirm/Cancel 必须幂等。
- 面试要点
  - 用具体资源状态解释，不要只背三个单词。

### 2.1.3 Try 的职责边界是什么？

- 核心结论：Try 做检查 + 预留，不写最终业务结果。
- 核心原理
  - Try 成功不代表全局一定提交。
  - 后续可能因为其他分支失败而 Cancel。
- 关键机制
  - 预留状态要显式建模，如 frozen、locked、reserved。
  - Try 必须幂等、原子。
- 面试要点
  - Try 里直接扣终态是常见错误。

### 2.1.4 Confirm 的职责边界是什么？

- 核心结论：Confirm 把预留转正式，必须幂等且尽量不依赖临时判断。
- 核心原理
  - TC 可能重复回调。
  - Confirm 失败需要重试。
- 关键机制
  - 业务终态 + barrier + Outbox 同本地事务。
  - Confirm 不应再做“可能失败”的业务校验。
- 面试要点
  - Confirm 不是“再执行一次 Try”。

### 2.1.5 Cancel 的职责边界是什么？

- 核心结论：Cancel 释放 Try 预占，必须幂等且能处理空回滚。
- 核心原理
  - Try 可能没到、失败、超时。
  - Cancel 可能重复。
- 关键机制
  - 无 barrier 插 SUSPENDED，不执行业务释放。
  - 已 CANCELLED/SUSPENDED 直接成功。
- 面试要点
  - Cancel 不能假设 Try 一定成功。

### 2.1.6 TCC 和 2PC 的本质区别是什么？

- 核心结论：2PC 锁数据库资源，TCC 锁业务预留状态。
- 核心原理
  - 2PC 锁持有到二阶段结束。
  - TCC Try 后数据库锁可以释放，资源由业务状态表示。
- 关键机制
  - TCC 隔离性弱，需要业务补偿和隔离。
  - TCC 业务侵入高。
- 面试要点
  - 用“数据库锁 vs 业务预留”一句话区分。

### 2.1.7 TCC 的优点和代价是什么？

- 核心结论：不长期占数据库锁、可跨服务、可补偿；但业务侵入、隔离弱、三方法复杂。
- 核心原理
  - 资源提前预留，避免超卖。
  - Confirm/Cancel 可重试、可恢复。
- 关键机制
  - 需要 barrier、事务日志、重试、对账。
  - 业务要处理空回滚、悬挂、幂等。
- 面试要点
  - 说优点必须同时说代价。

## 3. TCC 工程化

### 3.1.1 global 状态机怎么流转？

- 核心结论：TRYING 进入，成功走 CONFIRMING/CONFIRMED，失败走 CANCELLING/CANCELLED。
- 核心原理
  - 全局状态只能向前。
  - 更新带状态条件，CAS 失败表示并发推进。
- 关键机制
  - FAILED 表示不可自动恢复，需要人工。
- 面试要点
  - 能画出 TRYING、CONFIRMING、CONFIRMED、CANCELLING、CANCELLED。

### 3.1.2 branch 状态机怎么流转？

- 核心结论：TRYING 后分 TRY_SUCCESS/TRY_FAIL，之后进入 Confirm 或 Cancel。
- 核心原理
  - TRY_SUCCESS 的分支才需要真正 Confirm。
  - 失败分支也要收敛到 CANCELLED。
- 关键机制
  - DEAD 表示重试耗尽。
- 面试要点
  - 分支状态和全局状态是两层，不要混。

### 3.1.3 TCC 事务日志要存什么？

- 核心结论：global、branch、barrier 三层状态都要持久化。
- 核心原理
  - global：xid、requestId、biz、status、timeout、owner lease。
  - branch：resourceKey、action、callback endpoint、status、retry。
  - barrier：RM 本地 xid+branchId 状态。
- 关键机制
  - 不能只放内存或 Redis。
- 面试要点
  - 事务日志是恢复、幂等、审计的依据。

### 3.1.4 分支注册应该谁做？

- 核心结论：目标设计由 RM 在 Try 入口自己注册，TM 只传 xid 和业务参数。
- 核心原理
  - actionName、resourceKey、callbackEndpoint 属于 RM。
  - TM 不应知道 RM 部署细节。
- 关键机制
  - TC 从 RM 注册的分支行读取回调地址。
  - 当前项目 TM 注册是过渡实现。
- 面试要点
  - 不要把当前实现当成标准 TCC。

### 3.1.5 TCC 的超时怎么设计？

- 核心结论：Try 超时、回调重试超时、全局超时要分开。
- 核心原理
  - Try 超时决定预留窗口。
  - Confirm/Cancel 用退避和上限。
  - gRPC deadline 只是单次网络超时。
- 关键机制
  - 超时后结果未知，不能假设未执行。
- 面试要点
  - 不要用一个超时时间覆盖所有阶段。

### 3.1.6 TCC 的重试怎么做？

- 核心结论：可重试错误退避重试，永久错误进入 DEAD/人工。
- 核心原理
  - 网络、RM 暂时不可用、RETRYABLE 可重试。
  - 参数错误、业务永久失败不可重试。
- 关键机制
  - next_retry_at + retry_count 持久化。
  - 进程重启后仍能恢复。
- 面试要点
  - 重试是状态机的一部分，不是 for 循环。

### 3.1.7 TC 怎么做到高可用？

- 核心结论：TC 无状态，状态在 MySQL，多实例通过 owner lease 竞争推进。
- 核心原理
  - owner_token + lease_until 标记当前 owner。
  - 旧 owner 的写被 fencing。
- 关键机制
  - Scheduler 抢租约、恢复、重试。
- 面试要点
  - 没有 lease，多 TC 会重复 Confirm/Cancel。

### 3.1.8 TCC 的性能成本在哪里？

- 核心结论：多一次 Try RPC，多一次 Confirm/Cancel RPC，多几张状态表。
- 核心原理
  - Try、Register、Report、Commit、Callback 都是网络/DB 操作。
  - barrier 和幂等表增加写入。
- 关键机制
  - 批量、连接池、异步回调、状态 CAS。
  - 不能为了性能跳过持久化。
- 面试要点
  - TCC 不是零成本，换来的是灵活的资源预留。

## 4. TCC 三防

### 4.1.1 空回滚是什么？

- 核心结论：Cancel 先到，Try 还没到。
- 核心原理
  - 没有 barrier 就没有资源可释放。
  - 直接执行 cancelAction 可能误释放。
- 关键机制
  - 插入 SUSPENDED，返回成功。
- 面试要点
  - 空回滚是“没有资源”，不是失败。

### 4.1.2 悬挂是什么？

- 核心结论：Cancel 已经处理完，Try 才迟到。
- 核心原理
  - 迟到 Try 不能再占资源。
- 关键机制
  - Try 看到 SUSPENDED/CANCELLED 返回 FAILURE。
- 面试要点
  - SUSPENDED 是防悬挂标记。

### 4.1.3 幂等怎么实现？

- 核心结论：重复 Try/Confirm/Cancel 按 barrier 状态直接返回。
- 核心原理
  - Try 已 TRIED/CONFIRMED -> SUCCESS。
  - Confirm 已 CONFIRMED -> SUCCESS。
  - Cancel 已 CANCELLED/SUSPENDED -> SUCCESS。
- 关键机制
  - 冲突状态报错，不反向覆盖。
- 面试要点
  - 幂等不是“再执行一次”，而是“识别已经执行过”。

## 5. TCC 隔离与并发

### 5.1.1 TCC 能保证强隔离吗？

- 核心结论：不能，TCC 是最终一致，中间态可能被读到。
- 核心原理
  - Try 后资源处于 frozen/locked 中间态。
  - 其他事务可能读到期中状态。
- 关键机制
  - 业务状态机、预留字段、只读终态、版本号。
- 面试要点
  - 说“TCC 没有脏读”是错误。

### 5.1.2 Try 怎么防止超卖？

- 核心结论：用原子条件更新，不要先 SELECT 再 UPDATE。
- 核心原理
  - `available >= n` 作为 UPDATE 条件。
  - 影响行数为 0 就失败。
- 关键机制
  - 预留和冻结在同一 SQL/事务。
- 面试要点
  - 并发安全靠数据库原子性，不靠应用判断。

### 5.1.3 Confirm 和 Cancel 并发怎么办？

- 核心结论：用 barrier 状态 CAS，只允许一个方向成功。
- 核心原理
  - Confirm 只能从 TRIED 转 CONFIRMED。
  - Cancel 只能从 TRIED 转 CANCELLED。
- 关键机制
  - 更新影响行数为 0 表示状态已变。
- 面试要点
  - 不能靠“先查再改”。

## 6. 其他分布式事务方案

### 6.1.1 SAGA 是什么？

- 核心结论：每个服务执行本地事务，失败时执行补偿。
- 核心原理
  - 向后恢复：反向补偿。
  - 向前恢复：重试直到成功。
- 关键机制
  - 适合长流程、服务自治。
  - 没有隔离性，补偿可能失败。
- 面试要点
  - SAGA 的补偿不是物理回滚。

### 6.1.2 AT 模式是什么？

- 核心结论：业务 SQL + 自动反向 SQL + 全局锁。
- 核心原理
  - 业务侵入低。
  - 依赖 SQL 解析和回滚日志。
- 关键机制
  - 复杂业务/多表更新难。
  - 全局锁有性能代价。
- 面试要点
  - AT 不是“无锁强一致”。

### 6.1.3 本地消息表/Outbox 是什么？

- 核心结论：业务表和消息表同一个本地事务，后台 relay 投递。
- 核心原理
  - 业务成功消息一定在 MySQL。
  - 发送失败可重扫。
- 关键机制
  - 消费端幂等。
  - 不解决资源预留。
- 面试要点
  - Outbox 解决可靠通知，不解决跨服务回滚。

### 6.1.4 事务消息是什么？

- 核心结论：半消息 + 本地事务 + Commit/Rollback + Broker 回查。
- 核心原理
  - 生产者本地事务和消息发送绑定。
  - Broker 回查本地事务状态。
- 关键机制
  - 依赖 MQ 能力。
  - 不解决消费者业务回滚。
- 面试要点
  - 和本地消息表目标相似，实现位置不同。

### 6.1.5 exactly-once 存在吗？

- 核心结论：端到端严格 exactly-once 很难；工程上用至少一次 + 幂等。
- 核心原理
  - 网络确认不可靠。
  - 外部副作用不可回滚。
- 关键机制
  - 幂等键 + 唯一约束 + 状态机。
- 面试要点
  - 不要轻易说“MQ 保证 exactly-once”。

## 7. 选型矩阵

### 7.1.1 按业务场景怎么选？

- 核心结论：短事务强一致看 2PC/XA；资源预留看 TCC；长流程看 SAGA；业务消息看 Outbox/事务消息。
- 核心原理
  - 先看是否需要资源预留。
  - 再看是否能接受最终一致。
- 关键机制
  - 复杂 SQL 自动回滚评估 AT。
  - 非核心通知用最大努力通知。
- 面试要点
  - 先问业务约束，再谈方案。

### 7.1.2 按代价怎么选？

- 核心结论：XA 锁重，TCC 侵入大，SAGA 补偿复杂，Outbox 最终一致。
- 核心原理
  - 一致性与性能、复杂度是取舍。
- 关键机制
  - 不要为了“先进”选最复杂方案。
- 面试要点
  - 能说出每种方案的代价。

## 8. TCC 设计检查清单

### 8.1.1 业务建模检查什么？

- 核心结论：资源是否能预留、Confirm 是否只转终态、Cancel 是否能释放。
- 核心原理
  - Try 原子扣减/锁定。
  - Confirm/Cancel 幂等。
- 关键机制
  - 业务状态机显式化。
- 面试要点
  - 建模不清，代码一定乱。

### 8.1.2 异常检查什么？

- 核心结论：空回滚、悬挂、重复、超时、TC/RM 崩溃、callback 不可达。
- 核心原理
  - 每个异常都要有状态和恢复路径。
- 关键机制
  - barrier、事务日志、Scheduler、对账。
- 面试要点
  - 不要只画成功流程。

## 9. 58CRM 项目背景

### 9.1.1 58CRM 为什么需要 TCC？

- 核心结论：线索分配同时涉及 quota 和 coupon 等多个服务，本地事务管不了跨服务资源。
- 核心原理
  - 一个 RM 成功、另一个失败，已预占资源必须撤销。
- 关键机制
  - 成功统一 Confirm，失败 Cancel 已成功分支。
- 面试要点
  - 用“A 成功、B 失败、撤销 A”讲，不要只说用了 TCC。

### 9.1.2 为什么不用普通 MQ？

- 核心结论：MQ 没有资源预留和撤销协议。
- 核心原理
  - MQ 是事后通知，不是事前占位。
  - 消费失败不能阻止超卖。
- 关键机制
  - TCC 管资源，Outbox 管通知。
- 面试要点
  - 两者是分工，不是替代。

## 10. 模块地图

### 10.1.1 TCC 模块怎么分？

- 核心结论：api、protocol、client、participant、coordinator、id、starter、examples 分层。
- 核心原理
  - api 只放业务契约和注解。
  - protocol 放 gRPC stub 和内部 DTO。
  - client/participant/coordinator 各自依赖 api/protocol。
- 关键机制
  - starter 按 client/participant 角色开关。
- 面试要点
  - 包边界是 public/protocol/internal 三层。

### 10.1.2 消息模块怎么分？

- 核心结论：outbox 生产、consumer 消费、starter 装配。
- 核心原理
  - outbox 负责业务表+消息表+relay。
  - consumer 负责 Stream/PEL/幂等。
- 关键机制
  - 一条业务线一个 Stream/消费组。
- 面试要点
  - 不要把生产端和消费端混成一个模块。

## 11. 架构设计

### 11.1.1 逻辑架构是什么？

- 核心结论：业务应用 TM、独立 Coordinator、多个 RM、MySQL 状态、Redis Stream 消息。
- 核心原理
  - TM 调 Try，TC 管状态，RM 执行三阶段。
  - MySQL 是正本，Redis 是传输。
- 关键机制
  - TC 不发现 RM，回调地址由分支元数据提供。
- 面试要点
  - 能画出 TM/TC/RM/MySQL/Redis 五块。

### 11.1.2 传输矩阵是什么？

- 核心结论：TM→TC gRPC；TM→RM Try OpenFeign；RM→TC 注册/上报 gRPC；TC→RM Confirm/Cancel gRPC。
- 核心原理
  - Try 是业务 API。
  - Confirm/Cancel 是 TCC 协议。
- 关键机制
  - 不要用 TC 发现 RM。
- 面试要点
  - 能说清每条链路的发起方。

## 12. 目标流程

### 12.1.1 成功链路怎么走？

- 核心结论：TM begin → RM Try → RM 自注册分支 → RM barrier/业务预留 → 上报成功 → TM commit → TC 回调 Confirm。
- 核心原理
  - Try 由 TM 通过业务 API 调用。
  - 分支注册由 RM 在 Try 入口完成。
- 关键机制
  - TC 从分支表读取回调地址。
- 面试要点
  - 流程必须是 RM 自注册，不是 TM 代注册。

### 12.1.2 失败链路怎么走？

- 核心结论：quota Try 成功、coupon Try 失败 → coupon 上报 TRY_FAIL → TM rollback → TC Cancel quota → coupon 空回滚 SUSPENDED。
- 核心原理
  - 已成功分支必须撤销。
  - 失败分支没有 barrier，Cancel 插 SUSPENDED。
- 关键机制
  - 最终 global CANCELLED。
- 面试要点
  - 这是 TCC 最核心的价值场景。

### 12.1.3 当前仓库和目标设计差在哪？

- 核心结论：当前 TM 的 `@TccBranch` 先注册分支；目标由 RM 自注册。
- 核心原理
  - 当前 callbackEndpoint 写在 TM，耦合部署细节。
- 关键机制
  - 这是过渡实现，不是标准 TCC。
- 面试要点
  - 能主动说出设计债。

## 13. 状态机与数据

### 13.1.1 global/branch/barrier 的关系是什么？

- 核心结论：global 管全局，branch 管 TC 侧分支，barrier 管 RM 本地幂等/防悬挂。
- 核心原理
  - global/branch 在 TC 库。
  - barrier 在 RM 业务库。
- 关键机制
  - branch 状态推进不等于 RM 业务状态。
- 面试要点
  - 三张表职责不要混。

### 13.1.2 branchId 的作用域是什么？

- 核心结论：branchId 只在 xid 内唯一，真正标识是 `(xid, branchId)`。
- 核心原理
  - `xid=1` 和 `xid=2` 都可以有 branchId=1。
- 关键机制
  - 日志必须打 `xid:branchId`。
- 面试要点
  - 不是全局 ID，不是主键冲突。

## 14. Barrier 三防

### 14.1.1 58CRM 怎么处理空回滚？

- 核心结论：Cancel 无 barrier 时插 SUSPENDED，返回成功。
- 核心原理
  - 没有 Try 就没有资源。
  - 不执行 cancelAction。
- 关键机制
  - coupon Try 失败回滚 barrier，Cancel 空回滚。
- 面试要点
  - SUSPENDED 是防悬挂标记。

### 14.1.2 58CRM 怎么处理悬挂？

- 核心结论：迟到 Try 看到 SUSPENDED/CANCELLED 直接 FAILURE。
- 核心原理
  - Cancel 已处理过，不能再占资源。
- 关键机制
  - barrier 状态检查先于业务 Try。
- 面试要点
  - 没有它，资源会在事务结束后被重新占用。

## 15. 消息边界

### 15.1.1 TCC 和 Outbox 怎么配合？

- 核心结论：Confirm 的本地事务里写业务终态 + barrier + Outbox。
- 核心原理
  - TCC 管资源状态。
  - Outbox 管终态通知。
- 关键机制
  - 消息由 MySQL relay 到 Redis Stream。
- 面试要点
  - 框架不自动生成业务事件。

## 16. 注解 API 与 AOP

### 16.1.1 `@TccTransactional` 做什么？

- 核心结论：标记 TM 全局事务入口，切面负责 begin/commit/rollback。
- 核心原理
  - requestId 是幂等键。
  - bizCode/bizId 用于业务定位。
- 关键机制
  - 进入方法体前已经 begin 并绑定 xid。
- 面试要点
  - 它不等于本地 `@Transactional`。

### 16.1.2 为什么注解类都是代理对象？

- 核心结论：`LeadAssignService` 被 `@TccTransactional` 代理，两个 Gateway 被 `@TccBranch` 代理。
- 核心原理
  - Spring AOP 靠代理拦截。
  - 同类自调用绕过代理。
- 关键机制
  - Starter 里 `@EnableAspectJAutoProxy` 强制 CGLIB。
- 面试要点
  - 业务代码看不到 `@Enable`，但代理确实存在。

## 17. 设计债

### 17.1.1 当前最大的设计债是什么？

- 核心结论：TM 代 RM 注册分支、TM 配置 callbackEndpoint。
- 核心原理
  - actionName/resourceKey/地址属于 RM。
- 关键机制
  - 目标改为 RM 自注册，TM 只传 xid + payload。
- 面试要点
  - 能说出为什么这是债，而不是照着背。

### 17.1.2 还有哪些边界？

- 核心结论：嵌套 TCC 不支持、begin 不自动重试、TccContext 只表示当前分支。
- 核心原理
  - 同线程不能再开全局事务。
  - branchId 会被后续分支覆盖。
- 关键机制
  - begin 靠 requestId 幂等，但当前没重试。
- 面试要点
  - 这些是当前边界，不是“完美实现”。

## 22. 正确设计总则

### 22.1.1 什么才是正确的 TCC 分工？

- 核心结论：TM 发起并调用 Try，RM 自己注册分支并执行三阶段，TC 只维护状态和回调。
- 核心原理
  - TM 不该知道 RM 的 actionName、resourceKey、callbackEndpoint。
  - RM 最清楚自己的资源和回调地址。
  - TC 不执行业务，也不主动发现 RM。
- 关键机制
  - Try 是业务 API。
  - register/report 是 RM 到 TC 的协议。
  - Confirm/Cancel 是 TC 到 RM 的回调。
- 面试要点
  - 能画出“TM → RM Try → RM → TC 注册 → TM commit → TC 回调”的链路。

### 22.1.2 哪些东西必须持久化？

- 核心结论：global、branch、barrier、outbox 都必须在 MySQL，不能只放内存或 Redis。
- 核心原理
  - 事务状态要能崩溃恢复。
  - 幂等/防悬挂要能重查。
  - 消息正本要能重放。
- 关键机制
  - TC 库：global/branch。
  - RM 库：barrier + 业务表 + outbox。
- 面试要点
  - Redis 是传输，不是事实源。

### 22.1.3 哪些边界必须明确拒绝？

- 核心结论：TM 配置 RM 地址、TC 发现 RM、TM 代 RM 注册，都是错误方向。
- 核心原理
  - 这些做法把 RM 的部署细节泄漏给 TM/TC。
  - 扩展新 RM 要改上游，不可维护。
- 关键机制
  - 目标由 RM 注册 endpoint。
  - 当前项目 TM 注册是过渡实现。
- 面试要点
  - 主动指出这是设计债，不要把它讲成标准。

## 23. RM 自注册设计

### 23.1.1 RM 在 Try 入口应该做什么？

- 核心结论：RM 接收 Try 后先注册分支，再写 barrier、执行业务 Try、上报结果。
- 核心原理
  - 分支元数据由 RM 本地决定。
  - branchId 由 TC 分配，RM 写入 barrier。
- 关键机制
  - 注册成功后绑定 `(xid, branchId)`。
  - 失败时返回明确结果给 TM。
- 面试要点
  - 顺序不能反：先注册，再写 barrier/业务。

```text
TM                 RM                         TC
 |-- Try(xid,payload) ->|                      |
 |                     |-- registerBranch ---->|
 |                     |<-- branchId ----------|
 |                     |-- barrier TRIED        |
 |                     |-- tryAction            |
 |                     |-- report TRY_* ------->|
 |<-- TryResult --------|                      |
```

### 23.1.2 RM 怎么知道自己的元数据？

- 核心结论：actionName、resourceKey、callbackEndpoint 都由 RM 自己配置/推导。
- 核心原理
  - actionName 来自 `@TccActionHandler` 或显式注册。
  - resourceKey 来自业务 payload（如 `quota:userId`）。
  - callbackEndpoint 来自 RM 的 gRPC 服务配置/注册中心。
- 关键机制
  - TM 只传 xid 和业务 payload。
- 面试要点
  - 这样新增 RM 不需要改 TM。

### 23.1.3 分支注册失败怎么办？

- 核心结论：注册失败就不执行 Try，TM 直接失败/回滚。
- 核心原理
  - TC 没有分支，后续没有回调对象。
  - 本地 barrier 不能先写。
- 关键机制
  - 注册是 Try 的前置条件。
  - 网络失败可重试，靠 `(xid,resourceKey)` 幂等。
- 面试要点
  - 注册幂等键是 xid + resourceKey。

### 23.1.4 注册成功但 Try 失败怎么办？

- 核心结论：上报 TRY_FAIL，外层回滚；分支进入 CANCELLED/SUSPENDED 收敛。
- 核心原理
  - barrier 事务回滚，可能没有 barrier。
  - TC Cancel 空回滚。
- 关键机制
  - 失败也要让全局状态收敛。
- 面试要点
  - 不能把“本地失败”当作“全局已结束”。

## 24. TC 回调设计

### 24.1.1 TC 回调的完整链路是什么？

- 核心结论：TC 先推进 branch 状态，再在 DB 事务外调 RM，最后按结果推进 global。
- 核心原理
  - 先落状态，防止 TC 崩溃后不知道要回调。
  - 远程调用不能占数据库事务。
- 关键机制
  - 回调带 xid、branchId、actionName、applicationData。
  - RM 按 actionName 找 TccAction。
- 面试要点
  - 能说清“DB 事务内推进状态，DB 事务外回调”。

```text
TC                                    RM
 |-- 抢 owner lease                     |
 |-- branch: TRIED -> CONFIRMING        |
 |-- commit DB tx                       |
 |-- gRPC Confirm(xid,branchId,action) ->|
 |                                      |-- barrier 行锁
 |                                      |-- confirmAction
 |                                      |-- barrier CONFIRMED
 |<-- SUCCESS/RETRYABLE/PERMANENT ------|
 |-- branch CAS -> CONFIRMED/DEAD       |
 |-- global -> CONFIRMED/FAILED         |
```

### 24.1.2 TC 怎么找到 RM 的地址？

- 核心结论：从 RM 注册的 branch 行读取 callbackEndpoint，不查 Nacos 发现 RM。
- 核心原理
  - RM 注册时带上 endpoint。
  - TC 任意实例都能从 DB 拿到。
- 关键机制
  - endpoint 要经过校验，不能任意 URL（防 SSRF）。
- 面试要点
  - TC 不依赖客户端服务发现。

### 24.1.3 TC 回调失败怎么分类？

- 核心结论：网络/超时/5xx 归 RETRYABLE；参数/状态/永久业务失败归 PERMANENT。
- 核心原理
  - 超时结果未知，不能当成功。
  - 永久失败重试无意义。
- 关键机制
  - RM 返回明确的 phase result。
  - TC 统一映射重试策略。
- 面试要点
  - 不能把所有失败都无限重试。

### 24.1.4 TC 回调超时怎么办？

- 核心结论：超时按 RETRYABLE 处理，依赖 RM 幂等，不能直接判定成功/失败。
- 核心原理
  - RM 可能已经执行成功，只是响应丢了。
- 关键机制
  - 重试 Confirm/Cancel；barrier 状态判断。
- 面试要点
  - 超时是“结果未知”，不是“失败”。

### 24.1.5 重复回调怎么保证幂等？

- 核心结论：RM 用 barrier `(xid,branchId)` 状态做幂等。
- 核心原理
  - Confirm 已 CONFIRMED -> 直接 SUCCESS。
  - Cancel 已 CANCELLED/SUSPENDED -> 直接 SUCCESS。
- 关键机制
  - 业务动作 + barrier 同本地事务。
- 面试要点
  - TC 重试是常态，不幂等一定出事故。

### 24.1.6 Confirm 和 Cancel 并发怎么办？

- 核心结论：barrier 行锁 + 状态 CAS，只允许一个方向成功。
- 核心原理
  - 不可能既 CONFIRMED 又 CANCELLED。
  - 冲突状态返回明确错误。
- 关键机制
  - `SELECT ... FOR UPDATE` 或条件 UPDATE。
- 面试要点
  - 不能“先查状态再更新”两步走。

### 24.1.7 旧 TC 的迟到回调怎么办？

- 核心结论：branch 状态已终态时直接幂等返回；旧 owner 的推进被 fencing。
- 核心原理
  - 新 owner 可能已经处理过。
  - 旧回调不能覆盖终态。
- 关键机制
  - owner_token/lease + branch CAS。
- 面试要点
  - 多 TC 场景必须考虑迟到请求。

### 24.1.8 回调怎么鉴权？

- 核心结论：目标设计需要 token/mTLS/allowlist/重放防护，当前项目未实现。
- 核心原理
  - 内网也可能被 SSRF/伪造请求攻击。
  - callback 地址不能任意。
- 关键机制
  - 短期 token 绑定 xid/branchId。
  - mTLS 或签名 + nonce。
- 面试要点
  - 能主动说“当前是内网可信假设，不是生产安全方案”。

### 24.1.9 回调要不要重试队列/线程池？

- 核心结论：要，回调是远程 IO，必须限流、隔离、超时，不能占满主线程。
- 核心原理
  - 慢 RM 会拖垮 TC。
  - 大量回调需要背压。
- 关键机制
  - 独立线程池/信号量。
  - 每 RM/每 endpoint 限流。
- 面试要点
  - TC 也要防雪崩。

### 24.1.10 回调结果怎么落库？

- 核心结论：只按 CAS 更新 branch/global，不覆盖终态。
- 核心原理
  - 并发/旧回调可能重复。
  - 条件更新判断影响行数。
- 关键机制
  - `WHERE status=? AND owner_token=?`。
- 面试要点
  - 状态机更新必须带前置状态。

## 25. AOP 与核心代码形态

### 25.1.1 `@TccTransactional` 切面的正确顺序是什么？

- 核心结论：解析参数 → begin → 绑定 xid → 执行业务 → commit/rollback → 清理上下文。
- 核心原理
  - begin 在业务方法之前。
  - commit 在业务方法之后。
  - 异常必须 rollback。
- 关键机制
  - finally 清理 ThreadLocal。
  - 嵌套事务要明确拒绝或挂起。
- 面试要点
  - 顺序错一个，状态就不一致。

### 25.1.2 切面应该处理哪些异常？

- 核心结论：业务异常 rollback；分支失败转 CANCELLED；系统异常保留原始异常。
- 核心原理
  - 不同异常对应不同语义。
  - 不能把所有异常都吞掉。
- 关键机制
  - 分支失败返回业务结果。
  - 系统异常让上层感知。
- 面试要点
  - 异常分类比 try-catch 本身重要。

### 25.1.3 分支 AOP 应该放在哪一侧？

- 核心结论：目标设计放在 RM 的 Try 入口，不放在 TM 的分支网关。
- 核心原理
  - RM 才知道自己的 actionName/resourceKey/endpoint。
  - 放在 TM 会把元数据泄漏给业务方。
- 关键机制
  - RM 拦截 Try：注册分支、写 barrier、执行、上报。
- 面试要点
  - 当前项目 TM 侧是过渡，不要讲成标准。

### 25.1.4 代理失效的常见场景？

- 核心结论：同类自调用、异步线程、非 Spring Bean 都会绕过 AOP。
- 核心原理
  - Spring AOP 靠代理。
  - ThreadLocal 不会自动传播到异步线程。
- 关键机制
  - 分支方法必须独立 Bean。
  - 异步要显式传 xid/branchId。
- 面试要点
  - 能解释“为什么注解没生效”。

### 25.1.5 事务边界应该怎么放？

- 核心结论：DB 事务只包本地动作，远程调用放事务外。
- 核心原理
  - 远程调用不可控，不能长时间持有数据库连接/锁。
- 关键机制
  - 分支注册远程调用在本地事务前。
  - barrier + 业务 + outbox 在本地事务内。
  - report/confirm 在事务提交后。
- 面试要点
  - 事务里做 RPC 是常见事故源。

## 26. 各种异常场景

### 26.1.1 Try 超时/结果未知怎么处理？

- 核心结论：按失败或超时收敛，不能假设没执行。
- 核心原理
  - RM 可能已预占，只是响应丢。
- 关键机制
  - TM rollback；TC Cancel；barrier 判断。
- 面试要点
  - 超时是未知，不是失败。

### 26.1.2 Try 成功但 report 丢失怎么办？

- 核心结论：branch 仍是 TRYING，全局只能超时 Cancel。
- 核心原理
  - TC 没收到成功上报。
  - RM 实际已有 barrier。
- 关键机制
  - Cancel 时 barrier TRIED -> CANCELLED。
- 面试要点
  - 状态以 TC 日志为准，但资源以 RM 为准。

### 26.1.3 begin 响应丢失怎么办？

- 核心结论：TC 可能已建 global，TM 认为失败；靠 timeout 收敛。
- 核心原理
  - requestId 幂等，重试可拿回同一 xid。
- 关键机制
  - 当前 begin 没自动重试，是缺口。
- 面试要点
  - 重试前先确认 global 状态。

### 26.1.4 TM 崩溃在部分 Try 后怎么办？

- 核心结论：TC 超时后 Cancel 已成功分支。
- 核心原理
  - TM 不再 commit/rollback。
- 关键机制
  - 全局 timeout + Scheduler。
- 面试要点
  - TCC 不能假设 TM 一定活着。

### 26.1.5 TC 崩溃在 CONFIRMING/CANCELLING 怎么办？

- 核心结论：其他 TC 抢 owner lease，从 branch 状态继续回调。
- 核心原理
  - 状态已持久化。
  - owner fencing 防旧 TC。
- 关键机制
  - Scheduler 扫 next_retry_at。
- 面试要点
  - 无状态 TC + 有状态 DB。

### 26.1.6 RM 崩溃在 Try 前/后怎么办？

- 核心结论：Try 前没资源；Try 后 barrier 可能 TRIED，Cancel 释放。
- 核心原理
  - 以 barrier 和业务表为准。
- 关键机制
  - Cancel 幂等。
- 面试要点
  - RM 崩溃窗口决定资源状态。

### 26.1.7 Confirm 永久失败怎么办？

- 核心结论：标记 DEAD/FAILED，ERROR 日志，人工介入。
- 核心原理
  - 重试不能解决业务永久错误。
- 关键机制
  - 不无限重试。
- 面试要点
  - 要有死信/人工兜底。

### 26.1.8 Cancel 空回滚/悬挂怎么处理？

- 核心结论：空回滚插 SUSPENDED；迟到 Try 看到 SUSPENDED 拒绝。
- 核心原理
  - 没有 Try 就没有资源。
  - Cancel 后不能再占资源。
- 关键机制
  - barrier 状态机。
- 面试要点
  - 这是 TCC 三防的核心。

### 26.1.9 分支重复 resourceKey 怎么办？

- 核心结论：同一 xid 内直接失败，不能静默复用。
- 核心原理
  - `(xid, resourceKey)` 唯一。
  - 复用会导致幂等语义混乱。
- 关键机制
  - 注册前本地检查 + DB 唯一键。
- 面试要点
  - 循环分支必须保证 key 唯一。

### 26.1.10 回调 endpoint 不可达怎么办？

- 核心结论：按 RETRYABLE 退避重试，超过上限进 DEAD。
- 核心原理
  - 网络/RM 重启是暂时故障。
- 关键机制
  - 重试 + 告警 + 人工。
- 面试要点
  - 不能让全局永远卡在 CONFIRMING。

## 27. 面试官追问

### 27.1.1 为什么 Try 不由 TC 发起？

- 核心结论：Try 是业务 API，需要业务参数和业务语义；TC 只认 xid/branch/action。
- 核心原理
  - TC 不该依赖业务接口。
  - TM 最接近业务参数。
- 关键机制
  - TC 只在二阶段回调。
- 面试要点
  - 一句话：TC 管状态，不管业务。

### 27.1.2 为什么分支注册不放 TM？

- 核心结论：actionName/resourceKey/callbackEndpoint 属于 RM。
- 核心原理
  - TM 代注册会泄漏 RM 部署细节。
  - 新增 RM 要改 TM。
- 关键机制
  - RM 在 Try 入口自注册。
- 面试要点
  - 这是当前项目要改的设计债。

### 27.1.3 为什么 TC 不查 Nacos 找 RM？

- 核心结论：TC 不依赖 RM 的注册中心，回调地址由分支元数据提供。
- 核心原理
  - 服务端不应该反向发现客户端。
  - endpoint 变化由 RM 注册时更新。
- 关键机制
  - branch 行存 callbackEndpoint。
- 面试要点
  - 能说清“控制面/数据面”边界。

### 27.1.4 TC 怎么保证回调不丢？

- 核心结论：先持久化 branch 状态，再回调；失败可重扫。
- 核心原理
  - 状态在 DB，不在内存。
  - Scheduler 按 next_retry_at 恢复。
- 关键机制
  - 回调幂等 + 重试 + DEAD。
- 面试要点
  - 不是“保证一次”，是“保证最终收敛”。

### 27.1.5 回调超时怎么判？

- 核心结论：超时按 RETRYABLE，结果未知。
- 核心原理
  - RM 可能已成功。
  - 重试靠 barrier 幂等。
- 关键机制
  - 不能把超时当永久失败。
- 面试要点
  - 能区分网络错误/业务失败。

### 27.1.6 怎么防止回调被伪造？

- 核心结论：mTLS/token/allowlist/重放防护，当前未实现。
- 核心原理
  - callback endpoint 是攻击面。
- 关键机制
  - 短期 token 绑定 xid/branchId。
  - 只允许注册过的 endpoint。
- 面试要点
  - 主动承认当前安全边界。

### 27.1.7 怎么证明 TCC 设计正确？

- 核心结论：用故障注入证明“资源最终与全局状态收敛”。
- 核心原理
  - Try 失败、report 丢、TC 崩、RM 崩、重复回调都要测。
- 关键机制
  - 断言：无孤儿预占、无重复扣减、无悬挂。
- 面试要点
  - 不要只测成功链路。

## 28. 正确设计检查清单

### 28.1.1 画图时先检查什么？

- 核心结论：角色、状态、资源、回调、异常五件事。
- 核心原理
  - 任何一项缺失，面试都会被追问。
- 关键机制
  - 先画成功，再画失败，再画崩溃。
- 面试要点
  - 能白板讲 10 分钟不卡壳。

### 28.1.2 设计评审必问什么？

- 核心结论：谁注册、谁回调、怎么幂等、怎么恢复、怎么鉴权。
- 核心原理
  - 这五个问题覆盖 TCC 主要风险。
- 关键机制
  - 每个问题都有状态/代码落点。
- 面试要点
  - 不要只讲框架名词。

## 29. TCC 协议细节

### 29.1.1 Begin 的语义是什么？

- 核心结论：Begin 创建一个全局事务，requestId 是幂等键。
- 核心原理
  - 同一个 requestId 重试返回同一个 xid。
  - 同一个 requestId 但 bizCode/bizId 不同，应拒绝。
- 关键机制
  - global 表 request_id 唯一。
  - timeout 在 Begin 时确定。
- 面试要点
  - Begin 失败/响应丢失要能安全重试。

### 29.1.2 RegisterBranch 的语义是什么？

- 核心结论：注册分支元数据，返回 branchId，不执行 Try。
- 核心原理
  - `(xid, resourceKey)` 唯一。
  - 重复注册返回已有分支或拒绝冲突。
- 关键机制
  - branch_seq 在 global 行锁内分配。
  - branchId 只在 xid 内唯一。
- 面试要点
  - 注册幂等不是“再插一条”。

### 29.1.3 Report 的语义是什么？

- 核心结论：TM/RM 上报 Try 结果，驱动 branch 从 TRYING 进入 TRY_SUCCESS/TRY_FAIL。
- 核心原理
  - 只允许成功/失败两种结果。
  - 重复上报同状态幂等。
- 关键机制
  - global 必须还在 TRYING。
  - report 丢失时靠全局超时收敛。
- 面试要点
  - report 不是 commit。

### 29.1.4 Commit 的语义是什么？

- 核心结论：TM 告诉 TC“所有 Try 已成功，请推进 Confirm”。
- 核心原理
  - TC 检查 global 是否满足提交条件。
  - 不满足则拒绝或转回滚。
- 关键机制
  - branch 状态推进和 RM 回调分开。
  - Commit 本身要幂等。
- 面试要点
  - Commit 不是“所有分支已经 Confirm”。

### 29.1.5 Rollback 的语义是什么？

- 核心结论：TM 告诉 TC“放弃全局事务，Cancel 已成功分支”。
- 核心原理
  - 只 Cancel Try 成功的分支。
  - Try 失败分支也要收敛状态。
- 关键机制
  - Cancel 空回滚/悬挂处理。
- 面试要点
  - Rollback 不是“删除事务日志”。

### 29.1.6 Query 的语义是什么？

- 核心结论：查询 global/branch 状态，用于排障、补偿、对账。
- 核心原理
  - 不修改状态。
  - 返回分支列表和重试信息。
- 关键机制
  - 管理台/人工操作依赖 Query。
- 面试要点
  - 没有 Query，线上问题只能靠猜。

### 29.1.7 Branch 注册响应丢失怎么办？

- 核心结论：重试注册，`(xid,resourceKey)` 幂等返回同一个 branchId。
- 核心原理
  - DB 唯一键防重复。
  - 重试不能创建第二个分支。
- 关键机制
  - 注册前不能先写 barrier。
- 面试要点
  - 注册幂等是 RM 自注册的前提。

## 30. 幂等键与业务键设计

### 30.1.1 requestId、bizId、resourceKey 分别是什么？

- 核心结论：requestId 是全局事务幂等键；bizId 是业务对象；resourceKey 是分支资源键。
- 核心原理
  - requestId 防重复 Begin。
  - bizId 用于定位/查询。
  - resourceKey 防同一事务重复分支。
- 关键机制
  - 三者作用域不同，不能互相替代。
- 面试要点
  - 用错一个，幂等就会失效。

### 30.1.2 重试时 requestId 变了会怎样？

- 核心结论：TC 认为是两笔事务，可能重复执行业务。
- 核心原理
  - 唯一键只对相同 requestId 生效。
- 关键机制
  - requestId 由业务命令生成一次，重试复用。
- 面试要点
  - UUID 每次生成是常见事故。

### 30.1.3 同一个 requestId 但参数不同怎么办？

- 核心结论：应拒绝，不能返回旧事务继续执行。
- 核心原理
  - 幂等键对应同一业务请求。
  - 参数变化说明调用方复用了键。
- 关键机制
  - 比较 bizCode/bizId/关键参数哈希。
- 面试要点
  - 幂等不是“忽略参数”。

### 30.1.4 resourceKey 怎么设计？

- 核心结论：稳定、可预测、能唯一定位资源。
- 核心原理
  - `quota:userId`、`coupon:couponId`。
  - 不能包含随机数/时间戳。
- 关键机制
  - 同一 xid 内唯一。
  - 循环分支必须带业务 ID。
- 面试要点
  - resourceKey 不稳定，分支幂等就废了。

### 30.1.5 消费幂等键和 TCC 幂等键是一回事吗？

- 核心结论：不是。TCC 用 requestId/resourceKey，消息消费用 eventKey/msgId。
- 核心原理
  - 一个防全局事务重复。
  - 一个防消息重复消费。
- 关键机制
  - 两者都靠唯一约束/状态机。
- 面试要点
  - 不要用一个键覆盖所有层。

## 31. 隔离性设计

### 31.1.1 TCC 的中间态怎么对外隔离？

- 核心结论：预留状态单独建模，读接口只读终态，必要时加读栅栏。
- 核心原理
  - Try 后资源是 frozen/locked，不是最终可用。
  - 其他事务可能读到中间态。
- 关键机制
  - 状态机 + 查询过滤 + 版本号。
- 面试要点
  - TCC 不自动提供可串行化。

### 31.1.2 读请求读到 frozen 资源怎么办？

- 核心结论：业务查询只暴露可用/终态，不把 frozen 当可用。
- 核心原理
  - 中间态是内部状态。
- 关键机制
  - 接口层过滤 + 视图/字段设计。
- 面试要点
  - 不要让用户看到“半成功”。

### 31.1.3 关键资源要不要加锁？

- 核心结论：Try 用原子条件更新，必要时加行锁；不要依赖应用层先查后改。
- 核心原理
  - 数据库原子性保证不超卖。
- 关键机制
  - `available >= n` 条件更新。
- 面试要点
  - 锁粒度越小越好。

### 31.1.4 TCC 和分布式锁是什么关系？

- 核心结论：TCC 不是分布式锁；锁是局部并发控制，TCC 是跨服务事务协议。
- 核心原理
  - 锁解决互斥，TCC 解决资源预留/确认/取消。
- 关键机制
  - 可以配合使用，但不能互相替代。
- 面试要点
  - 不要把 Redis 锁说成 TCC。

## 32. 补偿、对账与人工

### 32.1.1 TCC 的补偿和数据库回滚有什么区别？

- 核心结论：Cancel 是业务补偿，不是物理回滚。
- 核心原理
  - 补偿要满足业务不变量。
  - 补偿可能失败、可能部分成功。
- 关键机制
  - 幂等、重试、对账。
- 面试要点
  - 补偿不是“删数据”。

### 32.1.2 为什么需要最终一致性对账？

- 核心结论：框架只能保证状态收敛，业务事实仍可能有差异。
- 核心原理
  - 回调永久失败、人工误操作、外部副作用失败。
- 关键机制
  - 差异表、定时扫描、人工处理。
- 面试要点
  - 没有对账，最终一致只是口号。

### 32.1.3 对账对什么？

- 核心结论：TCC 日志 vs 业务表、消息正本 vs 消费记录、预占 vs 终态。
- 核心原理
  - 找“状态不一致”和“资源孤儿”。
- 关键机制
  - 差异表 + 修复任务 + 告警。
- 面试要点
  - 对账不是重复执行业务。

### 32.1.4 永久失败怎么处理？

- 核心结论：DEAD/FAILED + 告警 + 人工，不能无限重试。
- 核心原理
  - 业务错误重试不会变成功。
- 关键机制
  - 人工重放/补偿/冲正。
- 面试要点
  - 要有操作审计。

## 33. 运维与可观测性

### 33.1.1 TCC 要看哪些指标？

- 核心结论：Begin/Register/Report/Commit 成功率、Confirm/Cancel 重试、DEAD、延迟、积压。
- 核心原理
  - 状态机每个阶段都可能卡住。
- 关键机制
  - 按 xid/branchId 打日志和 trace。
- 面试要点
  - 没有指标就无法发现“卡在 CONFIRMING”。

### 33.1.2 日志怎么打？

- 核心结论：必须带 xid、branchId、actionName、phase、outcome。
- 核心原理
  - 单看 branchId 会歧义。
- 关键机制
  - 结构化日志 + traceId。
- 面试要点
  - 日志是排障入口。

### 33.1.3 告警怎么设？

- 核心结论：DEAD/FAILED、回调重试超限、长期 TRYING/CONFIRMING、callback 不可达。
- 核心原理
  - 这些表示事务无法自动收敛。
- 关键机制
  - 阈值 + 持续时长 + 分级。
- 面试要点
  - 不要只监控 CPU。

### 33.1.4 事务日志怎么清理？

- 核心结论：终态保留审计窗口，超期归档/清理；不能删活跃事务。
- 核心原理
  - 日志是恢复/审计依据。
- 关键机制
  - 按状态+时间清理。
- 面试要点
  - 清理策略要考虑合规。

### 33.1.5 安全边界有哪些？

- 核心结论：callback 鉴权、endpoint 校验、payload 校验、重放防护、权限隔离。
- 核心原理
  - callback 是外部输入。
- 关键机制
  - mTLS/token/allowlist/nonce。
- 面试要点
  - 当前内网可信不是生产方案。

## 34. 测试与故障注入矩阵

### 34.1.1 TCC 最小测试矩阵是什么？

- 核心结论：成功、Try 失败、report 丢、begin 丢、TC 崩、RM 崩、重复回调、Cancel 先到、并发 Confirm/Cancel。
- 核心原理
  - 每个状态转移都要有测试。
- 关键机制
  - 故障注入 + 状态断言。
- 面试要点
  - 不要只测 happy path。

### 34.1.2 故障注入断言什么？

- 核心结论：无孤儿预占、无重复扣减、无悬挂、最终状态收敛。
- 核心原理
  - 以业务不变量为断言，不以日志为断言。
- 关键机制
  - 检查业务表 + barrier + global。
- 面试要点
  - 断言要能发现真实数据问题。

### 34.1.3 怎么测空回滚和悬挂？

- 核心结论：先 Cancel 后 Try；先 Try 成功后延迟 Cancel；重复 Try。
- 核心原理
  - 直接构造状态，不依赖网络偶发。
- 关键机制
  - barrier 状态断言。
- 面试要点
  - 三防必须单独测。

## 35. 面试陷阱清单

### 35.1.1 哪些说法会被面试官追着打？

- 核心结论：TCC 强一致、TC 调 Try、MQ exactly-once、TCC 不需要幂等、Cancel 就是删除。
- 核心原理
  - 这些说法混淆了协议边界。
- 关键机制
  - 用状态机、失败场景、代价解释。
- 面试要点
  - 主动说边界，比硬撑更加分。

### 35.1.2 怎么回答“TCC 和 2PC 哪个好”？

- 核心结论：没有绝对好坏，看资源锁、业务侵入、隔离性、性能。
- 核心原理
  - 2PC 强一致但阻塞；TCC 灵活但复杂。
- 关键机制
  - 按业务场景选。
- 面试要点
  - 不要站队，要讲取舍。

### 35.1.3 怎么回答“TCC 能不能保证不超卖”？

- 核心结论：能防超卖，但靠 Try 的原子条件更新，不是靠 TCC 三个字。
- 核心原理
  - 预留必须原子。
- 关键机制
  - `available >= n` 条件更新。
- 面试要点
  - 业务实现不对，TCC 也救不了。

### 35.1.4 怎么回答“消息会不会丢”？

- 核心结论：正本在 MySQL 就不会丢，Redis 丢了可重放。
- 核心原理
  - 先写正本，再异步投递。
- 关键机制
  - Outbox relay + 消费幂等。
- 面试要点
  - 不要承诺绝对不丢，讲恢复路径。

## 36. 独立审计：还没被讲透的风险

### 36.1.1 分支注册和 Try 之间有哪些崩溃窗口？

- 核心结论：RM 自注册解决了职责归属，但没有消除“注册成功、Try 未完成”的中间窗口。
- 核心原理
  - RM 先注册分支，再写 barrier、执行业务 Try、上报结果。
  - 注册是远程调用，和本地事务不可能原子。
- 关键机制
  - 注册成功、本地事务前崩溃：TC 有 branch，RM 无 barrier；Cancel 空回滚 SUSPENDED。
  - 本地事务提交、上报前崩溃：TC branch 仍 TRYING；超时 Cancel 时 barrier TRIED，释放资源。
  - 上报成功、TC 推进前崩溃：TC 从持久化状态恢复，不依赖 TM 内存。
- 面试要点
  - 不要把“谁注册”当成全部答案，要能逐个窗口说恢复。

### 36.1.2 callbackEndpoint 用 Pod IP 会怎样？

- 核心结论：即使 RM 自注册，注册 Pod IP:port 也不是稳定地址。
- 核心原理
  - K8s 重建、扩缩容、滚动发布都会换 IP。
  - branch 行里的 endpoint 变成过期地址，TC 回调一直失败。
- 关键机制
  - 方案 A：注册逻辑服务名，由回调网关/服务发现解析。
  - 方案 B：RM 与 TC 建反向长连接，TC 通过连接回调。
  - 方案 C：TC 发回调事件到 MQ，RM 消费；延迟更高。
- 面试要点
  - 能说出“地址稳定性”比“谁配置”更深一层。

### 36.1.3 TCC 的读隔离到底怎么落地？

- 核心结论：只说“TCC 隔离性弱”不够，必须定义读模型。
- 核心原理
  - Try 后资源是 frozen/locked，读接口若把它当可用，就会超卖。
  - Confirm/Cancel 又会改变可见状态。
- 关键机制
  - 预留字段和可用量分开。
  - 查询只读终态或显式过滤中间态。
  - 关键资源用版本号/条件更新。
- 面试要点
  - 能举一个“用户看到半成功”的具体反例。

### 36.1.4 没有对账，凭什么说最终一致？

- 核心结论：框架只能保证状态机收敛，不能证明业务事实一定正确。
- 核心原理
  - 永久失败、人工误操作、外部副作用失败都可能留下差异。
  - 只靠重试，无法发现“两边都成功但金额不对”。
- 关键机制
  - 差异表：TCC 日志 vs 业务表、预占 vs 终态、消息正本 vs 消费记录。
  - 修复任务 + 人工复核 + 审计。
- 面试要点
  - 主动说“最终一致需要兜底”，比硬说零丢失可信。

### 36.1.5 多 TC 和网络分区真的验证过吗？

- 核心结论：owner lease 设计正确，不等于多 TC 场景已经被证明。
- 核心原理
  - 旧 owner 可能迟到写，回调也可能重复。
  - 网络分区下，租约和时钟都可能误判。
- 关键机制
  - 故障注入：kill owner、延迟网络、重复回调、分区恢复。
  - 断言：不重复扣减、不覆盖终态、不产生孤儿预占。
- 面试要点
  - 没做过就说没做过，不要编造多 TC 压测。

### 36.1.6 回调协议怎么演进？

- 核心结论：actionName 和 callback 协议会变化，必须考虑版本兼容。
- 核心原理
  - 旧 branch 可能在新 RM 版本上回调。
  - 字段增删/语义变化会导致 Confirm/Cancel 失败。
- 关键机制
  - proto 向后兼容。
  - actionName 版本化或能力协商。
  - 旧分支保留兼容处理。
- 面试要点
  - 能说出“回调不是一次性接口”。

## 37. 独立审计后的设计结论

### 37.1.1 哪些设计必须改？

- 核心结论：分支注册归属、callback 地址稳定性、回调鉴权、对账兜底。
- 核心原理
  - 这四项决定系统能不能上线，不只是“优雅”。
- 关键机制
  - RM 自注册 + 稳定服务标识 + 安全回调 + 差异修复。
- 面试要点
  - 先讲风险，再讲方案。

### 37.1.2 哪些可以后置？

- 核心结论：管理台、自动扩缩容、全链路追踪可以后置，但状态机和恢复不能。
- 核心原理
  - 没有管理台还能人工，没有恢复就会卡死。
- 关键机制
  - 先保证正确性，再补体验。
- 面试要点
  - 能排序，不堆功能。

## 38. Coordinator 内核与部署

### 38.1.1 Begin/Register/Report 的事务边界怎么划？

- 核心结论：每个协议动作一个本地事务，状态更新和索引写入一起提交。
- 核心原理
  - Begin 查 request_id，插入 global。
  - Register 锁 global 行，分配 branch_seq，插 branch。
  - Report 锁 global，更新 branch 状态。
- 关键机制
  - 行锁顺序固定，避免死锁。
  - 影响行数必须检查。
- 面试要点
  - 不能把“查”和“改”拆到两个事务。

### 38.1.2 XID 怎么保证多实例不重复？

- 核心结论：MySQL 号段表原子领号，不靠应用内存。
- 核心原理
  - `UPDATE id_segment SET max_id = max_id + step`。
  - 同事务 SELECT 新水位。
- 关键机制
  - 行锁保证并发安全。
  - 号段独立提交，业务回滚不影响发号。
- 面试要点
  - 不要用“时间戳 + 随机数”解释唯一性。

### 38.1.3 gRPC 适配层负责什么？

- 核心结论：只做 proto/API 映射、错误码转换、调用服务层。
- 核心原理
  - 业务逻辑不写在 gRPC handler。
  - 参数错误映射为明确错误码。
- 关键机制
  - server 启动、端口、线程池独立配置。
- 面试要点
  - 不要把 gRPC 层写成业务层。

### 38.1.4 Nacos 为什么只注册 TC？

- 核心结论：TC 是服务端，TM 通过服务名发现 TC；TC 不发现 RM。
- 核心原理
  - Spring Cloud 默认按 Web 端口注册，TC 只有 gRPC，需要专用 Registrar。
  - 注册 metadata 标记 protocol=grpc。
- 关键机制
  - RM 回调地址来自分支注册，不来自 Nacos。
- 面试要点
  - 能说清“谁注册、谁发现、谁不发现”。

### 38.1.5 Scheduler 扫什么、怎么退避？

- 核心结论：扫两类：TRYING 超时、CONFIRMING/CANCELLING 到期。
- 核心原理
  - 每个 xid 抢 owner lease。
  - 成功推进；冲突跳过；失败记录。
- 关键机制
  - 退避 1s/5s/30s/2min/10min。
  - 超限 DEAD/FAILED。
- 面试要点
  - 扫描是“发现工作”，不是“执行所有分支”。

### 38.1.6 Metrics 应该看什么？

- 核心结论：扫描数、重试数、成功/跳过/错误、回调延迟、DEAD。
- 核心原理
  - 指标是旁路，不能影响主流程。
- 关键机制
  - 没 registry 时 no-op。
- 面试要点
  - 能说出“卡在 CONFIRMING”用哪个指标发现。

### 38.1.7 Coordinator 数据库怎么扛？

- 核心结论：global/branch 按 xid 访问，索引要覆盖状态+时间扫描。
- 核心原理
  - 热点在状态扫描和 branch 更新。
  - 事务日志会增长。
- 关键机制
  - 状态+时间索引、归档/清理、连接池。
  - 分库分表要按 xid 路由，不能跨分片事务。
- 面试要点
  - 先证明单库上限，再谈分片。

### 38.1.8 真实 E2E 暴露过哪些接入坑？

- 核心结论：Nacos Config import、BarrierMapper 扫描、自动配置顺序、Controller 参数名。
- 核心原理
  - Starter 自动装配依赖 classpath/扫描边界。
- 关键机制
  - 显式 config import、MapperScan、参数名编译。
- 面试要点
  - 能讲一个真实接入坑，比背概念可信。

### 38.1.9 多 TC 还缺什么验证？

- 核心结论：缺多实例并发、owner 切换、网络分区、旧回调。
- 核心原理
  - lease 设计正确，但未做故障注入。
- 关键机制
  - kill owner、延迟网络、重复回调。
- 面试要点
  - 没验证就说没验证。

## 39. 事务框架测试矩阵

### 39.1.1 单测覆盖什么？

- 核心结论：状态机、幂等、空回滚、悬挂、参数校验、序列化。
- 核心原理
  - 纯逻辑用单测，快速回归。
- 关键机制
  - 分支状态 CAS、barrier 转换、错误码。
- 面试要点
  - 不能只测成功路径。

### 39.1.2 集成测试覆盖什么？

- 核心结论：DB 事务、gRPC、callback、outbox、Stream。
- 核心原理
  - 真实中间件验证装配和事务边界。
- 关键机制
  - 单机 fixture + 真实 MySQL/Redis。
- 面试要点
  - 能说清单测和集成测试边界。

### 39.1.3 E2E 覆盖什么？

- 核心结论：成功双 RM、失败撤销、重复回调、空回滚、悬挂。
- 核心原理
  - 真实服务链路才能发现装配问题。
- 关键机制
  - 断言业务表 + barrier + global + outbox。
- 面试要点
  - E2E 不是“能启动”。

### 39.1.4 故障注入怎么做？

- 核心结论：kill RM/TC、延迟网络、重复回调、丢响应、分区。
- 核心原理
  - 只有故障注入才能证明恢复逻辑。
- 关键机制
  - 断言无孤儿预占、无重复扣减、最终收敛。
- 面试要点
  - 能说清每个故障的预期状态。

## 40. 面试官追问（框架层）

### 40.1.1 为什么 Coordinator 要独立部署？

- 核心结论：状态和调度不能放在业务应用内存里。
- 核心原理
  - 多实例共享状态、统一恢复。
- 关键机制
  - 无状态 TC + MySQL 状态。
- 面试要点
  - 不要每个业务应用自己跑 TC。

### 40.1.2 TC 崩溃后 TM 怎么办？

- 核心结论：TM 的 commit/rollback 可重试，最终由 TC 状态收敛。
- 核心原理
  - requestId/xid 幂等。
- 关键机制
  - 客户端超时 + 重试 + 查询。
- 面试要点
  - 不能假设一次 RPC 成功。

### 40.1.3 事务日志能删吗？

- 核心结论：终态保留审计窗口，活跃事务不能删。
- 核心原理
  - 日志是恢复依据。
- 关键机制
  - 按状态+时间归档。
- 面试要点
  - 删除策略要跟合规/恢复窗口一致。

## 41. 资源建模与业务隔离

### 41.1.1 什么资源适合 TCC？

- 核心结论：能显式建模“可用/冻结/锁定”状态的资源最适合。
- 核心原理
  - 库存：available → frozen → sold。
  - 优惠券：AVAILABLE → LOCKED → USED。
  - 额度：available → reserved → assigned。
- 关键机制
  - Try 只改预留状态。
  - Confirm/Cancel 只做状态转换。
- 面试要点
  - 不能预留的资源，不适合硬套 TCC。

### 41.1.2 没有“冻结字段”的资源怎么做？

- 核心结论：用业务状态/占用记录表达预留，不要直接改终态。
- 核心原理
  - 例如线索分配：NEW → ASSIGNING → ASSIGNED。
  - 分配记录本身可以作为预留。
- 关键机制
  - 状态机 + 唯一约束。
- 面试要点
  - 预留不一定是数字字段。

### 41.1.3 一个 RM 内有多个资源，分支怎么切？

- 核心结论：能在一个本地事务原子完成的，可以一个分支；不能的，拆多个分支。
- 核心原理
  - 分支是补偿单位，不是数据库表单位。
  - 一个分支失败要能整体 Cancel。
- 关键机制
  - 资源边界 + 事务边界。
- 面试要点
  - 不要为了“一个服务一个分支”把不可原子操作塞一起。

### 41.1.4 Try 预留多少合适？

- 核心结论：按业务最小占用单位预留，不要一次锁全部。
- 核心原理
  - 预留过多会降低并发。
  - 预留过少会导致 Confirm 失败。
- 关键机制
  - 数量/金额/库存单位。
- 面试要点
  - 预留粒度是业务决策，不是技术细节。

### 41.1.5 业务读模型怎么设计？

- 核心结论：读接口只暴露终态/可用量，不暴露 frozen 为可用。
- 核心原理
  - TCC 中间态可能被读到。
- 关键机制
  - 视图/字段/状态过滤。
- 面试要点
  - 用户不应看到“半成功”。

## 42. 多分支、并行与批量

### 42.1.1 多分支串行和并行怎么选？

- 核心结论：默认串行；只有分支独立、上下文可显式传递时才并行。
- 核心原理
  - ThreadLocal 上下文不适合并行。
  - 并行失败要 Cancel 所有已成功分支。
- 关键机制
  - 显式 xid/branchId 参数或上下文传播。
- 面试要点
  - 并行提高吞吐，但增加失败组合。

### 42.1.2 分支多了会有什么问题？

- 核心结论：RPC 数、DB 行数、回调、重试都线性增长。
- 核心原理
  - 3N 级别的协议调用。
  - 回调线程池/连接池压力。
- 关键机制
  - 限制分支数、批量注册/上报、并行回调。
- 面试要点
  - 100 个分支不是“更细”，可能是灾难。

### 42.1.3 部分分支失败怎么收敛？

- 核心结论：全局 rollback，Cancel 已成功分支；失败分支空回滚/收敛。
- 核心原理
  - 不能只处理失败分支。
- 关键机制
  - 分支状态表 + 重试。
- 面试要点
  - 关键是“已成功的也要撤销”。

### 42.1.4 并行分支的上下文怎么传？

- 核心结论：不能靠普通 ThreadLocal 跨线程。
- 核心原理
  - 线程池复用会污染上下文。
- 关键机制
  - 显式参数、任务包装、上下文传播。
- 面试要点
  - 能说出一个并行导致 branchId 串线的 bug。

## 43. 性能与容量

### 43.1.1 TCC 的延迟预算怎么拆？

- 核心结论：Begin + N 次 Try + N 次上报 + Commit + N 次回调。
- 核心原理
  - 每个 RPC 和 DB 写入都增加延迟。
  - 回调可以异步，但状态推进要同步。
- 关键机制
  - 批量、并行、连接池、超时。
- 面试要点
  - 能估算 10 个分支的调用次数。

### 43.1.2 TC 的瓶颈在哪里？

- 核心结论：DB 状态更新、gRPC 回调、owner 竞争、扫描。
- 核心原理
  - 每个事务多行更新。
  - 回调是远程 IO。
- 关键机制
  - 索引、批量、线程池隔离、限流。
- 面试要点
  - 不要只说“TC 无状态所以能扩”。

### 43.1.3 事务日志分片怎么设计？

- 核心结论：按 xid 路由，保证同一事务的 global/branch 在一个分片。
- 核心原理
  - 跨分片事务会引入新问题。
- 关键机制
  - xid 生成带分片信息或路由表。
- 面试要点
  - 不能按时间随便分。

### 43.1.4 回调线程池怎么隔离？

- 核心结论：按 RM/endpoint 隔离，避免慢 RM 拖垮所有回调。
- 核心原理
  - 回调是外部依赖。
- 关键机制
  - 信号量/线程池/超时/熔断。
- 面试要点
  - TC 也要防雪崩。

## 44. 多租户、安全与权限

### 44.1.1 TM 接入怎么鉴权？

- 核心结论：认证调用方、授权 bizCode、限制分支数/速率。
- 核心原理
  - 防止恶意/误用打爆 TC。
- 关键机制
  - token/mTLS + 配额。
- 面试要点
  - 内网不等于可信。

### 44.1.2 callback 怎么防伪造？

- 核心结论：mTLS/token/allowlist/重放防护。
- 核心原理
  - callback 是外部输入。
- 关键机制
  - 短期 token 绑定 xid/branchId。
- 面试要点
  - 当前项目未实现，要承认。

### 44.1.3 多租户怎么隔离？

- 核心结论：bizCode/namespace + 配额 + 数据隔离。
- 核心原理
  - 共享 TC 时一个租户可能打爆全局。
- 关键机制
  - 限流、连接池、表分区。
- 面试要点
  - 不只是加一个字段。

## 45. 场景设计题

### 45.1.1 设计“下单扣库存 + 优惠券”的 TCC。

- 核心结论：库存冻结、优惠券锁定，两个 RM 自注册，TC 统一 Confirm/Cancel。
- 核心原理
  - Try 原子条件扣减，Confirm 转终态，Cancel 释放。
- 关键机制
  - barrier 三防 + Outbox。
- 面试要点
  - 先画失败链路，再画成功。

### 45.1.2 有 100 个分支怎么办？

- 核心结论：限制单事务分支数，拆成多个全局事务或批量资源。
- 核心原理
  - 分支数线性放大 RPC/DB/回调。
- 关键机制
  - 批量资源、异步、分片。
- 面试要点
  - 不要硬扛，先重构边界。

### 45.1.3 跨币种/跨账务怎么处理？

- 核心结论：TCC 只管资源预留，汇率/账务规则属于业务。
- 核心原理
  - 不要在 Confirm 里做复杂规则计算。
- 关键机制
  - Try 固化汇率/金额快照。
- 面试要点
  - 业务规则前置，Confirm 只落终态。

## 46. 对账系统设计（TCC）

### 46.1.1 TCC 对账到底对什么？

- 核心结论：对“全局状态、分支状态、RM barrier、业务表、消息表”五方是否收敛。
- 核心原理
  - TC 认为成功，不代表 RM 业务表成功。
  - RM 预留成功，不代表全局最终 Confirm。
  - Outbox 已 SENT，不代表消费方 CONSUMED。
- 关键机制
  - 按 xid/branchId/msgId/eventKey 对比。
  - 以业务不变量为最终判断。
- 面试要点
  - 对账不是“再跑一次业务”。

### 46.1.2 五类差异分别是什么？

- 核心结论：卡住、状态冲突、孤儿预占、业务未落、消息未达。
- 核心原理
  - 卡住：global/branch 长期 TRYING/CONFIRMING/CANCELLING。
  - 状态冲突：global 终态与 branch/barrier 不一致。
  - 孤儿预占：barrier TRIED 但全局已结束。
  - 业务未落：TCC CONFIRMED 但业务表没有终态。
  - 消息未达：SENT 但消费方没有 CONSUMED。
- 关键机制
  - 每类差异对应不同修复动作。
- 面试要点
  - 能分类，才能修复。

### 46.1.3 对账扫描怎么做？

- 核心结论：短周期扫“卡住/消息滞留”，长周期扫“全量业务差异”。
- 核心原理
  - 5 分钟扫 TRYING/CONFIRMING/CANCELLING 超时、SENT 老消息。
  - T+1 全量对比业务终态和 TCC 终态。
- 关键机制
  - 分页/分片/水位，避免全表扫。
  - 差异写 `t_recon_diff` 唯一键幂等。
- 面试要点
  - 短周期是止血，长周期是兜底。

### 46.1.4 `t_recon_diff` 应该怎么设计？

- 核心结论：一条差异一行，唯一键防重复，状态可追踪。
- 核心原理
  - 字段：差异类型、bizCode/bizId、xid/branchId、msgId/eventKey、期望值、实际值、状态、修复动作、重试次数、创建/解决时间。
- 关键机制
  - 唯一键：差异类型 + 业务键 + 版本/批次。
  - 状态：OPEN/FIXING/RESOLVED/IGNORED。
- 面试要点
  - 差异表是修复工单，不是日志表。

### 46.1.5 差异怎么修？

- 核心结论：能自动的有限重试，不能自动的进人工，所有操作幂等可审计。
- 核心原理
  - 补 Cancel、补 Confirm、补发消息、人工冲正。
  - 修复前重新读最新状态，避免覆盖。
- 关键机制
  - 修复动作带版本/CAS。
  - 操作人、原因、结果留痕。
- 面试要点
  - 对账修复不能变成第二次事故。

### 46.1.6 当前仓库做到哪一步？

- 核心结论：只有 repository 钩子和文档设计，没有完整对账任务。
- 核心原理
  - `markDoneBatch`、`findForReconcile` 存在。
  - `t_recon_diff` 有设计，没有调度器/修复器。
- 关键机制
  - 面试时说“设计已完成、任务未落地”，不要夸大。
- 面试要点
  - 能说清缺口，比假装上线可信。

## 47. 简历口径（58 TCC）

### 47.1.1 项目标题和背景怎么写？

- 标题：58CRM 跨服务一致性框架（TCC + Outbox + Redis Stream）| Java 后端。
- 背景：CRM 12 条业务线、40+ 服务，跨服务写入靠“先落库再发 MQ + 定时扫表补偿”，存在索引不更新、业绩重复、权益重复发放。

### 47.1.2 简历 bullet 怎么写？

- 实现 RM barrier：Try/Confirm/Cancel 幂等、空回滚、悬挂防护；Confirm 与业务表、Outbox 同本地事务。

## 50. 业务场景深挖（58 TCC）

### 50.1.1 场景一：合同生效后的多下游更新

- 业务动作：合同从“审批中”变成“已生效”。
- 需要同时做：
  - 合同库写终态。
  - 搜索索引更新合同状态。
  - 业绩结算累计合同金额。
  - 权益系统发放合同权益。
- 失败场景：
  - 合同成功、搜索失败 -> 搜索仍显示审批中。
  - 合同成功、业绩失败 -> 业绩少算。
  - 权益重复消费 -> 重复发放。
- TCC 怎么解：
  - Try 预留/锁定，Confirm 写终态，Cancel 释放。
  - 下游通过消息/Outbox 可靠通知。
- 面试要点
  - 用“合同生效”讲，不要用抽象 A/B 服务。

### 50.1.2 场景二：线索分配

- 业务动作：把线索分配给销售。
- 需要同时做：
  - 线索归属更新。
  - 销售配额预占/扣减。
  - 客户表同步。
- 失败场景：
  - 线索已分配，客户表没同步。
  - 配额扣了，线索分配失败。
- TCC 怎么解：
  - quota/coupon 等 RM 先 Try，成功再 Confirm。
  - 任一失败，Cancel 已成功分支。
- 面试要点
  - 这是“跨服务资源预留”的典型。

### 50.1.3 场景三：业绩结算

- 业务动作：订单完成/合同生效后累计业绩。
- 风险：消息重复 -> 业绩重复累计；消息丢失 -> 业绩少算。
- TCC/消息怎么解：
  - 业务表 + Outbox 同事务。
  - 消费端幂等（eventKey/msgId + 唯一约束）。
- 面试要点
  - 业绩是钱，重复/丢失都是事故。

### 50.1.4 场景四：权益发放

- 业务动作：活动/合同触发权益发放。
- 风险：重复发放、超发、用户重复领。
- TCC/消息怎么解：
  - 预算/库存 Try 预留。
  - 发券记录唯一键。
  - Confirm 写终态 + Outbox。
- 面试要点
  - 权益和预算必须一起讲。

### 50.1.5 场景五：历史不一致修复

- 业务动作：旧补偿任务/人工对账发现差异。
- 处理：
  - 查 TCC global/branch/barrier。
  - 补 Confirm/Cancel 或人工冲正。
  - 记录差异/审计。
- 面试要点
  - 没有对账，历史差异永远修不干净。

## 51. 旧流程 vs 新流程

### 51.1.1 改造前业务怎么跑？

- 业务服务先写自己的库。
- 再发普通 MQ。
- 下游消费失败，各业务线自己写定时任务扫表补偿。
- 对账靠人工导 Excel。
- 结果：补偿逻辑重复、口径不一致、问题发现晚。

### 51.1.2 改造后业务怎么跑？

- 业务服务调用统一 TCC/消息 SDK。
- Try 预留，Confirm 落终态，Cancel 释放。
- Outbox 可靠通知下游。
- 平台统一重试/对账/告警。
- 结果：业务只关心自己的动作，平台管一致性。

### 51.1.3 业务方需要改什么？

- 实现 TccAction 三个方法（或注解）。
- 保证 Try/Confirm/Cancel 幂等。
- 提供 resourceKey/回调地址。
- 配置业务线/权限/预算。
- 面试要点
  - “零改造”不等于“什么都不写”。

## 52. 业务角色与协作

### 52.1.1 谁参与？

- 业务研发：实现 Try/Confirm/Cancel、业务表。
- 平台研发：Coordinator、SDK、消息、对账。
- SRE：部署、容量、告警、发布。
- DBA：表/索引/分片/慢 SQL。
- 产品/运营：业务规则、补偿策略。

### 52.1.2 新业务线怎么接入？

- 联调/压测/灰度。
- 观察一致性/告警。
- 面试要点
  - 接入是“业务建模 + 技术接入”，不是给个 SDK。

### 52.1.3 事故谁负责？

- 业务方确认业务影响/补偿。
- 平台方定位事务状态/重试。
- SRE/DBA 处理基础设施。
- 事后复盘/改进。
- 面试要点
  - 先止损，再定位，再补偿。

### 54.1.2 “业务方为什么要用？”

## 56. 面试兜底（TCC）

### 56.1.1 一句话

- 让 12 条业务线跨服务写入从“各自补偿 + 人工对账”变成“统一 TCC + 可靠消息 + 对账兜底”。

### 56.1.2 数字定版

- 12 条业务线、40+ 服务。
- 8W QPS（项目参数口径）。
- 9 个自建补偿任务下线。
- 每业务线每周约 4 人时对账节省。
- 222 核心单测、双 RM E2E。
- 当前开源实现本机消息约 700 msg/s。

### 56.1.3 必答 8 问

- 为什么 TCC 不用 2PC/Seata？
  - 2PC 锁 DB、阻塞、性能差；TCC 业务预留、Try 后释放 DB 锁；代价是业务侵入/幂等/隔离弱。
- 为什么 RM 自注册？
  - actionName/resourceKey/endpoint 属于 RM；TM 只传 xid+payload。
- 空回滚/悬挂/幂等？
  - 无 barrier Cancel -> SUSPENDED；迟到 Try 拒绝；重复按状态返回。
- 为什么 Confirm 写 Outbox？
  - 业务终态+barrier+Outbox 同事务，防业务成功消息丢。
- TC 怎么回调？
  - 先落 branch 状态，DB 事务外 gRPC 回调；超时按重试，幂等靠 barrier。
- owner lease 干什么？
  - 多 TC 只允许一个 owner；旧 owner 被 fencing。
- 怎么证明零资损？
  - 预算流水/barrier/对账/PENDING；承认边界。
- 当前最大债？
  - TM 代注册、callbackEndpoint 耦合、callback 未鉴权、begin 不自动重试。

### 56.1.4 被挑战怎么答

- “8W 真的吗？” -> 项目参数口径；当前实现本机约 700 msg/s，不混。
- “零资损？” -> 统计窗口 + 对账 + 人工兜底；Redis 正本/双写仍是风险。
- “222 测试能证明什么？” -> 核心逻辑回归，不是生产容量。
- “为什么还写 TCC？” -> 业务需要撤销已成功分支，不是为技术而技术。

### 56.1.5 红线

- 不说 TCC 强一致。
- 不说当前实现就是 8W。
- 不说 callback 已鉴权。
- 不说 TM 注册是标准设计。
