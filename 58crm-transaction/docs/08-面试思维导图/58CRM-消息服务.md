# 58CRM 消息服务面试思维导图

> 基线：`crm-tx-outbox` + `crm-tx-consumer` 当前实现。
> 范围：Outbox、Redis Stream、消费组、PEL、租约、时间轮、幂等、故障恢复、参数、面试题。
> 用法：标题层级即节点层级；每个节点按“核心结论、核心原理、关键机制、面试要点”展开。

## 0. 消息服务总览

### 0.1.1 消息服务解决什么问题？

- 核心结论：解决业务已成功、但下游事件没有可靠送达的问题。
- 核心原理
  - 业务表和消息表写在同一个 MySQL 本地事务。
  - 后台 relay 异步投递到 Redis Stream。
  - 消费端用消费组、PEL、幂等恢复。
- 关键机制
  - MySQL 是正本，Redis 是传送带。
  - 发送失败可重扫，消费崩溃可认领。
- 面试要点
  - 一句话：先可靠落库，再异步搬运。

### 0.1.2 三条红线是什么？

- 核心结论：MySQL 决定消息是否存在；Redis 只决定传得快不快；一条事件只进一个业务线 Stream。
- 核心原理
  - 消息正本不能只放 Redis。
  - 不做多消费组 fan-out。
- 关键机制
  - 一条业务线一个 Stream、一个消费组。
- 面试要点
  - 不要把 Redis 当最终消息存储。

### 0.1.3 当前可验证事实是什么？

- 核心结论：生产、投递、消费、PEL 恢复、租约、幂等链路都已实现。
- 核心原理
  - 本机压测约 700 msg/s。
  - 单测/集成测试全绿。
- 关键机制
  - 没有生产 8W QPS 验证。
- 面试要点
  - 区分“本仓库验证”和“原项目口径”。

## 1. 背景与边界

### 1.1.1 为什么不能业务提交后直接发 MQ？

- 核心结论：业务提交和 MQ 发送是两次独立操作，无法原子。
- 核心原理
  - 业务成功、发送失败 → 消息丢。
  - 发送成功、业务回滚 → 幽灵消息。
- 关键机制
  - Outbox 把业务事实和消息记录放进同一个本地事务。
- 面试要点
  - 不是 MQ 不可靠，是业务提交和发送不可原子。

### 1.1.2 Outbox 和 TCC 是什么关系？

- 核心结论：TCC 管跨服务资源，Outbox 管业务事实后的可靠通知。
- 核心原理
  - TCC Confirm 写业务终态 + Outbox。
  - Outbox 不参与 Try/Confirm/Cancel 决策。
- 关键机制
  - Confirm 的本地事务包含业务表、barrier、Outbox。
- 面试要点
  - 两者是配合，不是替代。

### 1.1.3 消息服务不做什么？

- 核心结论：不做通用 MQ、不做多消费组 fan-out、不做全局顺序。
- 核心原理
  - 只服务当前框架的可靠事件。
  - 一条事件只被一个业务线消费组消费。
- 关键机制
  - 跨业务线用不同 Stream。
- 面试要点
  - 边界越清楚，设计越稳。

## 2. 模块地图

### 2.1.1 生产端有哪些模块？

- 核心结论：api、config、persistence、producer、pipeline。
- 核心原理
  - api：BusinessEvent、OutboxPublisher。
  - producer：Scanner、Buffer、Sender、Producer。
  - pipeline：拦截器、路由、序列化、Stream 发布。
- 关键机制
  - OutboxPublisher 只写 MySQL，不直接写 Redis。
- 面试要点
  - 能说清 Scanner 和 Sender 的职责分离。

### 2.1.2 消费端有哪些模块？

- 核心结论：pull、persist、worker、ack、lease、recovery。
- 核心原理
  - Puller 拉取，Persister 落库，Worker 处理，AckBatcher 确认。
  - Lease 管理租约，PendingRecovery 恢复 PEL。
- 关键机制
  - 每个模块线程/职责独立。
- 面试要点
  - 消费端不是一个大循环。

### 2.1.3 Starter 负责什么？

- 核心结论：自动装配 OutboxProducer 和 ConsumerBootstrap。
- 核心原理
  - 绑定 bizCode、Stream、group、Redis、DB。
  - 按配置启动多个业务线消费者。
- 关键机制
  - 不在 Starter 里扫描业务 Mapper。
- 面试要点
  - 自动装配边界要清楚。

## 3. 生产链路

### 3.1.1 OutboxPublisher 做什么？

- 核心结论：在当前本地事务里写一条 INIT 消息，返回 msgId。
- 核心原理
  - 不写 Redis。
  - 业务事务回滚，消息一起回滚。
- 关键机制
  - 业务方只依赖这个接口。
- 面试要点
  - 发布接口必须和业务事务绑定。

### 3.1.2 BusinessEvent 有哪些字段？

- 核心结论：eventKey、bizCode、bizId、eventType、payload。
- 核心原理
  - eventKey 是业务事件唯一键。
  - bizCode 决定 Stream。
- 关键机制
  - 消费幂等优先用 eventKey。
- 面试要点
  - 不要把 bizId 当事件唯一键。

### 3.1.3 Scanner 怎么扫？

- 核心结论：按业务线公平扫描 INIT 消息，放入有界 buffer。
- 核心原理
  - 每个业务线每轮至少一个名额。
  - cursor 每轮移动，避免头部饥饿。
- 关键机制
  - inFlight 去重，避免重复入队。
- 面试要点
  - Scanner 不发送、不改状态。

### 3.1.4 Buffer 为什么有双重容量？

- 核心结论：同时限制条数和字节数，防止小消息撑爆条数、大消息撑爆内存。
- 核心原理
  - 全局容量 + 单业务线容量。
  - 队列满时 Scanner 跳过该业务线。
- 关键机制
  - 形成背压，不无限堆积。
- 面试要点
  - 只限条数不够。

### 3.1.5 Sender 怎么批量发送？

- 核心结论：先取第一条，在 linger 窗口内聚合，最多 batchSize 条。
- 核心原理
  - 减少 XADD RTT。
  - 按 Stream 分组发送。
- 关键机制
  - linger 默认 10ms，batch 默认 256。
- 面试要点
  - 批量是吞吐和延迟的折中。

### 3.1.6 一条坏消息会拖死整批吗？

- 核心结论：不会，整批失败会二分拆分，直到定位单条。
- 核心原理
  - 二分后好消息继续发送。
  - 单条失败标记失败/DEAD。
- 关键机制
  - poison 消息隔离。
- 面试要点
  - 这是生产端的重要容错。

### 3.1.7 XADD 成功但状态回写失败怎么办？

- 核心结论：保持 INIT，下一轮重投，消费端幂等兜底。
- 核心原理
  - Stream 已有消息，MySQL 还是 INIT。
- 关键机制
  - 消息可能重复，不能保证 exactly-once。
- 面试要点
  - 至少一次 + 幂等是现实解。

### 3.1.8 Sender shard 怎么分？

- 核心结论：按 bizCode 排序后轮询分配到 shard。
- 核心原理
  - shard 数不超过 bizCode 数。
  - 每个 sender 只处理自己的业务线。
- 关键机制
  - 避免多线程抢同一队列。
- 面试要点
  - 分区是为了局部性和减少竞争。

## 4. Redis Stream

### 4.1.1 Stream entry 是什么？

- 核心结论：只追加日志，每条消息有唯一 ID。
- 核心原理
  - XADD 返回 `时间戳-序号`。
  - 读取后 entry 不会自动删除。
- 关键机制
  - Stream 和消费组游标分离。
- 面试要点
  - entry 是消息本体。

### 4.1.2 消费组是什么？

- 核心结论：一组消费者竞争消费同一个 Stream。
- 核心原理
  - 组维护 last-delivered-id。
  - 组维护 PEL。
- 关键机制
  - 一个业务线一个组。
- 面试要点
  - 消费组不是多下游广播。

### 4.1.3 PEL 是什么？

- 核心结论：已投递但未 XACK 的消息列表。
- 核心原理
  - 消费者崩溃后消息还在 PEL。
  - 可以被其他消费者认领。
- 关键机制
  - 每个消费组各自维护 PEL。
- 面试要点
  - PEL 是恢复的核心。

### 4.1.4 XACK 做了什么？

- 核心结论：从 PEL 删除，不删除 Stream entry。
- 核心原理
  - 表示消费组已确认处理。
- 关键机制
  - XACK 必须在业务提交成功后。
- 面试要点
  - 先 XACK 再处理会丢消息。

### 4.1.5 为什么不用 List？

- 核心结论：List 没有消费组、PEL、XACK，崩溃恢复弱。
- 核心原理
  - List 弹出即离开队列。
  - Stream 有 pending 和认领。
- 关键机制
  - 本仓库用 Stream；原项目历史用 List。
- 面试要点
  - 不要把历史口径说成当前实现。

## 5. 消费链路

### 5.1.1 Puller 怎么拉？

- 核心结论：XREADGROUP 批量拉取，放入有界队列。
- 核心原理
  - 默认 count 500，block 1s。
  - 拉取后消息进入 PEL。
- 关键机制
  - Puller 不写 DB、不 XACK。
- 面试要点
  - 拉取和处理解耦。

### 5.1.2 Persister 做什么？

- 核心结论：批量 INSERT `t_consume_record(READY)`。
- 核心原理
  - 落库后 Worker 才能领取。
  - 落库前崩溃靠 PEL 重拉。
- 关键机制
  - Persister 也不 XACK。
- 面试要点
  - 消费记录是本地恢复依据。

### 5.1.3 Worker 怎么处理？

- 核心结论：claim READY → PROCESSING → 执行业务 → CONSUMED → ACK。
- 核心原理
  - 业务表、消费记录、幂等表同事务提交。
  - 提交成功后才 ACK。
- 关键机制
  - 失败 markRetry，超限 DEAD。
- 面试要点
  - 业务提交和 XACK 顺序不能反。

### 5.1.4 为什么先落 READY 再处理？

- 核心结论：把“拉到内存”变成“本地可恢复状态”。
- 核心原理
  - 内存队列崩溃会丢。
  - READY 记录可以本地恢复。
- 关键机制
  - PEL 也能兜底。
- 面试要点
  - 双重恢复：本地记录 + PEL。

### 5.1.5 ACK 为什么批量？

- 核心结论：减少 Redis RTT，提高吞吐。
- 核心原理
  - 每 100ms 或 200 条批量 XACK。
  - 按 Stream/group 分组。
- 关键机制
  - 队列满会丢弃 ACK，消息留 PEL。
- 面试要点
  - 批量提吞吐，但故障时 PEL 停留更久。

## 6. 租约与时间轮

### 6.1.1 为什么需要租约？

- 核心结论：防止两个 worker 同时处理同一条消息。
- 核心原理
  - 领取时设置 ownerToken、ownerEpoch、leaseUntil。
  - 过期后其他 worker 可以接管。
- 关键机制
  - 续约证明 worker 还活着。
- 面试要点
  - 只有租约不够，还要 fencing。

### 6.1.2 为什么需要 fencing？

- 核心结论：旧 worker 可能恢复后提交，必须阻止。
- 核心原理
  - `markConsumed` 带 ownerToken/ownerEpoch。
  - 影响行数为 0 表示任务已被接管。
- 关键机制
  - 旧事务回滚，不能 ACK。
- 面试要点
  - 租约 + fencing 才完整。

### 6.1.3 时间轮解决什么？

- 核心结论：避免每个任务一个 Timer/线程，批量调度续约和超时。
- 核心原理
  - Netty HashedWheelTimer。
  - tick 1s，wheel size 512。
- 关键机制
  - 到期任务进续约队列，批量 UPDATE。
- 面试要点
  - 高并发下不能一条消息一个定时器。

### 6.1.4 续约失败会怎样？

- 核心结论：任务从 in-flight 移除，lease 到期后其他 worker 接管。
- 核心原理
  - 续约批量失败触发 leaseLost。
- 关键机制
  - 旧 worker 提交被 fencing。
- 面试要点
  - 不能无限续约卡死任务。

### 6.1.5 Worker 卡死不响应中断怎么办？

- 核心结论：停止续约、标记 LOST、告警，lease 到期后接管。
- 核心原理
  - 不能安全 Thread.stop。
  - 外部副作用必须幂等。
- 关键机制
  - 旧 worker 无法提交。
- 面试要点
  - 隔离 + 告警 + fencing。

## 7. 幂等设计

### 7.1.1 当前仓库的幂等怎么做？

- 核心结论：MySQL `t_idempotent` 唯一约束。
- 核心原理
  - `insert ignore`，插入成功才执行业务。
  - 重复消息直接跳过业务。
- 关键机制
  - msgId 主键，biz_key 唯一。
- 面试要点
  - 当前没有 Redis 幂等占位。

### 7.1.2 幂等键怎么选？

- 核心结论：优先 eventKey，为空回退 msgId。
- 核心原理
  - eventKey 表达业务事件唯一性。
  - msgId 表达消息唯一性。
- 关键机制
  - 业务 handler 仍需幂等。
- 面试要点
  - 不要只用数据库自增 ID。

### 7.1.3 原项目为什么 Redis + MySQL？

- 核心结论：原项目用 Redis 快速挡重复，MySQL 唯一约束兜底。
- 核心原理
  - Redis 降低 DB 压力。
  - MySQL 防 Redis 丢/过期。
- 关键机制
  - 本仓库只落地 MySQL，面试要区分口径。
- 面试要点
  - 不要把原项目方案说成本仓库实现。

### 7.1.4 外部副作用怎么幂等？

- 核心结论：发短信、调第三方、写搜索必须带业务幂等键。
- 核心原理
  - 数据库能回滚，外部副作用不能。
- 关键机制
  - 通过 Outbox/补偿，不裸调。
- 面试要点
  - 消费幂等不等于外部副作用幂等。

## 8. PEL 恢复

### 8.1.1 消费者崩溃后消息在哪？

- 核心结论：在 PEL 里。
- 核心原理
  - XREADGROUP 已投递，但未 XACK。
- 关键机制
  - PendingRecovery 扫 XPENDING。
- 面试要点
  - 消息不会因为进程崩溃自动消失。

### 8.1.2 当前恢复流程是什么？

- 核心结论：XPENDING 扫描 → 查消费记录 → 过期标记 READY → 缺记录 XCLAIM。
- 核心原理
  - CONSUMED/DEAD 直接补 XACK。
  - READY 跳过。
  - lease 未过期跳过。
- 关键机制
  - 当前不用 XAUTOCLAIM。
- 面试要点
  - 恢复是“转移 pending”，不是重启消费者。

### 8.1.3 XACK 失败怎么办？

- 核心结论：消息留 PEL，重新投递后幂等跳过，再补 XACK。
- 核心原理
  - 业务已 CONSUMED。
  - 消费记录能判断。
- 关键机制
  - 幂等表兜底。
- 面试要点
  - ACK 失败不等于业务失败。

## 9. 故障矩阵

### 9.1.1 业务回滚消息会怎样？

- 核心结论：消息和业务一起回滚。
- 核心原理
  - 同一个本地事务。
- 关键机制
  - 不存在幽灵消息。
- 面试要点
  - Outbox 的第一价值。

### 9.1.2 relay 崩溃怎么办？

- 核心结论：消息还在 MySQL INIT，Scanner 重扫。
- 核心原理
  - 消息正本未丢。
- 关键机制
  - 进程重启继续。
- 面试要点
  - 发送失败只是延迟。

### 9.1.3 Redis 挂了会丢消息吗？

- 核心结论：不会丢正本，Outbox 可重放。
- 核心原理
  - MySQL 是正本。
- 关键机制
  - Redis 恢复后重投。
- 面试要点
  - 前提是消息已写 MySQL。

### 9.1.4 Puller/Persister/Worker 崩溃分别怎么办？

- 核心结论：Puller 崩溃靠 PEL；Persister 前崩溃靠 PEL；Persister 后崩溃靠 READY；Worker 崩溃靠 lease。
- 核心原理
  - 每层都有恢复依据。
- 关键机制
  - 本地记录 + PEL 双保险。
- 面试要点
  - 能按阶段说出恢复来源。

### 9.1.5 ACK 队列满会怎样？

- 核心结论：ACK 被丢弃，消息留 PEL，恢复任务补 ACK。
- 核心原理
  - 队列有界，offer 失败只告警。
- 关键机制
  - PEL 停留、重复投递、延迟上升。
- 面试要点
  - 生产要监控 ack 队列满日志。

## 10. 参数与容量

### 10.1.1 Outbox 默认参数是什么？

- 核心结论：linger 10ms、batch 256、buffer 5 万条/64MB、scan 1000/10ms。
- 核心原理
  - 延迟换吞吐。
  - 条数和字节双重限制。
- 关键机制
  - senderThreads 默认 8。
- 面试要点
  - 参数是生产起点，不是魔法值。

### 10.1.2 Consumer 默认参数是什么？

- 核心结论：queue 1 万、persist 500、worker 200/8、lease 60s、renew 20s。
- 核心原理
  - 批量提高吞吐。
  - lease 兼顾恢复速度与续约压力。
- 关键机制
  - retry 30s、maxRetries 3。
- 面试要点
  - 参数要按业务 RT/容量调。

### 10.1.3 为什么 batch 不是越大越好？

- 核心结论：批量大吞吐高，但单批延迟和内存压力大。
- 核心原理
  - 失败重试成本也更大。
- 关键机制
  - 按压测和下游能力定。
- 面试要点
  - 吞吐、延迟、内存三角。

### 10.1.4 消息服务吞吐是多少？

- 核心结论：本仓库本机约 700 msg/s。
- 核心原理
  - 不是生产容量结论。
- 关键机制
  - 原项目 8W 是面试口径。
- 面试要点
  - 不夸大数据。

## 11. 表结构

### 11.1.1 `t_local_message` 怎么设计？

- 核心结论：消息正本，msg_id 主键，event_key 唯一。
- 核心原理
  - 状态、重试、Stream entry ID 都持久化。
- 关键机制
  - 扫描按状态和重试时间。
- 面试要点
  - 正本表不能省。

### 11.1.2 `t_consume_record` 怎么设计？

- 核心结论：消费记录 + 租约 + 状态。
- 核心原理
  - READY/PROCESSING/CONSUMED/DEAD。
  - owner_token/owner_epoch/lease_until。
- 关键机制
  - 索引覆盖 claim/recovery。
- 面试要点
  - 这是本地恢复的核心表。

### 11.1.3 `t_idempotent` 怎么设计？

- 核心结论：msg_id 主键，biz_key 唯一。
- 核心原理
  - 插入成功才执行业务。
- 关键机制
  - 重复消息直接跳过。
- 面试要点
  - 唯一约束是最后防线。

## 12. 设计取舍

### 12.1.1 为什么 MySQL 是正本？

- 核心结论：可事务、可恢复、可审计。
- 核心原理
  - Redis 是缓存/传输。
- 关键机制
  - 发送失败可重扫。
- 面试要点
  - 不要本末倒置。

### 12.1.2 为什么至少一次而不是 exactly-once？

- 核心结论：网络/进程崩溃无法完全消除重复。
- 核心原理
  - 用幂等收敛成业务一次。
- 关键机制
  - 唯一约束 + 状态机。
- 面试要点
  - 不要承诺端到端 exactly-once。

## 13. 消息专项面试题

### 13.1.1 为什么先写 MySQL？

- 核心结论：业务表和消息表必须同事务。
- 核心原理：Redis 不能参与 MySQL 事务。
- 关键机制：Outbox 正本。
- 面试要点：可靠优先。

### 13.1.2 Outbox relay 失败会丢吗？

- 核心结论：不会，INIT 可重扫。
- 核心原理：消息在 MySQL。
- 关键机制：Sender 重试。
- 面试要点：失败只是延迟。

### 13.1.3 Stream 和 List 区别？

- 核心结论：Stream 有消费组/PEL/ACK。
- 核心原理：List 弹出即丢。
- 关键机制：XPENDING/XCLAIM。
- 面试要点：别混历史口径。

### 13.1.4 消费者崩溃消息在哪？

- 核心结论：PEL。
- 核心原理：未 XACK。
- 关键机制：PendingRecovery。
- 面试要点：XPENDING/XCLAIM。

### 13.1.5 为什么先提交再 XACK？

- 核心结论：先 XACK 会丢 PEL。
- 核心原理：业务崩溃无法恢复。
- 关键机制：业务提交成功后 ACK。
- 面试要点：顺序不能反。

### 13.1.6 XACK 失败怎么办？

- 核心结论：PEL 重投，幂等跳过，补 ACK。
- 核心原理：消费记录已 CONSUMED。
- 关键机制：幂等表。
- 面试要点：ACK 失败不是业务失败。

### 13.1.7 重复消费怎么挡？

- 核心结论：msgId/eventKey + MySQL 唯一约束。
- 核心原理：insert ignore。
- 关键机制：业务 handler 也要幂等。
- 面试要点：当前没有 Redis 占位。

### 13.1.8 为什么有租约还要 fencing？

- 核心结论：租约防并发领取，fencing 防旧 worker 提交。
- 核心原理：ownerToken/epoch CAS。
- 关键机制：更新影响 0 行。
- 面试要点：两者缺一不可。

### 13.1.9 时间轮解决什么？

- 核心结论：批量调度租约，避免每任务一个 Timer。
- 核心原理：分桶时间轮。
- 关键机制：到期进续约队列。
- 面试要点：高并发必备。

### 13.1.10 消费失败重试几次？

- 核心结论：默认 3 次，退避 30s。
- 核心原理：超限 DEAD。
- 关键机制：配置化。
- 面试要点：要有上限。

## 14. 一句话

### 14.1.1 用一句话总结消息服务

- 核心结论：Outbox 保证业务成功消息一定在 MySQL，Stream 保证高效搬运，PEL + 租约 + 幂等保证崩溃后可收敛。
- 核心原理：正本、传输、恢复三层分工。
- 关键机制：MySQL、Stream、barrier/幂等。
- 面试要点：先可靠，再吞吐，最后谈 exactly-once。

## 15. 正确设计总则

### 15.1.1 消息服务的正确分层是什么？

- 核心结论：正本层 MySQL、传输层 Redis Stream、消费恢复层 PEL/消费记录、业务幂等层。
- 核心原理
  - MySQL 决定消息是否存在。
  - Redis 决定传得快不快。
  - PEL/租约决定崩溃后能不能恢复。
- 关键机制
  - 四层职责分开，任何一层都不能替代另一层。
- 面试要点
  - 能画出四层，而不是只说“用了 Redis”。

```text
业务事务
  -> MySQL 正本（业务表 + t_local_message）
  -> Relay（Scanner/Buffer/Sender）
  -> Redis Stream
  -> Consumer Group / PEL
  -> Worker + 幂等
  -> XACK
```

### 15.1.2 为什么不能只做“业务提交后发消息”？

- 核心结论：业务提交和发送不是原子操作。
- 核心原理
  - 提交成功、发送失败 → 丢。
  - 发送成功、事务回滚 → 幽灵消息。
- 关键机制
  - Outbox 在同一本地事务写消息记录。
- 面试要点
  - 这是 Outbox 的第一性原理。

## 16. 生产多实例设计

### 16.1.1 多实例 Scanner 怎么避免重复扫描？

- 核心结论：inFlight 去重 + DB 状态 + 唯一发送责任。
- 核心原理
  - 同一实例内 inFlight 防重复入队。
  - 跨实例靠状态/发送分片/幂等。
- 关键机制
  - 消息最终可能重复投递，消费端幂等兜底。
- 面试要点
  - 不要声称生产端绝对不重复。

### 16.1.2 Sender 分片怎么设计？

- 核心结论：按 bizCode 稳定分片，一个 Stream 尽量由一个 Sender 负责。
- 核心原理
  - 减少多实例竞争。
  - 保持批量局部性。
- 关键机制
  - shard 数不超过 bizCode 数。
  - 失败后重新分配。
- 面试要点
  - 分片是为了降低竞争，不是提高单机吞吐。

### 16.1.3 发送批次怎么做到“坏消息不拖死好消息”？

- 核心结论：整批失败二分拆分，最终定位单条 poison 消息。
- 核心原理
  - 好消息继续发送。
  - 坏消息单独标记失败/DEAD。
- 关键机制
  - 单条失败不影响整批。
- 面试要点
  - 这是生产端容错的关键设计。

### 16.1.4 发送成功但状态回写失败怎么办？

- 核心结论：保持 INIT，下一轮重投，消费端幂等。
- 核心原理
  - XADD 已成功，MySQL 不知道。
- 关键机制
  - 至少一次投递。
- 面试要点
  - 重复是设计内，不是 bug。

## 17. 消费多实例与恢复

### 17.1.1 多消费者怎么避免重复处理？

- 核心结论：消费组竞争 + PEL + 消费记录/幂等，不是只靠一个锁。
- 核心原理
  - 组内一条消息投递给一个 consumer。
  - 崩溃后 PEL 转移。
- 关键机制
  - 业务幂等是最后防线。
- 面试要点
  - 消费组只能减少并发重复，不能消除重复。

### 17.1.2 消费端完整恢复链路是什么？

- 核心结论：PEL 扫 pending → 查消费记录 → 过期标记 READY → 缺记录 XCLAIM。
- 核心原理
  - READY/ PROCESSING / CONSUMED / DEAD 四种状态。
- 关键机制
  - lease 过期才允许接管。
- 面试要点
  - 恢复不是重启消费者，是转移 pending。

```text
PEL pending
  -> 有记录：CONSUMED/DEAD -> 补 XACK
  -> 有记录：READY -> 等 Worker
  -> 有记录：PROCESSING + lease 未过期 -> 跳过
  -> 有记录：PROCESSING + lease 过期 -> 标 READY
  -> 无记录 -> XCLAIM -> 插 READY
```

### 17.1.3 租约和 fencing 怎么配合？

- 核心结论：租约防并发领取，fencing 防旧 worker 提交。
- 核心原理
  - claim 设置 ownerToken/ownerEpoch/leaseUntil。
  - markConsumed 带同样 token/epoch。
- 关键机制
  - 影响行数为 0 表示任务已被接管。
- 面试要点
  - 只有租约没有 fencing，会出现双写。

### 17.1.4 Worker 卡死怎么处理？

- 核心结论：停止续约、标记 LOST、告警，lease 到期后接管。
- 核心原理
  - 不能安全 Thread.stop。
  - 外部副作用必须幂等。
- 关键机制
  - 旧 worker 无法提交。
- 面试要点
  - 隔离 + 告警 + fencing。

### 17.1.5 ACK 失败/队列满怎么办？

- 核心结论：消息留 PEL，恢复任务重投，幂等跳过，补 ACK。
- 核心原理
  - ACK 不是业务成功的前提。
- 关键机制
  - ACK 队列满只告警，不阻塞业务。
- 面试要点
  - 监控 ACK 队列满日志。

## 18. 各种异常场景

### 18.1.1 业务事务回滚消息会怎样？

- 核心结论：消息和业务一起回滚。
- 核心原理
  - 同一本地事务。
- 关键机制
  - 不存在幽灵消息。
- 面试要点
  - Outbox 的第一价值。

### 18.1.2 relay 进程崩溃怎么办？

- 核心结论：消息还在 MySQL INIT，重启后重扫。
- 核心原理
  - 正本未丢。
- 关键机制
  - Scanner 重新加载。
- 面试要点
  - 失败只是延迟。

### 18.1.3 Redis 不可用怎么办？

- 核心结论：保持 INIT/SENT，退避重试，不删正本。
- 核心原理
  - Redis 是传输层。
- 关键机制
  - 恢复后重投。
- 面试要点
  - MySQL 在，消息就不会丢。

### 18.1.4 消费者崩溃在业务提交前后分别怎样？

- 核心结论：提交前事务回滚，消息留 PEL/READY；提交后消息可能重复，幂等跳过。
- 核心原理
  - 本地事务和 XACK 不是原子的。
- 关键机制
  - 幂等表 + 消费记录。
- 面试要点
  - 这是 at-least-once 的必然窗口。

### 18.1.5 重复消息怎么处理？

- 核心结论：msgId/eventKey 唯一约束，插入成功才执行业务。
- 核心原理
  - 重复消息不能重复改业务。
- 关键机制
  - MySQL `t_idempotent`。
- 面试要点
  - 当前仓库没有 Redis 占位，别混原项目口径。

### 18.1.6 消息积压怎么发现/处理？

- 核心结论：看 Stream lag、PEL pending、消费延迟；扩容消费者/提高批量/限流上游。
- 核心原理
  - 积压是吞吐不足或下游变慢。
- 关键机制
  - 监控 + 背压 + 扩容。
- 面试要点
  - 不要只说“加机器”。

## 19. 面试官追问

### 19.1.1 为什么消息先写 MySQL，不直接写 Redis？

- 核心结论：Redis 不能参与业务本地事务，也不能作为可靠正本。
- 核心原理
  - 业务表和消息表要同事务。
- 关键机制
  - Outbox relay 异步搬运。
- 面试要点
  - 先可靠，再吞吐。

### 19.1.2 为什么不用 Redis List？

- 核心结论：List 没有消费组/PEL/ACK，崩溃恢复弱。
- 核心原理
  - 弹出即离开队列。
- 关键机制
  - Stream 有 pending 和认领。
- 面试要点
  - 原项目历史用 List，当前仓库用 Stream。

### 19.1.3 为什么先提交业务再 XACK？

- 核心结论：先 XACK 会丢 PEL，业务崩溃无法恢复。
- 核心原理
  - ACK 表示已处理。
- 关键机制
  - 提交成功后再批量 ACK。
- 面试要点
  - 顺序反了就是丢消息。

### 19.1.4 怎么保证消费幂等？

- 核心结论：唯一约束 + 状态机 + 业务幂等键。
- 核心原理
  - 至少一次投递无法消除重复。
- 关键机制
  - msgId/eventKey 唯一。
- 面试要点
  - 不要承诺 exactly-once。

### 19.1.5 租约过期后旧 worker 又活了怎么办？

- 核心结论：fencing 让它提交失败。
- 核心原理
  - ownerToken/epoch 不匹配。
- 关键机制
  - CAS 更新影响 0 行。
- 面试要点
  - 旧 worker 不能覆盖新 owner。

### 19.1.6 消息吞吐上不去怎么排查？

- 核心结论：分生产、Redis、DB、消费、下游五段看。
- 核心原理
  - 瓶颈可能在批量、锁、连接池、下游 RT。
- 关键机制
  - 指标 + 压测 + 火焰图。
- 面试要点
  - 不要一上来就加机器。

### 19.1.7 消息服务最大的风险是什么？

- 核心结论：ACK 滞留、租约失效、外部副作用不幂等、积压。
- 核心原理
  - 恢复链路比正常链路更关键。
- 关键机制
  - PEL/租约/幂等/监控。
- 面试要点
  - 能说出至少三个故障场景。

## 20. 独立审计：消息服务的真实风险

### 20.1.1 多实例 Scanner 会重复扫同一条消息吗？

- 核心结论：会。当前 inFlight 只在本 JVM 内，跨实例没有互斥。
- 核心原理
  - 两个实例同时扫到同一条 INIT，可能都入队、都 XADD。
  - 消费端幂等能兜底，但会产生重复流量。
- 关键机制
  - DB claim/lease、按业务线分片、或发送幂等键。
  - 不能只靠本地内存去重。
- 面试要点
  - 敢承认“生产端可能重复”，比假装 exactly-once 可信。

### 20.1.2 ACK 队列满时丢弃 ACK 有什么后果？

- 核心结论：消息留 PEL，恢复任务会再处理/补 ACK。
- 核心原理
  - ACK 只是确认，不是业务成功的前提。
- 关键机制
  - PEL 滞留、重复投递、延迟上升。
  - 生产应阻塞/持久化 ACK 或至少强告警。
- 面试要点
  - 这是当前实现的一个真实风险点。

### 20.1.3 PEL 扫描会不会饿死旧消息？

- 核心结论：会，如果每次只取固定窗口且没有游标/空闲时间过滤。
- 核心原理
  - 老 pending 可能一直在扫描范围里。
  - 新 pending 也可能被反复处理。
- 关键机制
  - 按 min-idle、游标、分批推进。
  - 处理过的记录要推进状态。
- 面试要点
  - 恢复任务也要考虑公平性。

### 20.1.4 消息 schema 和版本怎么管理？

- 核心结论：payload 会演进，消费端必须兼容旧消息。
- 核心原理
  - 消息可能积压数小时/数天。
  - 新消费者可能读到旧格式。
- 关键机制
  - 版本字段、向后兼容、默认值、灰度。
  - 不做破坏性字段删除。
- 面试要点
  - “消息发出去就不归你管”是错的。

### 20.1.5 死信和人工重放怎么设计？

- 核心结论：重试上限后要进 DEAD，并提供查询/重放/审计。
- 核心原理
  - 永久失败重试无意义。
  - 人工处理需要知道原消息和失败原因。
- 关键机制
  - 死信表/状态、操作日志、权限控制。
- 面试要点
  - 没有死信，失败消息就永远沉默。

### 20.1.6 顺序和重试怎么处理？

- 核心结论：Stream 只保证单 Stream 内追加顺序，多 worker 并发处理会乱序。
- 核心原理
  - 消费组竞争 + 并发 worker 不保序。
- 关键机制
  - 按业务键分区、串行消费、或业务状态机容忍乱序。
- 面试要点
  - 不要说“用了 Stream 就有顺序”。

### 20.1.7 消息保留/裁剪怎么做？

- 核心结论：Stream 会增长，必须按时间/长度裁剪，但不能裁掉未消费消息。
- 核心原理
  - PEL 仍引用 entry，裁剪要谨慎。
  - MySQL 正本可重放，Stream 可重建。
- 关键机制
  - XTRIM/MAXLEN、监控长度、按业务线保留。
- 面试要点
  - 保留策略要跟恢复窗口匹配。

## 21. 生产状态机与对账

### 21.1.1 `t_local_message` 的完整状态是什么？

- 核心结论：INIT、SENT、DONE、DEAD 四种状态，不是只有 INIT/SENT。
- 核心原理
  - INIT：业务事务已写库，还没投递到 Stream。
  - SENT：XADD 成功，等待对账确认消费结果。
  - DONE：对账确认消费方已经 CONSUMED，生产方终态。
  - DEAD：重投/发送超限，等待人工处理。
- 关键机制
  - SENT 不等于消费成功。
  - 消费成功由消费方记录和 XACK 证明。
- 面试要点
  - 能解释“生产方为什么不知道消费结果”。

### 21.1.2 为什么 SENT 不能直接变 DONE？

- 核心结论：XADD 只证明消息进了 Redis，不证明消费方处理成功。
- 核心原理
  - 消费可能失败、重复、延迟。
  - 生产方不能靠发送结果推断消费结果。
- 关键机制
  - 对账读取消费方 `CONSUMED`，再推进 DONE。
- 面试要点
  - SENT 是“已投递”，DONE 是“已消费确认”。

### 21.1.3 对账组件应该怎么设计？

- 核心结论：按 eventKey/msgId 对比生产消息和消费记录，修复差异。
- 核心原理
  - 生产侧：SENT + stream_entry_id。
  - 消费侧：CONSUMED + msgId/eventKey。
- 关键机制
  - 已消费但生产未 DONE → 推进 DONE。
  - 生产 SENT 但消费缺失 → 重放/告警。
  - 长期不一致 → 差异表/人工。
- 面试要点
  - 当前仓库有 markDone 能力，但对账任务未完整落地，要如实说。

### 21.1.4 DEAD 之后怎么处理？

- 核心结论：人工查看原因，修复后重放为 INIT，不能直接改 SENT。
- 核心原理
  - DEAD 是重试耗尽，不是成功。
  - 直接改 SENT 会绕过投递/消费验证。
- 关键机制
  - 重放记录操作人、原因、时间。
- 面试要点
  - 要有操作审计。

## 22. Stream 运维陷阱

### 22.1.1 建消费组用 0 还是 $？

- 核心结论：首次建组用 0 可以消费历史消息；用 $ 只消费新消息。
- 核心原理
  - 0 从最早开始。
  - $ 从当前末尾开始。
- 关键机制
  - 业务需要补历史时不能用 $。
- 面试要点
  - 建组参数决定是否漏历史。

### 22.1.2 BUSYGROUP 是什么？

- 核心结论：消费组已存在，不是错误。
- 核心原理
  - 多实例启动都会尝试建组。
- 关键机制
  - 捕获 BUSYGROUP 视为成功。
- 面试要点
  - 这是幂等建组。

### 22.1.3 XACK 写错 entryId 会怎样？

- 核心结论：PEL 不会清，消息会被重复投递。
- 核心原理
  - XACK 必须和投递的 entryId 一致。
- 关键机制
  - ACK 命令要带 stream/group/entryId。
- 面试要点
  - ACK 错 ID 是常见低级故障。

### 22.1.4 XTRIM 会不会删掉未消费消息？

- 核心结论：会，XTRIM 不看 PEL，可能把 pending 的 entry 裁掉。
- 核心原理
  - PEL 只引用 entry ID，entry 被裁后无法恢复 payload。
- 关键机制
  - 按未消费水位/保留窗口裁剪。
  - 优先依赖 MySQL 正本重放。
- 面试要点
  - 不能无脑 MAXLEN。

### 22.1.5 Redis 持久化能保证消息不丢吗？

- 核心结论：不能把 Redis 当唯一正本；RDB/AOF 都有窗口。
- 核心原理
  - Redis 故障可能丢最近写入。
- 关键机制
  - MySQL Outbox 可重放。
- 面试要点
  - 可靠性来自 MySQL，不是 Redis 配置。

### 22.1.6 一个 Stream 能做多下游广播吗？

- 核心结论：消费组是竞争消费，不是广播。
- 核心原理
  - 同组消费者分摊消息。
  - 多下游需要多 Stream/多组或上层分发。
- 关键机制
  - 本设计按业务线分 Stream，不做 fan-out。
- 面试要点
  - 不要把消费组当 pub/sub。

## 23. 启动、顺序与多实例

### 23.1.1 消费者启动顺序是什么？

- 核心结论：建组 → 启动 Puller/Persister/Worker/ACK/Recovery → 再对外服务。
- 核心原理
  - 组不存在时拉取会失败。
  - 先拉取后落库会丢内存消息。
- 关键机制
  - 启动失败要整体回滚/关闭。
- 面试要点
  - 启动顺序也是可靠性的一部分。

### 23.1.2 多消费者能保证顺序吗？

- 核心结论：不能保证全局顺序；多 worker 并发会乱序。
- 核心原理
  - 消费组只保证投递，不保证处理顺序。
  - 并发 worker 各自提交。
- 关键机制
  - 按业务键串行/分区，或业务状态机容忍乱序。
- 面试要点
  - 不要说“用了 Stream 就有顺序”。

### 23.1.3 多实例消费组怎么分配？

- 核心结论：Redis Stream 没有 Kafka 式分区 rebalance，消费者共同读同一个组游标。
- 核心原理
  - XREADGROUP 由 Redis 分配新消息。
  - PEL 记录归属。
- 关键机制
  - 多实例靠组竞争，不靠本地分区表。
- 面试要点
  - 扩容消费者不一定线性提升，受 DB/下游限制。

## 24. 生产管线扩展点

### 24.1.1 BizCodeRegistry 解决什么？

- 核心结论：业务线白名单 + Stream key 推导。
- 核心原理
  - 未注册 bizCode 直接拒绝。
  - `streamKey = prefix + bizCode`。
- 关键机制
  - 防止拼错写错 Stream。
- 面试要点
  - 白名单是边界，不是装饰。

### 24.1.2 Interceptor 能做什么？

- 核心结论：发送前/后的横切逻辑，如 trace、审计、指标、payload 修饰。
- 核心原理
  - 不能改 msgId/bizId 等身份字段。
- 关键机制
  - 身份字段变更会导致状态回写错行。
- 面试要点
  - 扩展点要有约束。

### 24.1.3 Partitioner 和 Serializer 怎么分工？

- 核心结论：Partitioner 决定去哪个 Stream，Serializer 决定 field/value。
- 核心原理
  - 默认按 bizCode 路由。
  - 序列化失败要可重试/DEAD。
- 关键机制
  - 序列化结果要能反序列化。
- 面试要点
  - 路由和编码不要混在一起。

### 24.1.4 OutboxSendResult.entryId 有什么用？

- 核心结论：记录 XADD 返回的 Stream entry ID，供对账/排障。
- 核心原理
  - entryId 能定位 Stream 消息。
- 关键机制
  - 当前实现有些路径不回填，属于边界。
- 面试要点
  - 要诚实说实现完整度。

## 25. 压测与死锁复盘

### 25.1.1 本机压测结果是什么？

- 核心结论：单机单 MySQL 约 715 QPS，没有达到 10W。
- 核心原理
  - 16 核/15GiB，Redis 7，MySQL 8。
  - 10 万条，16 worker，139.8s。
- 关键机制
  - Redis 拉取/队列/ACK 不是瓶颈。
  - MySQL 每消息事务是瓶颈。
- 面试要点
  - 不要包装成“生产 8W”。

### 25.1.2 为什么增加 worker 反而下降？

- 核心结论：单 MySQL 连接/锁竞争饱和，更多线程只增加争抢。
- 核心原理
  - 16 worker 约 617 QPS，64 worker 约 369 QPS。
  - 多消费者运行时约 542 QPS。
- 关键机制
  - 不是线程越多吞吐越高。
- 面试要点
  - 瓶颈在 DB 事务，不在 Redis。

### 25.1.3 死锁是怎么产生的？

- 核心结论：Persister 对已存在消息重复 INSERT IGNORE，持 S 锁；Worker 更新同一行要 X 锁。
- 核心原理
  - `INSERT IGNORE` 对已存在行仍做唯一键检查。
  - 批量插入与单行 update 形成锁顺序冲突。
- 关键机制
  - 先 SELECT 已存在 ID，过滤后只插新消息。
  - claim 改单行条件 UPDATE，减少多行锁。
- 面试要点
  - 能说清根因，不是“加个重试”。

### 25.1.4 10W QPS 的结论是什么？

- 核心结论：当前单库不宣称 10W；先做批量幂等/状态写入、多消费者/多 Stream 验证，再考虑分片。
- 核心原理
  - 没有基准就分片是逃避问题。
- 关键机制
  - 先证明单库优化上限。
- 面试要点
  - 诚实说边界比吹数字可信。

## 26. 设计点完整性清单

### 26.1.1 生产端设计点有哪些？

- 核心结论：事务绑定、状态机、白名单、扫描、缓冲、发送、路由、序列化、拦截器、重试、DEAD、对账。
- 核心原理
  - 每一项都影响可靠性或可运维性。
- 关键机制
  - 不能只实现“写库 + XADD”。
- 面试要点
  - 能按链路逐项展开。

### 26.1.2 消费端设计点有哪些？

- 核心结论：建组、拉取、缓冲、落库、领取、幂等、租约、续约、fencing、ACK、恢复、DEAD、顺序。
- 核心原理
  - 消费端是状态机 + 并发控制 + 恢复。
- 关键机制
  - 每层都有失败恢复来源。
- 面试要点
  - 不要只说“XREADGROUP + XACK”。

### 26.1.3 运维设计点有哪些？

- 核心结论：lag、PEL、ACK 延迟、重试、DEAD、队列满、Stream 长度、Redis/MySQL 故障。
- 核心原理
  - 消息系统的问题通常先在积压/延迟上体现。
- 关键机制
  - 指标 + 告警 + 人工重放。
- 面试要点
  - 能说出三个关键告警。

### 26.1.4 当前还没落地的有哪些？

- 核心结论：完整对账任务、完整死信管理台、消息 schema 版本、跨集群容灾。
- 核心原理
  - 这些是生产化能力，不是当前主链路。
- 关键机制
  - 面试时明确“设计/已实现/未实现”。
- 面试要点
  - 不把设计稿说成已上线。

## 27. 面试官追问

### 27.1.1 消息服务最难的是什么？

- 核心结论：不是发出去，而是崩溃后如何证明最终收敛。
- 核心原理
  - 重复、丢失、顺序、租约、幂等同时存在。
- 关键机制
  - 正本 + PEL + 幂等 + 对账。
- 面试要点
  - 讲恢复，不要只讲吞吐。

### 27.1.2 怎么证明消息不丢？

- 核心结论：不能证明绝对不丢，只能证明有正本、可重放、可对账。
- 核心原理
  - Redis 可能丢；MySQL 正本在。
- 关键机制
  - 重扫 + 幂等 + 对账。
- 面试要点
  - 说边界，不吹零丢失。

### 27.1.3 怎么证明消息不重复？

- 核心结论：不能证明网络层不重复，只能证明业务效果不重复。
- 核心原理
  - 至少一次投递。
- 关键机制
  - 幂等键 + 唯一约束 + 状态机。
- 面试要点
  - 区分“投递重复”和“业务重复”。

### 27.1.4 消费者扩容为什么不一定提升吞吐？

- 核心结论：瓶颈可能在 MySQL 事务、锁、连接池或下游。
- 核心原理
  - 多线程争抢同一行/同一连接。
- 关键机制
  - 压测定位瓶颈。
- 面试要点
  - 不要用“加消费者”回答所有问题。

## 28. 监控与运维

### 28.1.1 消息系统要监控哪些指标？

- 核心结论：生产积压、消费 lag、PEL pending、ACK 延迟、重试、DEAD、Stream 长度。
- 核心原理
  - 问题通常先在积压/延迟体现。
- 关键机制
  - 按 bizCode/consumer 维度打点。
- 面试要点
  - 能说出“lag 大但 PEL 不大”和“PEL 大”的区别。

### 28.1.2 ACK 延迟怎么发现？

- 核心结论：看投递时间到 XACK 的时间差，不只看 QPS。
- 核心原理
  - 高吞吐可能掩盖长尾。
- 关键机制
  - 消费记录时间戳 + ACK 时间。
- 面试要点
  - P99 比平均值重要。

### 28.1.3 告警怎么设？

- 核心结论：持续 lag、PEL 增长、ACK 队列满、DEAD 增长、Redis/MySQL 错误。
- 核心原理
  - 这些表示自动恢复可能失效。
- 关键机制
  - 阈值 + 持续时长 + 分级。
- 面试要点
  - 不要只监控 CPU。

### 28.1.4 人工重放怎么保证安全？

- 核心结论：重放前确认幂等、权限、审计；不能直接改状态跳过链路。
- 核心原理
  - 重放可能重复执行业务。
- 关键机制
  - 操作人/原因/消息 ID/结果记录。
- 面试要点
  - 重放不是“再发一次”这么简单。

## 29. Redis Cluster 与容量

### 29.1.1 Stream key 在 Cluster 下怎么设计？

- 核心结论：一个 Stream 一个 key，按业务线拆分，天然分散到不同 slot。
- 核心原理
  - Redis Cluster 按 key 计算 slot。
  - 多 key 操作需要同 slot。
- 关键机制
  - 单 Stream 操作只涉及一个 key。
  - 跨 Stream 批量要分开执行。
- 面试要点
  - 不要假设所有 Stream 在同一个节点。

### 29.1.2 需要 hash tag 吗？

- 核心结论：只有需要多 key 同 slot 时才用 hash tag。
- 核心原理
  - 本项目按业务线单 Stream，通常不需要。
  - 若做全局幂等/计数多 key，才需要设计 tag。
- 关键机制
  - hash tag 会导致热点，不能滥用。
- 面试要点
  - 能说出“为什么要/为什么不要”。

### 29.1.3 容量怎么估？

- 核心结论：按消息大小 × 积压条数 + PEL + Stream 保留量估算。
- 核心原理
  - Stream 不会因消费自动删除。
  - PEL 也占内存。
- 关键机制
  - 监控内存、长度、裁剪策略。
- 面试要点
  - 不能只按 QPS 估容量。

### 29.1.4 Redis 主从切换会丢消息吗？

- 核心结论：异步复制可能丢最近写入；MySQL 正本兜底。
- 核心原理
  - 主挂时未同步数据可能丢。
- 关键机制
  - 重扫 + 幂等 + 对账。
- 面试要点
  - 不要把 Redis 主从当强一致。

## 30. 多租户与安全

### 30.1.1 业务线怎么隔离？

- 核心结论：bizCode、独立 Stream、独立消费组、独立幂等空间。
- 核心原理
  - 一个业务线积压不影响其他线。
- 关键机制
  - 白名单 + Stream 分片。
- 面试要点
  - 不是靠一个字段过滤。

### 30.1.2 消息里能不能放敏感数据？

- 核心结论：尽量少放，必须放要加密/脱敏/权限控制。
- 核心原理
  - 消息会落 MySQL/Redis/日志。
- 关键机制
  - payload 脱敏、访问审计、保留期限。
- 面试要点
  - 不要把消息系统当保险箱。

### 30.1.3 payload 大小怎么限制？

- 核心结论：设置单条上限，超限拒绝/大对象引用。
- 核心原理
  - 大 payload 会撑爆 buffer/Redis/内存。
- 关键机制
  - `payload_ref` 存对象存储引用。
- 面试要点
  - 大消息是生产事故源。

## 31. 测试矩阵

### 31.1.1 生产端测试什么？

- 核心结论：事务绑定、状态机、扫描公平、buffer 背压、批量拆分、重试/DEAD。
- 核心原理
  - 每个失败路径都要有测试。
- 关键机制
  - 单测 + 真实 Redis 集成。
- 面试要点
  - 不能只测发送成功。

### 31.1.2 消费端测试什么？

- 核心结论：拉取、落库、claim、幂等、租约、fencing、ACK、PEL 恢复。
- 核心原理
  - 并发和崩溃是重点。
- 关键机制
  - 多 worker/多实例/故障注入。
- 面试要点
  - 能说出至少三个崩溃场景。

### 31.1.3 压测看什么？

- 核心结论：QPS、P99 延迟、积压、PEL、DB 锁、死锁。
- 核心原理
  - 吞吐不是唯一指标。
- 关键机制
  - 逐步加 worker，找拐点。
- 面试要点
  - 715 QPS 是当前本机结果。

## 32. 面试官追问（消息层）

### 32.1.1 为什么 MySQL 是瓶颈还要先用它？

- 核心结论：可靠性和事务边界优先，Redis 不能做正本。
- 核心原理
  - 先保证不丢，再优化吞吐。
- 关键机制
  - 批量、异步、分片后续优化。
- 面试要点
  - 不要为了吞吐牺牲正确性。

### 32.1.2 消息服务能不能不用 Redis？

- 核心结论：可以，但需要另一种传输/通知机制；Redis 只是当前选择。
- 核心原理
  - 正本在 MySQL，Redis 是传输。
- 关键机制
  - 可换 MQ/Stream/本地投递。
- 面试要点
  - 区分本质和实现。

### 32.1.3 消费端为什么不用线程池直接处理？

- 核心结论：需要背压、租约、幂等、ACK、恢复，裸线程池不可控。
- 核心原理
  - 线程池没有持久化状态。
- 关键机制
  - Puller/队列/Worker/ACK 分层。
- 面试要点
  - 消费端是系统，不是回调。

## 33. 热点、大 Key 与流量倾斜

### 33.1.1 一个业务线消息特别多会怎样？

- 核心结论：单个 Stream 成热点，Redis 分片和消费组都被压。
- 核心原理
  - 一个 Stream 一个 key，落一个 slot。
  - 单业务线消费组吞吐受单 Stream/DB 限制。
- 关键机制
  - 按子业务/租户拆 Stream，或分片 key。
- 面试要点
  - “按业务线隔离”不等于自动水平扩展。

### 33.1.2 大 payload 有什么风险？

- 核心结论：内存、网络、Redis、DB 都被放大，容易 OOM/超时。
- 核心原理
  - Buffer 按字节限容。
  - 大消息会拖慢整批。
- 关键机制
  - 单条上限 + payload_ref 大对象引用。
- 面试要点
  - 大消息要单独治理。

### 33.1.3 消费热点怎么打散？

- 核心结论：按业务键拆 Stream/分区，或把大业务线拆成多个消费组。
- 核心原理
  - 单 Stream 的消费者扩展有上限。
- 关键机制
  - 子 Stream + 路由规则。
- 面试要点
  - 拆之前先确认瓶颈在 Redis 还是 DB。

## 34. 背压与流控

### 34.1.1 生产端怎么背压？

- 核心结论：Scanner 用有界 Buffer，满了跳过/等待，不能无限堆内存。
- 核心原理
  - 条数 + 字节双重限制。
- 关键机制
  - tryPut 失败跳过当前业务线。
- 面试要点
  - 背压要能传到上游。

### 34.1.2 消费端怎么背压？

- 核心结论：有界队列 + Puller 限速 + Worker 数量，防止拉得比处理快。
- 核心原理
  - 无限拉取会 OOM。
- 关键机制
  - 队列满阻塞 Puller。
- 面试要点
  - 背压不是丢消息。

### 34.1.3 ACK 也要背压吗？

- 核心结论：要，ACK 队列满不能静默丢。
- 核心原理
  - 丢 ACK 会让 PEL 滞留。
- 关键机制
  - 阻塞/持久化 ACK 或强告警。
- 面试要点
  - 当前实现丢弃 ACK 是风险。

### 34.1.4 Redis/MySQL 慢时怎么限流？

- 核心结论：按依赖隔离限流，避免重试风暴。
- 核心原理
  - 重试会放大故障。
- 关键机制
  - 退避、熔断、令牌桶。
- 面试要点
  - 不能所有失败都立即重试。

## 35. 消费组运维 Runbook

### 35.1.1 lag 持续上涨怎么排查？

- 核心结论：先看生产速率、消费速率、PEL、DB/下游耗时。
- 核心原理
  - 积压可能是生产突增，也可能是消费变慢。
- 关键机制
  - XINFO GROUPS、监控、日志。
- 面试要点
  - 不要直接扩容。

### 35.1.2 PEL 很大但 lag 不大说明什么？

- 核心结论：消息已投递但未 ACK，问题在消费/ACK 链路。
- 核心原理
  - 消费者崩溃、处理慢、ACK 队列满。
- 关键机制
  - XPENDING 明细、消费者归属、idle。
- 面试要点
  - lag 和 PEL 是两种信号。

### 35.1.3 消费者一直重启怎么办？

- 核心结论：看启动失败、组不存在、Redis 连接、DB 连接、权限。
- 核心原理
  - 启动顺序/外部依赖问题。
- 关键机制
  - 启动日志 + 健康检查。
- 面试要点
  - 不要只看业务异常。

### 35.1.4 消费组被误删怎么办？

- 核心结论：重建组会丢游标/PEL，必须从 MySQL 正本/消费记录恢复。
- 核心原理
  - 组游标是 Redis 状态，不是正本。
- 关键机制
  - 重建 + 重放 + 幂等。
- 面试要点
  - 组不是可靠状态存储。

### 35.1.5 Stream 被裁剪过头怎么办？

- 核心结论：从 MySQL 正本重放，不能从 Redis 恢复已删 entry。
- 核心原理
  - Stream 只是传输。
- 关键机制
  - Outbox 重扫 + 消费幂等。
- 面试要点
  - 裁剪策略要留恢复窗口。

## 36. 多 Stream 与容量规划

### 36.1.1 多业务线怎么分配消费者？

- 核心结论：一个业务线一个消费运行时，按资源独立扩缩容。
- 核心原理
  - 不同业务线流量/RT 不同。
- 关键机制
  - ConsumerBootstrap 按 bizCode 配置。
- 面试要点
  - 不要所有业务线共用一个固定线程池。

### 36.1.2 多实例怎么估容量？

- 核心结论：按消息速率、payload、DB 写、PEL、保留窗口估算。
- 核心原理
  - 瓶颈常在 DB 事务，不在 Redis。
- 关键机制
  - 压测拐点 + 监控。
- 面试要点
  - 715 QPS 是当前本机上限。

### 36.1.3 10 万 QPS 需要什么？

- 核心结论：批量写入、分片、异步、独立 DB/Redis、限流，不是单机加线程。
- 核心原理
  - 单 MySQL 每消息事务撑不住。
- 关键机制
  - 分库分表 + 批量状态推进。
- 面试要点
  - 先证明瓶颈，再谈架构。

## 37. 场景设计题

### 37.1.1 设计“订单创建后通知 5 个下游”。

- 核心结论：Outbox 写一条事件，按业务线 Stream 分发；5 个下游用 5 个 Stream/消费组。
- 核心原理
  - 消费组不是广播。
- 关键机制
  - 每个下游独立 Stream，或上游 fan-out 到多个 Stream。
- 面试要点
  - 不要用一个消费组给 5 个下游。

### 37.1.2 消息要求严格顺序怎么办？

- 核心结论：按业务键路由到同一 Stream/串行消费，或业务状态机容忍乱序。
- 核心原理
  - 多 worker 并发会乱序。
- 关键机制
  - 单 key 单消费者/分区串行。
- 面试要点
  - 顺序和吞吐要取舍。

### 37.1.3 消息要求不重复怎么办？

- 核心结论：只能做业务幂等，不能保证网络层不重复。
- 核心原理
  - 至少一次投递。
- 关键机制
  - 唯一约束 + 状态机。
- 面试要点
  - 不要说 exactly-once。

### 37.1.4 延迟消息怎么做？

- 核心结论：当前 Stream 不支持延迟投递；需要延迟队列/定时表/时间轮。
- 核心原理
  - Stream 是即时传输。
- 关键机制
  - 定时表扫描后再 XADD。
- 面试要点
  - 不要硬说 Stream 能做延迟消息。

## 33. 对账系统设计（消息）

### 33.1.1 消息对账对什么？

- 核心结论：生产消息状态、Stream entry、消费记录、业务结果四方对齐。
- 核心原理
  - `t_local_message`：INIT/SENT/DONE/DEAD。
  - `t_consume_record`：READY/PROCESSING/CONSUMED/DEAD。
  - Redis：entry 是否存在、PEL 是否 pending。
- 关键机制
  - 按 msgId/eventKey 对齐。
- 面试要点
  - 不是只看 Redis 有没有消息。

### 33.1.2 SENT 老消息怎么处理？

- 核心结论：查消费方是否 CONSUMED；已消费推进 DONE，未消费重放/告警。
- 核心原理
  - SENT 只代表 XADD 成功。
  - 消费结果在消费方表。
- 关键机制
  - `findForReconcile` 按创建时间捞 SENT。
  - `markDoneBatch` 推进 DONE。
- 面试要点
  - 当前有钩子，没有完整定时任务。

### 33.1.3 消费记录 CONSUMED 但生产还是 SENT 怎么办？

- 核心结论：直接推进 DONE，不能重发。
- 核心原理
  - 消费已成功。
  - 重发会造成重复。
- 关键机制
  - 对账修复动作：SENT → DONE。
- 面试要点
  - 先确认消费记录可信。

### 33.1.4 生产 SENT 但消费记录缺失怎么办？

- 核心结论：先查 Redis entry/PEL；能重放则重放，不能则告警/人工。
- 核心原理
  - 可能 Stream 被裁剪、消费者从未拉到、组被删。
- 关键机制
  - MySQL 正本重放 + 幂等。
- 面试要点
  - 不要直接改 DONE。

### 33.1.5 消费 DEAD 怎么处理？

- 核心结论：人工看失败原因，修复后重放；不能自动无限重试。
- 核心原理
  - 永久失败重试无意义。
- 关键机制
  - 死信表/状态 + 操作审计。
- 面试要点
  - 对账与死信管理要配合。

### 33.1.6 对账任务的频率和分片？

- 核心结论：5 分钟扫滞留，T+1 全量；按 bizCode/bizId 分片。
- 核心原理
  - 全量对账不能压垮在线库。
- 关键机制
  - 水位、分页、只读从库、限速。
- 面试要点
  - 对账任务也要限流。

### 33.1.7 当前仓库的对账缺口是什么？

- 核心结论：缺定时对账任务、差异表落地、自动修复和人工平台。
- 核心原理
  - 只有 `findForReconcile`/`markDoneBatch` 能力。
- 关键机制
  - 设计已写，任务未完整实现。
- 面试要点
  - 明确“已实现/设计/未实现”。
