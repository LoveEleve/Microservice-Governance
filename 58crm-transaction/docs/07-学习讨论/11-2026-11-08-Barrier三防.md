# 2026-11-08 Barrier 三防：空回滚、悬挂、幂等

> 关联文章：`07-2026-11-08-双RM-TCC逐段讲解.md`
> 场景：quota 成功、coupon 失败时，quota 被 Cancel，coupon 空回滚为 SUSPENDED。
> 目标：能解释 barrier 的四种状态，以及三种异常怎么被挡住。

## 1. 为什么需要 barrier

TCC 的三个动作不是一次调用：

```text
Try     TM 调 RM
Confirm TC 回调 RM，可能重试
Cancel  TC 回调 RM，可能重试
```

网络和进程都可能出问题：

```text
Cancel 先到，Try 还没来
Try 后到，Cancel 已经处理完
Confirm 重复回调
Cancel 重复回调
Try 重复调用
```

如果没有 barrier，RM 会重复执行业务，或者 Cancel 空跑、Try 又在 Cancel 后落资源。

barrier 就是 RM 本地的一张防重表：

```text
t_branch_barrier
  PRIMARY KEY (xid, branch_id)
  status: TRIED / CONFIRMED / CANCELLED / SUSPENDED
```

它不是业务状态，业务状态仍在 quota/coupon 自己的表里。

## 2. 四种 barrier 状态

```text
TRIED
  Try 已经执行，业务资源已预占。

CONFIRMED
  Confirm 已经成功，业务终态已写。

CANCELLED
  Cancel 已经成功，Try 的预占已释放。

SUSPENDED
  Cancel 先到，或 Try 失败后回滚，没有有效 Try。
  这是一个“防悬挂”标记。
```

对应关系：

```text
成功链路：
  TRIED -> CONFIRMED

失败链路（Try 成功的分支）：
  TRIED -> CANCELLED

失败链路（Try 失败的分支）：
  没有 barrier -> Cancel 插入 SUSPENDED
```

## 3. 空回滚：Cancel 先到

代码在 `TccParticipantService.cancel`：

```java
BarrierEntity barrier = barriers.findForUpdate(context.xid(), context.branchId());
if (barrier == null) {
    actionRegistry.require(context.actionName());
    try {
        barriers.insert(barrier(context, BarrierStatus.SUSPENDED));
        return TccPhaseResult.SUCCESS;
    } catch (DuplicateKeyException duplicate) {
        BarrierEntity winner = barriers.findForUpdate(context.xid(), context.branchId());
        if (winner == null) {
            throw duplicate;
        }
        return cancelExisting(winner, context);
    }
}
```

含义：

```text
Cancel 来了，但 barrier 没有
  -> Try 没来过，或者 Try 失败已回滚
  -> 不执行 cancelAction
  -> 插入 SUSPENDED
  -> 返回 SUCCESS
```

为什么返回成功：

```text
Cancel 的目标是“确保资源没有被占用”
没有 Try 就没有资源
所以空回滚是成功，不是失败
```

coupon 999 失败时：

```text
coupon Try 返回 FAILURE
  -> barrier 插入事务回滚
  -> 数据库没有 coupon barrier
  -> TC Cancel 到达
  -> 空回滚插入 SUSPENDED
```

## 4. 悬挂：Try 后到

代码在 `TccParticipantService.handleExistingTry`：

```java
private TccTryResult handleExistingTry(
        BarrierEntity barrier, BusinessActionContext context) {
    assertSameAction(barrier, context);
    return switch (parse(barrier.getStatus())) {
        case TRIED, CONFIRMED -> TccTryResult.SUCCESS;
        case CANCELLED, SUSPENDED -> TccTryResult.FAILURE;
    };
}
```

含义：

```text
Try 来了，但 barrier 已经是 CANCELLED/SUSPENDED
  -> 说明 Cancel 先处理过
  -> 直接返回 FAILURE
  -> 不执行业务 tryAction
```

如果没有这个检查，就会发生悬挂：

```text
1. Cancel 先到，资源释放
2. Try 后到，重新预占
3. 事务已经 CANCELLED，但资源被 Try 占了
```

所以 `SUSPENDED` 不是“失败状态”，而是“以后 Try 来了要拒绝”的标记。

## 5. 幂等：重复 Try / Confirm / Cancel

### 重复 Try

```java
case TRIED, CONFIRMED -> TccTryResult.SUCCESS;
```

```text
Try 已经成功过
  -> 直接返回 SUCCESS
  -> 不重复预占
```

### 重复 Confirm

```java
if (status == BarrierStatus.CONFIRMED) {
    return TccPhaseResult.SUCCESS;
}
```

```text
Confirm 已经成功
  -> 直接返回 SUCCESS
  -> 不重复扣减、不重复写 Outbox
```

### 重复 Cancel

```java
if (status == CANCELLED || status == SUSPENDED) {
    return TccPhaseResult.SUCCESS;
}
```

```text
Cancel 已经成功过
  -> 直接返回 SUCCESS
  -> 不重复释放
```

### 冲突状态

```text
Confirm 遇到 CANCELLED/SUSPENDED -> 报错
Cancel 遇到 CONFIRMED -> 报错
```

因为事务已经走向另一条终态，不能反向覆盖。

## 6. Confirm 与 Outbox 为什么必须同事务

`TccParticipantService.confirm` 是 `@Transactional`：

```java
@Transactional
public TccPhaseResult confirm(BusinessActionContext context) {
    BarrierEntity barrier = barriers.findForUpdate(context.xid(), context.branchId());
    ...
    TccPhaseResult result = action.confirmAction(context);
    if (result != TccPhaseResult.SUCCESS) {
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        return result;
    }
    barriers.markConfirmed(context.xid(), context.branchId(), now());
    return TccPhaseResult.SUCCESS;
}
```

`QuotaTccAction.confirmAction` 里：

```java
if (quotaMapper.confirm(userId) != 1) {
    return TccPhaseResult.PERMANENT_FAILURE;
}
outboxPublisher.publish(new BusinessEvent(...));
return TccPhaseResult.SUCCESS;
```

三件事在同一个本地事务：

```text
quota 业务表：reserved -> assigned
barrier：TRIED -> CONFIRMED
Outbox：插入待发消息
```

如果任何一步失败：

```text
整个本地事务回滚
barrier 不会变成 CONFIRMED
TC 重试 Confirm
```

不能写成：

```text
先提交业务表
再另开线程发消息
```

否则业务成功但消息可能丢。

## 7. 用 coupon 999 走一遍

```text
1. quota Try 成功
   barrier quota=TRIED
   reserved=1

2. coupon Try 失败
   coupon barrier 插入回滚
   数据库没有 coupon barrier
   report TRY_FAIL

3. rollback
   Cancel quota：
     barrier TRIED -> CANCELLED
     reserved 1 -> 0
   Cancel coupon：
     barrier 不存在
     插入 SUSPENDED
     coupon cancelAction 不执行

4. 最终
   quota barrier=CANCELLED
   coupon barrier=SUSPENDED
   global=CANCELLED
```

## 8. 三个实验

```text
实验 1：空回滚
  手动先调 Cancel，再调 Try
  预期：Cancel 插入 SUSPENDED；Try 返回 FAILURE

实验 2：重复 Confirm
  对同一个 xid/branchId 连调两次 Confirm
  预期：第二次直接 SUCCESS，不重复扣减

实验 3：重复 Cancel
  对同一个 xid/branchId 连调两次 Cancel
  预期：第二次直接 SUCCESS，不重复释放
```

## 10. 一句话

> **barrier 的三防不是三个开关，而是同一张状态表上的三个判断：
> 没有 Try 的 Cancel 记 SUSPENDED，SUSPENDED 拒绝迟到的 Try，重复的 Try/Confirm/Cancel 按状态幂等返回。**
