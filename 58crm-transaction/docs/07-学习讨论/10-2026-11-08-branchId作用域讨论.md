# 2026-11-08 branchId 作用域讨论

> 问题：`branchId = global.branch_seq + 1`，xid=1 时 branchId=1，xid=2 时 branchId 又从 1 开始。
> 结论：不是主键冲突，`branchId` 的作用域是 xid；但字段名和日志展示容易误导，需要明确。

## 1. 当前规则

```text
xid       全局事务号，全局唯一
branchId  分支号，只在当前 xid 内唯一
```

表结构：

```sql
t_tcc_branch
  PRIMARY KEY (xid, branch_id)
  UNIQUE KEY (xid, resource_key)

t_branch_barrier
  PRIMARY KEY (xid, branch_id)
```

所以下面两行是两个不同的分支：

```text
(xid=1, branchId=1)  quota:1
(xid=2, branchId=1)  quota:1
```

不冲突，因为完整主键是 `(xid, branchId)`。

## 2. 为什么容易觉得怪

因为字段名 `branchId` 看起来像全局 ID：

```text
xid=1 branchId=1
xid=2 branchId=1   <- 数字重复
```

如果日志只打：

```text
branchId=1
```

就会歧义。

正确日志应该始终带 xid：

```text
xid=1 branchId=1
xid=2 branchId=1
```

## 3. 当前设计是否错误

正确性上不是错误：

```text
TC callback 请求同时带 xid + branchId
Repository 查询按 xid + branchId
t_tcc_branch 主键是 (xid, branch_id)
barrier 主键也是 (xid, branch_id)
```

所以不存在“branchId=1 被另一笔事务覆盖”的问题。

问题在：

```text
1. 命名像全局 ID
2. 日志/监控容易只打 branchId
3. 对外返回 TccBranchResult 时只看 branchId 不够，必须同时看 xid
```

## 4. 两个可选方案

### 方案 A：保留 xid 内自增，修正命名和展示（推荐）

```text
branchId 继续只在 xid 内唯一
日志统一打印 xid:branchId
文档明确 branchId 作用域
需要时增加 branchKey = xid + ":" + branchId
```

优点：

```text
不改 schema
不增加发号器
分支号紧凑
```

缺点：

```text
字段名仍然容易误解
```

### 方案 B：branchId 全局唯一

```text
每次 registerBranch 从独立号段发号
t_tcc_branch 仍然可以保留 (xid, branch_id) 主键
但 branch_id 全局不重复
```

优点：

```text
日志/排障更直观
branchId 可单独作为全局标识
```

缺点：

```text
多一次发号
号段成为热点
schema/API 语义变化
```

## 5. 建议

```text
短期：方案 A
  保留 per-xid branchId
  日志、文档、TccBranchResult 都带 xid
  对外展示用 xid:branchId

长期：如果确实需要全局 branchId，再评估方案 B
  不要为了“看起来不重复”直接改主键
```

## 6. 当前实现需要补的文档点

```text
TccContext.branchId() 只在当前 xid 内有意义
TccBranchResult.branchId() 必须和 xid 一起看
gRPC callback 必须同时传 xid 和 branchId
日志禁止只打 branchId
```

## 7. 一句话

> **branchId 不是全局分支 ID，而是“当前 xid 内的第几个分支”；
> 真正的分支标识是 `(xid, branchId)`，不是单独的 branchId。**
