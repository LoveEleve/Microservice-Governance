# 2026-11-08 分支注册职责讨论：TM register 还是 RM self-register

> 关联文章：`07-2026-11-08-双RM-TCC逐段讲解.md`
> 结论：当前实现是“TM 替 RM 注册分支”，能跑通，但不是标准 TCC 形态；目标应改为“RM 在 Try 入口自注册”。

## 1. 当前实现

代码路径：

```text
LeadAssignService.assign
  -> QuotaBranchGateway 代理
  -> TccBranchAspect.around
       -> TccAnnotationTransaction.registerBranch
       -> gRPC registerBranch 到 TC
       -> TC 写 t_tcc_branch
       -> TccContext.bindBranch(xid, branchId)
  -> QuotaBranchGateway.reserve
       -> OpenFeign 调 quota /tcc/try
```

关键点：

```text
TM 的 @TccBranch 负责：
  actionName
  resourceKey
  callbackEndpoint
  applicationData
  registerBranch

RM 的 /tcc/try 只负责：
  barrier TRIED
  执行业务 Try
```

所以当前分支注册的发起者是 TM，不是 RM。

## 2. 为什么怪

因为 `actionName`、`resourceKey`、`callbackEndpoint` 本质上属于 RM：

```text
actionName       RM 的 TccAction 名称
resourceKey      RM 的资源唯一键
callbackEndpoint RM 的 gRPC 地址
```

现在却写在 TM 的 `@TccBranch` 上：

```java
@TccBranch(
        actionName = "reserveQuota",
        resourceKey = "quota:#{#userId}",
        callbackEndpoint = "${quota.callback-endpoint}",
        applicationData = "#{#userId}")
```

后果：

```text
1. TM 知道了 RM 的部署地址
2. TM 和 RM 的 actionName 要人工保持一致
3. 新增一个 RM 要同时改 TM 和 RM
4. callbackEndpoint 无法由 RM 自己治理
```

这就是之前记录的“TM 配置 RM callbackEndpoint”问题的根因。

## 3. 目标形态：TM 只调 Try，RM 自己 register

目标时序：

```text
TM
  begin(xid)
  -> OpenFeign Try(xid, payload)
       -> RM participant
            registerBranch(xid, actionName, resourceKey,
                           callbackEndpoint=本机, applicationData=payload)
            branchId
            barrier TRIED
            执行业务 tryAction
            report TRY_SUCCESS/TRY_FAIL
            return TryResponse(success, branchId)
  -> 所有 Try 成功? commit : rollback
```

职责重新划分：

```text
TM：
  只负责 begin 和调用 Try
  不写 actionName/resourceKey/callbackEndpoint
  只传 xid + 业务 payload

RM：
  知道自己的 actionName/resourceKey/callbackEndpoint
  在 Try 入口向 TC 注册分支
  写 barrier、执行 Try、上报结果

TC：
  接收 RM 注册的分支
  Commit/Cancel 时从 branch 行读 RM endpoint
```

## 4. 这样改需要动什么

```text
1. RM participant 增加 BranchRegistrar
   通过 gRPC 调 TC registerBranch

2. RM 的 Try 入口先注册分支
   branchId 由 TC 分配
   再写 barrier 和执行业务 Try

3. TM 的 Feign 请求只带 xid + 业务 payload
   或者通过 header 传 xid

4. TM 的 @TccBranch 不再负责 register
   甚至可以移除；只在 TM 侧保留 @TccTransactional

5. callbackEndpoint 由 RM 配置/注册中心提供
   TM 不再感知
```

## 5. 需要讨论的难点

### 5.1 TM 怎么知道分支失败

RM 的 Try 响应必须明确返回：

```text
success = false
actionName/resourceKey
message
```

TM 外层 `@TccTransactional` 收到失败后 rollback。

### 5.2 RM 注册和 barrier 不在同一个事务

```text
registerBranch 是 TC 的远程事务
barrier + 业务 Try 是 RM 本地事务
不能做成一个本地事务
```

可能顺序：

```text
1. RM registerBranch 成功
2. RM 本地事务：插 barrier TRIED + 执行 tryAction
3. 本地提交
4. RM report TRY_SUCCESS/TRY_FAIL
5. 返回 TM
```

如果第 2 步失败：

```text
branch 已存在但 barrier 没有
TM rollback -> TC Cancel
RM 空回滚 -> SUSPENDED
```

如果 report 丢失：

```text
branch 仍是 TRYING
TC 超时后 Cancel
RM barrier TRIED -> cancelAction
```

### 5.3 TM 还要不要 @TccBranch

两种方案：

```text
A. 删掉 TM 的 @TccBranch
   TM 直接调 Feign，RM 自己注册
   最干净，但 TM 侧没有分支声明

B. 保留 @TccBranch 作为“本地分支标记”
   只负责上下文/响应映射，不负责 register
   兼容现有代码，但概念仍有重叠
```

倾向 A 或 B 需要再定。

## 6. 为什么当前先这么做

当前实现选择了“TM 先注册，再调 RM”：

```text
优点：
  RM 的 Try 接口可以保持普通 HTTP
  RM 不需要依赖 TC 客户端
  分支注册时机确定，在 Try 之前

缺点：
  TM 耦合 RM 元数据
  callbackEndpoint 泄漏到 TM
  actionName 两边手工对齐
```

这是实现权宜，不是最终架构。

## 8. 一句话

> **TCC 的分支注册职责应该在 RM：RM 最清楚自己的 actionName、resourceKey 和 callback 地址；TM 只应该负责 begin 和调用 Try。**
