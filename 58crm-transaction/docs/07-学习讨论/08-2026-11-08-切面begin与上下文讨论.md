# 2026-11-08 切面 begin、嵌套事务与 TccContext 讨论

> 关联文章：`07-2026-11-08-双RM-TCC逐段讲解.md`
> 主题：进入 `@TccTransactional` 方法体之前发生了什么，以及由此引出的三个边界问题。
> 结论：当前实现可用，但有三处明确边界，后续需要产品或框架级决策。

## 1. 嵌套 TCC 与“TM 同时是 RM”

### 代码

```java
public TccAnnotationTransaction begin(TccTransactionOptions options) {
    if (current.get() != null) {
        throw new IllegalStateException("nested TCC transaction is not supported");
    }
    TccBeginResult result = coordinator.begin(new TccBeginRequest(
            options.requestId(),
            options.bizCode(),
            options.bizId(),
            timeoutSeconds(options)));
    ...
}
```

### 结论

```text
同一线程里不能再开第二个全局 TCC 事务。
```

例如：

```java
@TccTransactional(...)
public void outer() {
    innerService.inner();   // inner() 也有 @TccTransactional
}
```

`outer` 已经 begin，ThreadLocal 里有当前事务；`inner` 再 begin 会直接抛异常。

### TM 同时是 RM 有问题吗？

不直接冲突。

```text
TM 路径：
  @TccTransactional
  -> TccTransactionManager.begin
  -> ThreadLocal current

RM 路径：
  /tcc/try
  -> TccParticipantService.tryAction
  -> 不经过 TccTransactionManager

  gRPC Confirm/Cancel
  -> TccParticipantService.confirm/cancel
  -> 也不经过 TccTransactionManager
```

所以一个服务可以同时是 TM 和 RM：

```text
它的普通业务方法用 @TccTransactional 发起全局事务
它的 RM 方法实现 TccAction
两条路径不共用同一个“当前事务”检查
```

真正不支持的是：

```text
@TccTransactional 方法里同步调用另一个 @TccTransactional 方法
RM 的 tryAction 里再开一个新的全局 TCC 事务
```

### 待决策

```text
嵌套全局 TCC 是否需要支持？
  A. 继续禁止，文档写清楚
  B. 支持挂起/恢复（类似 REQUIRES_NEW）
  C. 外层加入内层，合并成一个全局事务
```

当前选 A。

## 2. TccContext 的 branchId 被覆盖

### 代码

```java
public static void bindTransaction(long xid) {
    CURRENT.set(new TccContext(xid, 0));
}

public static void bindBranch(long xid, long branchId) {
    CURRENT.set(new TccContext(xid, branchId));
}
```

`TccBranchAspect` 在分支方法结束后：

```java
finally {
    TccContext.bindTransaction(transaction.xid());
}
```

### 时序

```text
assign 开始
  TccContext = (xid=1, branchId=0)

quota reserve
  bindBranch(1, 1)
  TccContext = (1, 1)
  quota Try 使用 (1, 1)
  finally bindTransaction(1)
  TccContext = (1, 0)

coupon lock
  bindBranch(1, 2)
  TccContext = (1, 2)
  coupon Try 使用 (1, 2)
  finally bindTransaction(1)
  TccContext = (1, 0)
```

### 第一个 branchId 会丢吗？

ThreadLocal 里会被覆盖，但数据没有丢：

```text
t_tcc_branch 保存：
  xid=1, branchId=1, resourceKey=quota:1
  xid=1, branchId=2, resourceKey=coupon:1

TccAnnotationTransaction 保存分支列表
最终 TccResult.branches() 返回
```

Confirm/Cancel 也不依赖 `TccContext`：

```text
TC 从 t_tcc_branch 读 branchId
  -> gRPC 请求带 branchId
  -> RM 按 branchId 找 barrier
```

### 当前语义

```text
TccContext = 当前正在执行的分支上下文
不是“整个事务所有分支的集合”
```

限制：

```text
分支必须串行调用
不能并行调两个 @TccBranch
不能把 TccContext 带到异步线程
```

### 待决策

如果以后要并行分支：

```text
A. 把 TccContext 作为方法参数显式传入
B. 用栈保存多个分支上下文
C. 用可继承/可传播的上下文（InheritableThreadLocal / TaskDecorator）
D. 明确不支持并行，保持单线程串行
```

当前选 D。

## 3. begin 失败没有自动重试

### 代码

```java
public TccBeginResult begin(TccBeginRequest request) {
    ManagedChannel channel = channel();
    try {
        var response = stub(channel).begin(...);
        ...
    } finally {
        channel.shutdownNow();
    }
}
```

`CoordinatorGrpcClient.begin` 只调一次，没有重试；`TccTransactionManager.begin` 也没有重试。

### 失败路径

```text
情况 A：请求没到 TC
  -> 数据库没有 t_tcc_global
  -> 用同一个 requestId 重试，安全

情况 B：TC 插入成功，但响应丢给 TM
  -> t_tcc_global 留下 TRYING
  -> TM 认为 begin 失败，assign 不执行
  -> 这个 global 会被 timeout 收敛
  -> 用同一个 requestId 重试，如果还在 TRYING，会拿到同一个 xid
```

### 现状

```text
begin        没有自动重试
commit       服务端 Scheduler 会重试
cancel       服务端 Scheduler 会重试
```

### 为什么可以安全重试

```text
t_tcc_global.request_id 有唯一键
Begin 对同一个 requestId 是幂等的
```

### 待决策

```text
A. 保持不重试，由调用方/HTTP 层重试
B. 在 TccTransactionManager 加有限次重试 + 退避
C. 只对网络/超时/TCC_NOT_READY 重试
D. 重试耗尽后抛明确异常，交给上游处理
```

推荐 B + C，但需要补测试：

```text
TC 插入后响应丢失 -> 重试拿回同一个 xid
TC 已 CONFIRMED -> 重试明确失败，不重复执行业务
TC 未插入 -> 重试重新 begin
```

## 4. 和 callbackEndpoint 问题的关系

这几个问题都属于“注解接入看起来简单，但边界没有完全收干净”：

```text
TM 配置 RM callbackEndpoint      -> TM 知道了 RM 部署细节
@EnableAspectJAutoProxy 藏在 starter -> 代理入口不直观
嵌套全局 TCC 不支持               -> TM 兼 RM 时需明确限制
TccContext 只有当前分支           -> 并行分支/异步传递不支持
begin 不自动重试                  -> 网络失败要靠上游或人工兜底
```

## 5. 一句话

> **当前注解 TCC 的核心链路是闭环的，但这些边界必须在文档和后续版本中明确：
> 不支持嵌套全局事务、TccContext 只表示当前分支、begin 没有自动重试。**
