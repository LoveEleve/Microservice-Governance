# 双 RM TCC 逐段讲解

> 日期：2026-11-08
> 场景：Lead 分配线索，同时操作 quota（额度）和 coupon（优惠券）两个 RM。
> 读法：一段一段看，每段末尾有“自测问题”；有问题直接按段号提问。
>
> 配套时序图：`docs/02-设计/19-TCC时序与状态图.md`
> - A 正常成功（双 RM + TC）
> - B Try 失败（quota 成功、coupon 失败、quota Cancel）

## 0. 先看全链路

成功：

```text
LeadController
  -> LeadAssignService（TM）
  -> quota Try 成功（RM1）
  -> coupon Try 成功（RM2）
  -> report TRY_SUCCESS x2
  -> commit
  -> TC Confirm quota/coupon
  -> CONFIRMED
```

失败：

```text
LeadController
  -> LeadAssignService（TM）
  -> quota Try 成功（RM1）
  -> coupon Try 失败（RM2）
  -> report TRY_FAIL
  -> rollback
  -> TC Cancel quota（释放预占）
  -> coupon 空回滚 SUSPENDED
  -> CANCELLED
```

先记住三个角色：

```text
TM = Lead，发起全局事务，调用 Try，决定 commit/rollback
RM = quota/coupon，实现 Try/Confirm/Cancel
TC = Coordinator，记录状态，回调 Confirm/Cancel
```

Lead 只做 TM，不是 RM；Confirm/Cancel 不在 Lead 里。

# 第 1 段：LeadController

文件：

```text
crm-tx-tcc-examples/lead/src/main/java/com/wuba/crm/tx/tcc/example/lead/LeadController.java
```

代码：

```java
@RestController
public class LeadController {

    private final LeadAssignService service;

    public LeadController(LeadAssignService service) {
        this.service = service;
    }

    @PostMapping("/leads/{leadId}/assign")
    public AssignResult assign(
            @PathVariable("leadId") long leadId,
            @RequestParam("userId") long userId,
            @RequestParam("couponId") long couponId) {
        String requestId = "lead-" + leadId + "-" + userId + "-" + couponId
                + "-" + UUID.randomUUID();
        TccResult result = service.assign(
                new AssignLeadCommand(requestId, leadId, userId, couponId));
        return new AssignResult(result.xid(), result.status().name());
    }
}
```

逐行解释：

```text
@RestController
  Lead 对外提供 HTTP 接口，不参与 TCC 协议。

leadId / userId / couponId
  业务参数：
    leadId   线索
    userId   配额归属人
    couponId 优惠券

requestId
  业务幂等键。
  同一个业务请求重试必须复用同一个 requestId。
  示例里拼 UUID 是为了“每次点击算一次新分配”；
  生产应该用 commandId/订单号，而不是每次生成 UUID。

service.assign(...)
  调用的是 Spring 代理对象。
  只有走代理，@TccTransactional 才会生效。

TccResult
  框架返回的全局事务结果，包含 xid 和最终状态。

AssignResult
  只是把结果转成 HTTP 响应，没有 TCC 逻辑。
```

这一段在链路中的位置：

```text
HTTP 入口
  -> 生成/接收业务幂等键
  -> 调 TM 业务方法
```

# 第 2 段：LeadAssignService（TM 入口）

文件：

```text
crm-tx-tcc-examples/lead/src/main/java/com/wuba/crm/tx/tcc/example/lead/LeadAssignService.java
```

代码：

```java
@Service
public class LeadAssignService {

    private final QuotaBranchGateway quotaGateway;
    private final CouponBranchGateway couponGateway;

    public LeadAssignService(
            QuotaBranchGateway quotaGateway,
            CouponBranchGateway couponGateway) {
        this.quotaGateway = quotaGateway;
        this.couponGateway = couponGateway;
    }

    @TccTransactional(
            requestId = "#{#command.requestId}",
            bizCode = "lead",
            bizId = "#{#command.leadId}",
            tryTimeoutSeconds = 30)
    public TccResult assign(AssignLeadCommand command) {
        quotaGateway.reserve(command.userId());
        couponGateway.lock(command.couponId());
        return null;
    }
}
```

逐行解释：

```text
@Service
  Spring Bean，会被 AOP 代理。

构造器注入两个 Gateway
  注意注入的是代理对象，不是 new 出来的普通对象。
  这样 @TccBranch 才能拦截。

@TccTransactional
  标记全局事务入口。

requestId = "#{#command.requestId}"
  从 command 里取业务幂等键。
  #{...} 是表达式边界，内部的 #command 才是 SpEL 变量。

bizCode = "lead"
  业务域，用于查询、日志、排障。

bizId = "#{#command.leadId}"
  业务单号，用于定位“这笔 TCC 是哪条线索”。

tryTimeoutSeconds = 30
  Try 阶段超时时间。
  不是 Confirm/Cancel 的超时。

quotaGateway.reserve(...)
  第一个分支，RM1。

couponGateway.lock(...)
  第二个分支，RM2。
  顺序很重要：quota 先成功，coupon 后失败，才能演示撤销已成功分支。

return null
  业务方法不自己构造 TccResult。
  切面在 commit 后统一返回 TccResult。
```

切面在背后做的事：

```text
进入 assign 前：
  TccTransactionalAspect 调 manager.begin
  Coordinator 创建 xid
  TccContext 绑定 xid

执行 assign：
  quota Try
  coupon Try

正常返回：
  transaction.commit
  返回 TccResult(xid, CONFIRMED, 分支列表)

分支失败：
  transaction.rollback
  返回 TccResult(xid, CANCELLED, 分支列表)
```

为什么 Lead 里看不到 Confirm/Cancel：

```text
Lead 是 TM，只负责发起和决定提交/回滚。
Confirm/Cancel 是 RM 在第二阶段执行的业务动作。
```

自测问题：

1. `tryTimeoutSeconds` 超时后，TC 会做什么？
2. 为什么业务方法返回 `null`，调用方还能拿到 `TccResult`？

# 第 3 段：QuotaBranchGateway（第一个分支）

文件：

```text
crm-tx-tcc-examples/lead/src/main/java/com/wuba/crm/tx/tcc/example/lead/QuotaBranchGateway.java
```

代码：

```java
@Service
public class QuotaBranchGateway {

    private final QuotaFeignClient quotaClient;

    public QuotaBranchGateway(QuotaFeignClient quotaClient) {
        this.quotaClient = quotaClient;
    }

    @TccBranch(
            actionName = "reserveQuota",
            resourceKey = "quota:#{#userId}",
            callbackEndpoint = "${quota.callback-endpoint}",
            applicationData = "#{#userId}")
    public TccTryResult reserve(long userId) {
        TccContext context = TccContext.current();
        TryQuotaResponse response = quotaClient.tryQuota(new TryQuotaRequest(
                context.xid(),
                context.branchId(),
                "reserveQuota",
                "{\"userId\":" + userId + "}"));
        return response.success() ? TccTryResult.SUCCESS : TccTryResult.FAILURE;
    }
}
```

四个注解字段：

```text
actionName = "reserveQuota"
  RM 端用哪个 TccAction 处理。
  quota 服务里对应 @TccActionHandler("reserveQuota")。

resourceKey = "quota:#{#userId}"
  分支幂等键。
  同一个全局事务内必须唯一；重复会直接失败。
  quota:1 和 quota:2 是两个分支。

callbackEndpoint = "${quota.callback-endpoint}"
  TC 回调 quota Confirm/Cancel 的 gRPC 地址。
  不是 Feign 地址，也不是 Nacos 服务名。
  这里从配置读取，默认 127.0.0.1:9092。

applicationData = "#{#userId}"
  RM 在 Confirm/Cancel 时需要的业务数据。
  它会被存到 t_tcc_branch.application_data。
  quota 的 Confirm 需要 userId，所以这里放 userId。
```

方法体：

```text
TccContext.current()
  取当前线程的 xid 和 branchId。
  这是 @TccBranch 切面在方法执行前绑定的。

quotaClient.tryQuota(...)
  通过 OpenFeign 调 quota-service 的通用 /tcc/try。
  请求里带 xid/branchId/actionName/applicationData。

response.success()
  true  -> 返回 TccTryResult.SUCCESS
  false -> 返回 TccTryResult.FAILURE
```

切面在方法前后做的事：

```text
方法前：
  从当前 TCC 事务拿 xid
  registerBranch
  分配 branchId，例如 1
  TccContext 绑定 xid + branchId

方法后：
  成功 -> report TRY_SUCCESS
  失败 -> report TRY_FAIL，并抛 TccBranchFailedException

finally：
  把 TccContext 恢复成全局事务上下文（xid）
```

为什么 `@TccBranch` 要写在独立 Bean 上：

```text
Spring AOP 靠代理拦截。
如果 LeadAssignService 内部自己调用自己的 @TccBranch 方法，
绕过了代理，注解不会生效。
```

自测问题：

1. `resourceKey` 为什么不能用 `"quota"` 一个固定值？
2. `callbackEndpoint` 是谁在用？Feign 还是 TC？

# 第 4 段：CouponBranchGateway（第二个分支）

文件：


代码：

```java
@Service
public class CouponBranchGateway {

    private final CouponFeignClient couponClient;

    public CouponBranchGateway(CouponFeignClient couponClient) {
        this.couponClient = couponClient;
    }

    @TccBranch(
            actionName = "lockCoupon",
            resourceKey = "coupon:#{#couponId}",
            callbackEndpoint = "${coupon.callback-endpoint}",
            applicationData = "#{#couponId}")
    public TccTryResult lock(long couponId) {
        TccContext context = TccContext.current();
        TryCouponResponse response = couponClient.tryCoupon(new TryCouponRequest(
                context.xid(),
                context.branchId(),
                "lockCoupon",
                "{\"couponId\":" + couponId + "}"));
        return response.success() ? TccTryResult.SUCCESS : TccTryResult.FAILURE;
    }
}
```

和 quota 分支同构，只是换了资源：

```text
resourceKey = coupon:1
actionName  = lockCoupon
callback    = coupon 的 gRPC 9093
```

执行顺序：

```text
quota Try 成功
coupon Try 失败
```

这时 quota 已经预占成功，必须由 TC 回头 Cancel。  
这就是 TCC 最核心的“撤销已成功分支”场景。

1. 为什么两个分支要用不同的 `actionName`？

# 第 5 段：QuotaTccAction（RM1 的三个阶段）

文件：

```text
crm-tx-tcc-examples/quota/src/main/java/com/wuba/crm/tx/tcc/example/quota/QuotaTccAction.java
```

代码：

```java
@TccActionHandler("reserveQuota")
public class QuotaTccAction implements TccAction {

    private final QuotaMapper quotaMapper;
    private final OutboxPublisher outboxPublisher;

    @Override
    public TccTryResult tryAction(BusinessActionContext context) {
        return quotaMapper.reserve(userId(context)) == 1
                ? TccTryResult.SUCCESS : TccTryResult.FAILURE;
    }

    @Override
    public TccPhaseResult confirmAction(BusinessActionContext context) {
        long userId = userId(context);
        if (quotaMapper.confirm(userId) != 1) {
            return TccPhaseResult.PERMANENT_FAILURE;
        }
        outboxPublisher.publish(new BusinessEvent(
                "quota-confirmed:" + context.xid() + ":" + context.branchId(),
                "quota",
                String.valueOf(userId),
                "QUOTA_CONFIRMED",
                "{\"userId\":" + userId + "}"));
        return TccPhaseResult.SUCCESS;
    }

    @Override
    public TccPhaseResult cancelAction(BusinessActionContext context) {
        return quotaMapper.cancel(userId(context)) == 1
                ? TccPhaseResult.SUCCESS : TccPhaseResult.PERMANENT_FAILURE;
    }
}
```

`@TccActionHandler("reserveQuota")`：

```text
把这个 Bean 注册成 actionName=reserveQuota 的 RM 动作。
TC 回调时根据 actionName 找到它。
```

`tryAction`：

```text
只预占：reserved + 1
不写最终状态
返回 SUCCESS/FAILURE
```

`confirmAction`：

```text
正式扣减：reserved - 1，assigned + 1
同一事务写 Outbox
返回 SUCCESS 或 PERMANENT_FAILURE
```

`cancelAction`：

```text
释放预占：reserved - 1
其他分支失败时由 TC 回调
```

为什么 Confirm 要写 Outbox：

```text
业务终态（assigned+1）和消息（QUOTA_CONFIRMED）
必须在同一个本地事务里。
否则会出现“业务成功但消息没发”或“消息发了但业务没成功”。
```

自测问题：

1. `tryAction` 为什么不能直接写 `assigned + 1`？
2. `confirmAction` 执行两次会怎样？barrier 起什么作用？

```java
public class CouponTccAction implements TccAction {

    @Override

        return couponMapper.lock(couponId(context)) == 1

    }

    @Override

        long couponId = couponId(context);
        if (couponMapper.confirm(couponId) != 1) {
            return TccPhaseResult.PERMANENT_FAILURE;
        }
        outboxPublisher.publish(new BusinessEvent(

    }

    @Override
    public TccPhaseResult cancelAction(BusinessActionContext context) {
        return couponMapper.cancel(couponId(context)) == 1
                ? TccPhaseResult.SUCCESS : TccPhaseResult.PERMANENT_FAILURE;
    }
}
```

优惠券状态机：

```text
AVAILABLE --Try--> LOCKED --Confirm--> USED
                    |
                    +--Cancel--> AVAILABLE
```

失败例子 `couponId=999`：

```text
999 已经是 USED
lock 更新 0 行
tryAction 返回 FAILURE
barrier 事务回滚（数据库里没有 coupon 的 TRIED）
```

所以：

```text
coupon 不会执行 confirmAction
coupon 也不会执行 cancelAction
TC 的 Cancel 到达时，participant 发现没有 barrier
插入 SUSPENDED
```

1. 为什么 coupon 999 失败后，barrier 是 `SUSPENDED` 而不是 `CANCELLED`？
2. `SUSPENDED` 如何防止迟到的 Try？

# 第 7 段：Participant 怎么执行 Confirm/Cancel

文件：

```text
crm-tx-tcc-participant/src/main/java/com/wuba/crm/tx/tcc/participant/barrier/TccParticipantService.java
crm-tx-tcc-participant/src/main/java/com/wuba/crm/tx/tcc/participant/grpc/TccParticipantCallbackGrpcService.java
```

调用链：

```text
TC
  -> gRPC TccParticipantCallbackGrpcService
  -> TccParticipantService.confirm/cancel
  -> 按 actionName 找 QuotaTccAction/CouponTccAction
  -> 调 confirmAction/cancelAction
  -> 同一本地事务更新 barrier
```

Confirm 的核心逻辑：

```java
@Transactional
public TccPhaseResult confirm(BusinessActionContext context) {
    BarrierEntity barrier = barriers.findForUpdate(context.xid(), context.branchId());
    if (barrier == null) {
        throw new TccException(TccResultCode.TCC_INVALID_STATE, "barrier not found");
    }

    BarrierStatus status = parse(barrier.getStatus());
    if (status == BarrierStatus.CONFIRMED) {
        return TccPhaseResult.SUCCESS;   // 幂等
    }
    if (status == BarrierStatus.CANCELLED || status == BarrierStatus.SUSPENDED) {
        throw new TccException(TccResultCode.TCC_INVALID_STATE, "barrier already " + status);
    }

    TccPhaseResult result = action.confirmAction(context);
    if (result != TccPhaseResult.SUCCESS) {
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        return result;
    }

    barriers.markConfirmed(context.xid(), context.branchId(), now());
    return TccPhaseResult.SUCCESS;
}
```

Cancel 的核心逻辑：

```java
@Transactional
public TccPhaseResult cancel(BusinessActionContext context) {
    BarrierEntity barrier = barriers.findForUpdate(context.xid(), context.branchId());
    if (barrier == null) {
        // 空回滚：Try 没来过或 Try 失败已回滚
        barriers.insert(barrier(context, BarrierStatus.SUSPENDED));
        return TccPhaseResult.SUCCESS;
    }

    if (status == CANCELLED || status == SUSPENDED) {
        return TccPhaseResult.SUCCESS;   // 幂等
    }
    if (status == CONFIRMED) {
        throw new TccException(...);     // Confirm 后不能 Cancel
    }

    TccPhaseResult result = action.cancelAction(context);
    if (result != SUCCESS) {
        setRollbackOnly();
        return result;
    }

    barriers.markCancelled(...);
    return TccPhaseResult.SUCCESS;
}
```

关键点：

```text
Confirm/Cancel 的业务动作和 barrier 更新在同一个本地事务里。
barrier 是 RM 本地表，不是 TC 的表。
```

1. Confirm 重复回调时，为什么直接返回 SUCCESS？
2. 空回滚为什么插入 `SUSPENDED`，而不是直接返回成功？

# 第 8 段：完整失败链路，带状态

请求：

```http
POST /leads/1001/assign?userId=1&couponId=999
```

执行：

```text
1. begin
   t_tcc_global: xid=2, TRYING

2. quota 分支
   register: branchId=1
   quota Try: reserved 1
   barrier: TRIED
   report: TRY_SUCCESS

3. coupon 分支
   register: branchId=2
   coupon Try: 更新 0 行，返回 FAILURE
   barrier 事务回滚：没有 coupon TRIED
   report: TRY_FAIL

4. 外层 rollback
   t_tcc_global: CANCELLING

5. Cancel quota
   barrier TRIED -> CANCELLED
   quota cancelAction: reserved 1 -> 0
   t_tcc_branch quota -> CANCELLED

6. Cancel coupon
   没有 barrier
   插入 barrier=SUSPENDED
   t_tcc_branch coupon -> CANCELLED

7. t_tcc_global: CANCELLED
   返回 TccResult(CANCELLED)
```

这就是真实 E2E 的结果：

```text
xid=2 CANCELLED
quota reserved=0，assigned 未增加
coupon 999 仍是 USED
quota barrier=CANCELLED
coupon barrier=SUSPENDED
```

# 第 9 段：三个最容易混的点

```text
1. TM 不是 RM
   Lead 只发起事务，不实现 TccAction。
   quota/coupon 才实现 Try/Confirm/Cancel。

2. Try 和 Confirm/Cancel 的调用方不同
   Try：TM 通过 OpenFeign 调 RM，是业务 API。
   Confirm/Cancel：TC 通过 gRPC 调 RM，是 TCC 协议。

3. barrier 状态不是业务状态
   TRIED/CONFIRMED/CANCELLED/SUSPENDED 是 RM 防重/防悬挂的本地状态。
   quota 的 reserved/assigned、coupon 的 LOCKED/USED 才是业务状态。
```
