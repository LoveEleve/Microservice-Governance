# Redis Stream 原理与使用

> 读完你能做什么：看懂 Stream 的 entry、consumer group、PEL、XACK、XPENDING、XCLAIM，并能判断我们的 Outbox 为什么这样用。  
> 本文关键命令已在本机 Redis 7.0.15 上实际验证。

## 1. 先看一个具体例子

业务事件：

```text
线索 lead-1 分配给销售 1001
```

写入 Stream：

```bash
XADD tx:stream:lead * \
  msgId m-1 \
  bizCode lead \
  bizId lead-1 \
  eventType LEAD_ASSIGNED \
  payload '{"salesId":1001}'
```

返回：

```text
1793967010576-0
```

`1793967010576-0` 就是这条 entry 的 Stream ID。

创建消费组：

```bash
XGROUP CREATE tx:stream:lead tx-group-lead 0
```

消费者读取：

```bash
XREADGROUP GROUP tx-group-lead consumer-1 \
  COUNT 1 \
  STREAMS tx:stream:lead '>'
```

返回：

```text
tx:stream:lead
1793967010576-0
msgId
m-1
bizCode
lead
...
```

此时消息：

```text
已投递给 consumer-1
但还没 ACK
→ 在 PEL 里
```

确认：

```bash
XACK tx:stream:lead tx-group-lead 1793967010576-0
```

返回：

```text
1
```

PEL 清空。

## 1.1 先看全景图

```text
                    XADD
业务事件 ──────────────────────┐
                                ▼
                     ┌──────────────────────┐
                     │ Redis Stream         │
                     │ tx:stream:lead       │
                     │                      │
                     │  ID          entry   │
                     │  ...-0       m-1     │
                     │  ...-1       m-2     │
                     │  ...-2       m-3     │
                     └──────────┬───────────┘
                                │
                     consumer group 读取
                                │
                                ▼
                 ┌────────────────────────────┐
                 │ Group: tx-group-lead       │
                 │ last-delivered-id = ...-1  │
                 │                            │
                 │ PEL                        │
                 │  ...-0 -> consumer-1       │
                 │  ...-1 -> consumer-2       │
                 └──────────┬─────────────────┘
                            │
                 ┌──────────┴──────────┐
                 ▼                     ▼
           consumer-1             consumer-2
           XACK ...-0             XACK ...-1
                 │                     │
                 └──────────┬──────────┘
                            ▼
                      PEL 删除对应项
                      Stream entry 还在
```

三个关键点：

```text
Stream entry：消息本体
Group cursor：消费组投递到哪
PEL：投递了但还没 XACK 的消息
```

## 2. Stream 到底是什么

可以把它理解成：

```text
一个只追加的日志
每条消息有唯一 ID
消费者组记录“读到哪”
PEL 记录“读了但没确认”
```

和 List 最大的区别：

| 能力 | Redis List | Redis Stream |
|---|---|---|
| 一条消息多个消费者竞争 | 是 | 是 |
| 消费组 | 无 | 有 |
| offset / last-delivered-id | 无 | 有 |
| 未确认消息 | 无 | PEL |
| 重投/认领 | 自己做 | XPENDING/XCLAIM |
| 读取后消息是否消失 | 是 | 否 |
| 历史回溯 | 困难 | 可以按 ID |

Stream entry 不会因为 `XREADGROUP` 被删除。  
它还在 Stream 里，只是消费组记住了投递位置，PEL 记住了未确认项。

## 3. Stream ID

格式：

```text
<millisecondsTime>-<sequenceNumber>
```

例子：

```text
1793967010576-0
```

特殊 ID：

```text
*   让 Redis 自动生成
$   当前最后一条消息之后
>   消费组里的新消息
0   从最早开始
-   最小 ID
+   最大 ID
```

`XADD ... *` 表示自动生成 ID。

## 4. 消费组

```text
Stream: tx:stream:lead
Group:  tx-group-lead
```

消费组保存：

```text
last-delivered-id   最后投递到哪
entries-read        已读多少条
lag                 还有多少条没投递
pel-count           多少条已投递未 ACK
consumers           组内消费者
```

查看：

```bash
XINFO GROUPS tx:stream:lead
```

典型输出：

```text
name              tx-group-lead
consumers         1
pending           1
last-delivered-id 1793967010576-0
entries-read      1
lag               0
```

含义：

```text
pending=1
  有一条已投递未 ACK

last-delivered-id
  组已经投递到哪

entries-read
  已读条数

lag
  还有多少条没投递
```

## 4.1 消费组和 PEL 的关系图

```text
                       Stream
     ┌──────┬──────┬──────┬──────┐
     │ m-1  │ m-2  │ m-3  │ m-4  │
     └──┬───┴──┬───┴──────┴──────┘
        │      │
        │      │ last-delivered-id = m-3
        │      │
        │      └─────────────┐
        │                    ▼
        │             consumer-2
        │             PEL: m-2, m-3
        ▼
   consumer-1
   PEL: m-1

XACK m-1
  → consumer-1 PEL 删除 m-1
  → Stream 里 m-1 仍然存在
  → last-delivered-id 不变
```

PEL 是**每个消费组各自维护**的，不是全 Stream 只有一份。

## 5. XREAD 和 XREADGROUP

### 普通读取

```bash
XREAD COUNT 10 STREAMS tx:stream:lead 0
```

`0` 表示从最早开始读。

特点：

```text
不改变消费组位置
不产生 PEL
适合查看/调试
```

### 消费组读取

```bash
XREADGROUP GROUP tx-group-lead consumer-1 \
  COUNT 500 BLOCK 1000 \
  STREAMS tx:stream:lead '>'
```

`>` 表示：

```text
只读这个消费组还没投递过的新消息
```

读完后：

```text
消息进入 consumer-1 的 PEL
last-delivered-id 前进
```

读取自己的 pending：

```bash
XREADGROUP GROUP tx-group-lead consumer-1 \
  COUNT 100 STREAMS tx:stream:lead 0
```

`0` 表示：

```text
读取当前 consumer 自己的 pending
```

注意：

```text
> 读新消息
0 读自己的 pending
XPENDING 看所有 pending
```

选择图：

```text
我要读什么？
│
├── 消费组还没投递过的新消息
│      └── XREADGROUP ... STREAMS key >
│
├── 当前 consumer 自己的 pending
│      └── XREADGROUP ... STREAMS key 0
│
└── 这个组全部 pending
       └── XPENDING key group
```

## 6. PEL 是什么

PEL = Pending Entries List。

```text
消息已经投递给某个 consumer
但还没有 XACK
```

PEL 记录：

```text
entry ID
consumer
最后投递时间
投递次数
```

查看摘要：

```bash
XPENDING tx:stream:lead tx-group-lead
```

输出：

```text
1
1793967010576-0
1793967010576-0
consumer-1
1
```

含义：

```text
1 条 pending
最小 ID
最大 ID
哪个 consumer
投递次数
```

查看详情：

```bash
XPENDING tx:stream:lead tx-group-lead - + 10
```

## 7. XACK

```bash
XACK tx:stream:lead tx-group-lead 1793967010576-0
```

作用：

```text
从 PEL 移除
不删除 Stream entry
```

所以：

```text
XACK 成功 ≠ 消息被删除
```

Stream entry 仍然存在，直到 `XTRIM` / `XDEL`。

```text
XREADGROUP
   └── entry 进入 PEL
          │
          ├── XACK
          │     └── 从 PEL 移除，entry 保留
          │
          └── 不 ACK
                └── 一直 pending
```

## 8. 消费者崩溃

假设：

```text
consumer-1 XREADGROUP 拿到 m-2
处理中崩溃
没有 XACK
```

消息：

```text
在 PEL
consumer-1 名下
```

恢复方式：

```bash
XPENDING tx:stream:lead tx-group-lead - + 10
```

看到：

```text
1793967024471-0
consumer-1
idle=...
delivery-count=1
```

### XCLAIM

```bash
XCLAIM tx:stream:lead tx-group-lead consumer-2 60000 1793967024471-0
```

含义：

```text
把 idle 超过 60 秒的 entry 转给 consumer-2
```

### XAUTOCLAIM

Redis 6.2+：

```bash
XAUTOCLAIM tx:stream:lead tx-group-lead consumer-2 60000 0-0 COUNT 100
```

含义：

```text
自动扫描 idle > 60s 的 pending
转给 consumer-2
```

它会返回：

```text
next-start-id
claimed entries
deleted ids
```

`next-start-id` 是下一次继续扫描的游标，不能只调用一次就认为扫完了。

Redis 7 基线用 `XAUTOCLAIM`；Redis 5 用 `XPENDING + XCLAIM`。

## 8.1 崩溃恢复时序

```text
consumer-1                 Redis Stream / PEL              consumer-2
    │                              │                           │
    │ XREADGROUP >                 │                           │
    │─────────────────────────────>│                           │
    │                              │ PEL: entry -> consumer-1  │
    │ 进程崩溃                      │                           │
    │                              │                           │
    │                              │  XPENDING 发现 idle       │
    │                              │──────────────────────────>│
    │                              │                           │
    │                              │  XCLAIM/XAUTOCLAIM        │
    │                              │<──────────────────────────│
    │                              │ PEL: entry -> consumer-2  │
    │                              │                           │
    │                              │  XACK entry               │
    │                              │<──────────────────────────│
    │                              │ PEL 删除                  │
```

## 9. 消费组不是广播

一个 Stream 可以有很多消费组：

```text
stream: tx:stream:lead
group A: search-index
group B: data-warehouse
```

但这不是我们当前模型。

我们的模型：

```text
一个业务线一个 Stream
一个业务线一个消费组
组内多个 consumer 竞争
不做多下游 fan-out
```

同一事件需要多个下游时，上游拆成多条事件，不是复制给多个组。

## 10. 项目里的完整链路

生产方：

```text
业务表 + t_local_message(INIT) COMMIT
→ Scanner 扫 INIT
→ Buffer
→ Sender XADD
→ t_local_message(SENT)
```

消费方：

```text
XREADGROUP
→ t_consume_record(PROCESSING)
→ 业务处理
→ 本地事务提交
→ t_consume_record(CONSUMED)
→ XACK
```

崩溃：

```text
未 XACK
→ PEL
→ XPENDING
→ XAUTOCLAIM
→ 新 consumer 重试
```

关键边界：

```text
SENT 表示已写入 Stream
SENT 是生产方终态
生产方不扫描 SENT 重投
消费失败由 PEL/XCLAIM 处理
重复由 msgId + bizKey 幂等
```

项目链路图：

```text
┌──────────────┐
│ 业务 MySQL    │
│ 业务表        │
│ t_local_message│
└──────┬───────┘
       │ 同事务
       ▼
┌──────────────┐     ┌──────────────┐     ┌──────────────────┐
│ OutboxScanner│────>│ OutboxBuffer │────>│ OutboxSender     │
└──────────────┘     └──────────────┘     │ 拦截器/路由/序列化 │
                                            └────────┬─────────┘
                                                     │ XADD pipeline
                                                     ▼
                                            ┌──────────────────┐
                                            │ Redis Stream     │
                                            │ tx:stream:{biz}  │
                                            └────────┬─────────┘
                                                     │ XREADGROUP
                                                     ▼
                                            ┌──────────────────┐
                                            │ StreamConsumer   │
                                            │ t_consume_record │
                                            └────────┬─────────┘
                                                     │ 业务提交后 XACK
                                                     ▼
                                            ┌──────────────────┐
                                            │ Redis PEL        │
                                            │ pending/claim    │
                                            └──────────────────┘
```

## 11. Java 使用方式

Spring Data Redis 的核心 API：

```java
String stream = "tx:stream:lead";
String group = "tx-group-lead";
String consumer = "consumer-1";

Map<String, String> fields = new LinkedHashMap<>();
fields.put("msgId", "m-1");
fields.put("bizId", "lead-1");
fields.put("eventType", "LEAD_ASSIGNED");
fields.put("payload", "{\"salesId\":1001}");

redis.opsForStream().add(
    StreamRecords.string(fields).withStreamKey(stream));

redis.opsForStream().createGroup(
    stream, ReadOffset.from("0"), group);
```

读取：

```java
List<MapRecord<String, Object, Object>> records =
    redis.opsForStream().read(
        Consumer.from(group, consumer),
        StreamReadRequest.builder(
                StreamOffset.create(stream, ReadOffset.lastConsumed()))
            .count(500)
            .autoAcknowledge(false)
            .build());
```

确认：

```java
redis.opsForStream().acknowledge(stream, group, recordId);
```

注意：

```text
autoAcknowledge(false)
  读取后进入 PEL，不会自动 ACK
```

              ┌────────┐

## 13. 常见坑

### 坑 1：建组用 `$`

```bash
XGROUP CREATE tx:stream:lead tx-group-lead $
```

表示从当前最后一条之后开始。  
创建组之前写入的消息不会被这个组消费。

需要处理历史消息时用：

```bash
XGROUP CREATE tx:stream:lead tx-group-lead 0
```

### 坑 2：以为 Stream 读取后删除

不会。

```text
XREADGROUP 只推进组位置
XACK 只清 PEL
entry 仍在 Stream
```

### 坑 3：XACK 写错 ID

XACK 的参数是 Stream entry ID，不是业务 `msgId`。

```text
msgId 是业务消息 ID
entry ID 是 Redis Stream ID
```

### 坑 4：先 ACK 后提交业务

错误：

```text
XACK
→ 业务事务回滚
→ 消息没了，业务没做
```

正确：

```text
业务本地事务提交
→ 再 XACK
```

ACK 失败会导致重复消费，靠幂等兜底；不能反过来。

### 坑 5：XTRIM 删掉 pending

XTRIM 和 XDEL 都只看 Stream entry，不看 PEL。

`XTRIM` 可能删除还没 ACK 的 entry。

如果删了：

```text
PEL 里还有 ID
Stream 里没有正文
```

所以：

```text
未 ACK 的 pending 不能被 trim
trim 策略必须和 PEL 监控一起设计
```

### 坑 6：没有幂等

Stream 是至少一次投递，不是 exactly-once。

```text
XCLAIM/XAUTOCLAIM
进程 kill
ACK 丢失
```

都会导致重复。

必须：

```text
msgId 幂等
bizKey 幂等
```

### 坑 7：Redis 持久化边界

Stream 不是绝对持久化：

```text
Redis 主从异步复制
主节点故障切换可能丢未同步 entry
```

所以 MySQL 仍是正本；Redis 丢失后必须有重建/重放路径。

### 坑 8：Redis 版本不匹配

```text
XAUTOCLAIM: Redis 6.2+
Redis 5: XPENDING + XCLAIM
```

### 坑 9：一个 Stream 做广播

消费组是竞争消费，不是每个组自动复制。  
需要多下游就拆事件或显式多组，后者会带来 fan-out 成本。

## 14. 运维看什么

```text
XPENDING 数量
单条 pending idle 时间
delivery-count
group lag
Stream 长度
Redis 内存
XADD 失败率
consumer 数量
```

告警优先级：

```text
PEL 长时间不降
lag 持续上涨
XAUTOCLAIM 频繁
Stream 内存接近上限
```
