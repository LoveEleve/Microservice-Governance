# Redis Stream 命令大全

> 独立命令手册，不改已有文章。  
> 基线：Redis 7.0.15。命令按学习顺序排列，先学读和写，再学消费组和 PEL。

## 0. 学习顺序

```text
Level 1 基础读写
  XADD
  XLEN
  XRANGE
  XREVRANGE
  XREAD

Level 2 消费组
  XGROUP CREATE
  XREADGROUP
  XACK
  XINFO GROUPS

Level 3 pending 恢复
  XPENDING
  XCLAIM
  XAUTOCLAIM

Level 4 清理和运维
  XTRIM
  XDEL
  XINFO STREAM / CONSUMERS
  MEMORY USAGE
  CLUSTER KEYSLOT
```

建议每学一个命令都记录：

```text
它改变什么
它不改变什么
失败时会怎样
生产环境能不能用
```

## 1. XADD：写一条消息

语法：

```text
XADD key [NOMKSTREAM]
     [MAXLEN | MINID [= | ~] threshold [LIMIT count]]
     <* | id>
     field value [field value ...]
```

最常用：

```bash
XADD tx:stream:lead * \
  msgId m-1 \
  bizId lead-1 \
  eventType LEAD_ASSIGNED \
  payload '{"salesId":1001}'
```

返回：

```text
1793968239949-0
```

返回值是 Stream entry ID，不是业务 `msgId`。

### 1.1 自动生成 ID

```text
*  → Redis 生成 <毫秒时间>-<序号>
```

### 1.2 指定 ID

```bash
XADD tx:stream:lead 1000-0 msgId m-1
```

生产环境一般不要手工指定，除非做迁移/重放。

### 1.3 不自动建 Stream

```bash
XADD tx:stream:lead NOMKSTREAM * msgId m-1
```

Stream 不存在时返回 nil，不创建。

### 1.4 限制长度

```bash
XADD tx:stream:lead MAXLEN ~ 100000 * msgId m-1
```

`~` 是近似裁剪，性能好，但可能多留一些。

`=` 是精确裁剪：

```bash
XADD tx:stream:lead MAXLEN = 100000 * msgId m-1
```

危险点：

```text
MAXLEN 可能裁掉还没 ACK 的 pending
```

如果使用裁剪，必须和 `XPENDING` 监控一起设计；有未 ACK 的消息时不要激进裁剪。

### 1.5 按最小 ID 裁剪

```bash
XADD tx:stream:lead MINID ~ 1790000000000-0 * msgId m-1
```

含义：

```text
删除 ID 小于阈值的 entry
```

## 2. XLEN：条目数量

```bash
XLEN tx:stream:lead
```

返回：

```text
3
```

注意：

```text
XLEN 是 Stream entry 数量
不是 PEL 数量
不是消费组未读数
```

---

## 3. XRANGE / XREVRANGE：按范围读

正序：

```bash
XRANGE tx:stream:lead - + COUNT 2
```

倒序：

```bash
XREVRANGE tx:stream:lead + - COUNT 1
```

ID 范围：

```text
-        最小
+        最大
( ID     排除该 ID
```

例子：

```bash
XRANGE tx:stream:lead 1793968239949-0 1793968239949-2
```

用途：

```text
排查某段时间的消息
按 ID 回溯
不是消费组读取
```

---

## 4. XREAD：不创建 PEL 的读取

语法：

```text
XREAD [COUNT count] [BLOCK milliseconds]
      STREAMS key [key ...] id [id ...]
```

从最早读：

```bash
XREAD COUNT 10 STREAMS tx:stream:lead 0
```

只读新消息：

```bash
XREAD COUNT 10 BLOCK 1000 STREAMS tx:stream:lead '$'
```

`$` 的含义：

```text
调用这一刻之后的新消息
```

注意：

```text
XREAD 不进入消费组
不产生 PEL
不会 XACK
适合查看/调试/普通日志消费
```

`BLOCK 0` 表示永久阻塞，生产代码不要随便用，必须能中断。

---

## 5. XGROUP CREATE：创建消费组

语法：

```text
XGROUP CREATE key group <id | $> [MKSTREAM] [ENTRIESREAD entries-read]
```

从最早开始：

```bash
XGROUP CREATE tx:stream:lead tx-group-lead 0
```

从当前最后一条之后开始：

```bash
XGROUP CREATE tx:stream:lead tx-group-lead '$'
```

Stream 不存在时同时创建：

```bash
XGROUP CREATE tx:stream:lead tx-group-lead 0 MKSTREAM
```

### 关键区别

```text
0  → 组从最早消息开始消费
$  → 组从当前最后一条之后开始，历史消息不投递
```

如果先写消息，再建组：

```text
用 $：旧消息不会被这个组消费
用 0：旧消息会补投
```

### 幂等

重复创建同名组通常返回：

```text
BUSYGROUP Consumer Group name already exists
```

代码里要把它视为“已存在”，不是致命错误。

---

## 6. XREADGROUP：消费组读取

语法：

```text
XREADGROUP GROUP group consumer
           [COUNT count] [BLOCK milliseconds] [NOACK]
           STREAMS key [key ...] id [id ...]
```

读新消息：

```bash
XREADGROUP GROUP tx-group-lead consumer-1 \
  COUNT 500 BLOCK 1000 \
  STREAMS tx:stream:lead '>'
```

`>`：

```text
只读该组还没投递过的新消息
```

读自己的 pending：

```bash
XREADGROUP GROUP tx-group-lead consumer-1 \
  COUNT 100 \
  STREAMS tx:stream:lead 0
```

`0`：

```text
读取当前 consumer 自己的 pending
```

### 读完后发生什么

```text
消息进入当前 consumer 的 PEL
last-delivered-id 前进
消息还没有 ACK
Stream entry 仍然存在
```

### NOACK

```bash
XREADGROUP GROUP g c NOACK STREAMS key '>'
```

含义：

```text
读完直接当作已确认
不进入 PEL
```

生产可靠性场景不要用。  
一旦进程崩溃，消息既不在 PEL，也没有 ACK 记录。

---

## 7. XACK：确认消费

语法：

```text
XACK key group id [id ...]
```

例子：

```bash
XACK tx:stream:lead tx-group-lead 1793968239949-0
```

批量：

```bash
XACK tx:stream:lead tx-group-lead \
  1793968239949-0 \
  1793968239949-1
```

返回：

```text
2
```

作用：

```text
从 PEL 删除
不删除 Stream entry
```

正确顺序：

```text
业务事务提交成功
→ XACK
```

不能：

```text
XACK
→ 业务事务回滚
```

---

## 8. XPENDING：查看未确认消息

### 8.1 摘要

```bash
XPENDING tx:stream:lead tx-group-lead
```

输出字段：

```text
pending 数量
最小 ID
最大 ID
consumer 列表
每个 consumer 的 pending 数
```

### 8.2 明细

```bash
XPENDING tx:stream:lead tx-group-lead - + 10
```

每行：

```text
entry ID
consumer
idle 毫秒
delivery count
```

### 8.3 按 idle 过滤

```bash
XPENDING tx:stream:lead tx-group-lead IDLE 60000 - + 100
```

含义：

```text
只看 idle 超过 60 秒的 pending
```

用途：

```text
找出长时间没 ACK 的消息
决定是否 XCLAIM
```

---

## 9. XCLAIM：认领 pending

语法：

```text
XCLAIM key group consumer min-idle-time
        id [id ...]
        [IDLE ms] [TIME unix-time-ms]
        [RETRYCOUNT count]
        [FORCE] [JUSTID] [LASTID lastid]
```

例子：

```bash
XCLAIM tx:stream:lead tx-group-lead consumer-2 \
  60000 \
  1793968239949-0
```

含义：

```text
idle 超过 60 秒的 entry
从原 consumer 转给 consumer-2
delivery count 增加
```

### JUSTID

```bash
XCLAIM ... JUSTID 1793968239949-0
```

只返回 ID，不增加 delivery count。

### FORCE

```text
即使 entry 不在 PEL，也创建 pending
```

迁移/修复时用，普通消费不要用。

### RETRYCOUNT

显式设置投递次数，谨慎使用。

---

## 10. XAUTOCLAIM：自动扫描 pending

Redis 6.2+：

```text
XAUTOCLAIM key group consumer min-idle-time start
            [COUNT count] [JUSTID]
```

例子：

```bash
XAUTOCLAIM tx:stream:lead tx-group-lead consumer-2 \
  60000 0-0 COUNT 100
```

返回三部分：

```text
next-start-id
claimed entries
deleted ids
```

重要：

```text
next-start-id 是下一次扫描游标
```

循环：

```text
start = 0-0
do:
  result = XAUTOCLAIM ... start
  start = result.next-start-id
while start != 0-0
```

不能只调用一次就假设所有 pending 都扫完了。

Redis 5 没有 `XAUTOCLAIM`：

```text
XPENDING + XCLAIM
```

## 11. XINFO：查看 Stream / 组 / 消费者

### Stream

```bash
XINFO STREAM tx:stream:lead
```

关注：

```text
length
last-generated-id
first-entry
last-entry
```

完整信息：

```bash
XINFO STREAM tx:stream:lead FULL COUNT 10
```

`FULL` 会带组/PEL 等信息，数据大时谨慎用。

### 消费组

```bash
XINFO GROUPS tx:stream:lead
```

关注：

```text
name
consumers
pending
last-delivered-id
entries-read
lag
```

### 消费者

```bash
XINFO CONSUMERS tx:stream:lead tx-group-lead
```

关注：

```text
name
pending
idle
```

## 12. XGROUP 其他命令

### 创建消费者

```bash
XGROUP CREATECONSUMER tx:stream:lead tx-group-lead consumer-1
```

返回：

```text
1 创建成功
0 已存在
```

### 删除消费者

```bash
XGROUP DELCONSUMER tx:stream:lead tx-group-lead consumer-1
```

返回该消费者名下 pending 数。

注意：

```text
删除消费者不等于 ACK 它的 pending
pending 可能变成无主
```

### 修改组游标

```bash
XGROUP SETID tx:stream:lead tx-group-lead 0
```

用于重置/回放，破坏性操作，必须审批。

### 删除组

```bash
XGROUP DESTROY tx:stream:lead tx-group-lead
```

删除组、消费者、PEL 元数据。不可逆。

---

## 13. XTRIM：裁剪 Stream

语法：

```text
XTRIM key MAXLEN | MINID [= | ~] threshold [LIMIT count]
```

按长度：

```bash
XTRIM tx:stream:lead MAXLEN ~ 100000
```

按最小 ID：

```bash
XTRIM tx:stream:lead MINID ~ 1790000000000-0
```

危险：

```text
XTRIM 不看 PEL
可能删掉还没 ACK 的 entry
```

所以：

```text
有 pending 时不要激进 trim
trim 前先看 XPENDING
```

---

## 14. XDEL：删除指定 entry

```bash
XDEL tx:stream:lead 1793968239949-0
```

注意：

```text
删除 entry 不会自动清 PEL
PEL 里可能留下没有正文的 ID
```

必须先确认该 ID 已 ACK 或明确要丢弃。

---

## 15. XSETID：修改最后 ID（高级）

```text
XSETID key last-id [ENTRIESADDED entries-added] [MAXDELETEDID max-deleted-id]
```

用于迁移、修复、恢复。  
不是日常消费命令，生产操作必须审批。

---

## 16. 运维辅助命令

```bash
XLEN tx:stream:lead
MEMORY USAGE tx:stream:lead
CLUSTER KEYSLOT tx:stream:lead
```

`CLUSTER KEYSLOT` 用来确认 key 落在哪个 slot。

Redis Cluster 注意：

```text
同一个 Stream 的所有操作都在同一个 key
多 key 的 XREAD/XREADGROUP 可能 CROSSSLOT
```

---

## 17. 危险命令清单

```text
XGROUP DESTROY
  删除组和 PEL 元数据

XGROUP SETID
  改变消费起点，可能重复消费

XTRIM / XDEL
  可能删除未 ACK 的 entry

XADD MAXLEN
  可能删除未 ACK 的 entry

XREADGROUP NOACK
  不进入 PEL，崩溃后无法恢复

XCLAIM FORCE
  给不存在的 pending 强行建记录

XSETID
  修改 Stream 游标/ID
```

---

## 18. 最小排障顺序

```text
1. XLEN                  有没有消息
2. XINFO GROUPS          组游标和 lag
3. XPENDING              有没有未 ACK
4. XPENDING - + 10       看 idle 和 delivery count
5. XINFO CONSUMERS       哪个消费者卡住
6. XAUTOCLAIM            转移 pending
7. XACK                  业务提交后确认
```
