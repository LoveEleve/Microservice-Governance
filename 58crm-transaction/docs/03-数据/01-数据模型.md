# 数据模型

> 读完你能做什么：知道每张表属于谁、主键/唯一键是什么、分片键是什么，以及为什么生产方和消费方不能共用一张状态表。

## 1. 数据归属

```text
生产方业务 MySQL：
  业务表
  t_local_message

消费方业务 MySQL：
  t_consume_record
  t_idempotent
  t_message_attempt

协调器 MySQL：
  t_tcc_global
  t_tcc_branch

参与方业务 MySQL：
  t_branch_barrier

对账库：
  t_recon_diff
```

关键原则：

```text
生产方不知道消费者是否处理成功
消费方不能远程写生产方数据库
消费租约只放消费方自己的库
```

## 2. 生产方：t_local_message

```text
msg_id            PK
event_key         UK
biz_code
biz_id            分片键
event_type
payload / payload_ref
status            INIT / SENT / CONSUMED / DEAD
retry_count       重投次数
next_retry_at     下次允许重投的时间
created_at
updated_at
```

字段含义：

| 字段 | 含义 |
|---|---|
| `msg_id` | 这条消息记录的唯一 ID |
| `event_key` | 业务事件唯一键，防重复发布 |
| `biz_code` | 业务编码，Redis List 路由键 |
| `biz_id` | 业务单号，消息表分片键 |
| `event_type` | 事件类型 |
| `payload` | 小消息正文 |
| `payload_ref` | 大消息对象存储地址 |
| `status` | 生产方投递状态 |
| `retry_count` | 生产方重投次数 |
| `next_retry_at` | 下次允许重投时间 |
| `created_at` | 创建时间 |
| `updated_at` | 最后更新时间 |

生产方状态：

```text
INIT      已写 MySQL，尚未投递 Redis
SENT      已投递 Redis，等待批量 ACK
CONSUMED  消费方已 ACK，生产方不再重投
DEAD      重投超限，等待人工处理
```

注意：

```text
这里没有 PROCESSING
这里没有 lease_until
这里没有 consumer_id
```

原因：

```text
消费者是另一个服务
它不能远程修改生产方的 t_local_message
```

## 3. 消费方：t_consume_record

```text
msg_id            PK
biz_id
consumer_id
status            PROCESSING / CONSUMED / DEAD
lease_until
retry_count
next_retry_at
payload / payload_ref
created_at
updated_at
```

字段含义：

| 字段 | 含义 |
|---|---|
| `msg_id` | 消费记录对应的消息 |
| `biz_id` | 业务单号；查消息、排障 |
| `consumer_id` | 哪个消费实例领取了消息 |
| `status` | 消费状态 |
| `lease_until` | 消费租约到期时间 |
| `retry_count` | 消费失败重试次数 |
| `next_retry_at` | 下次重试时间 |
| `payload` | 消费方保存的正文，支持本地重试 |
| `payload_ref` | 大消息引用 |

消费状态：

```text
PROCESSING   正在处理，租约有效
CONSUMED     业务处理成功
DEAD         重试超限，人工处理
```

流程：

```text
BLPOP
  → 写自己的 t_consume_record(PROCESSING, lease)
  → 业务处理
  → 更新自己的 t_consume_record(CONSUMED)
```

续约：

```text
消费者更新自己数据库的 lease_until
不请求生产方数据库
```

## 4. 消费方：t_idempotent

```text
msg_id     PK
biz_key    UK
status
created_at
```

用途：

```text
同一业务效果只执行一次
消费记录负责租约/重试
幂等表负责业务幂等
```

## 5. 消费方：t_message_attempt

```text
id          PK
msg_id
attempt_no
consumer_id
status
error_msg
created_at
UNIQUE(msg_id, attempt_no)
```

用途：

```text
记录每次消费尝试
用于排障和重试分析
不是多消费组账本
```

## 6. 队列信封

Redis List 里不能只放 `msgId`，否则消费者无法按 `biz_id` 路由到分片。

正确信封：

```text
bizId
msgId
eventKey
eventType
payload / payloadRef
```

说明：

```text
生产方 MySQL 是正本
Redis 里是传输副本
消费者拿到后写自己的 t_consume_record
消费者崩溃后可以从自己的消费记录重试
```

## 7. 生产方重投

生产方不等待消费 ACK，因此需要超时重投：

```text
INIT
  → 立即投递
  → SENT + next_retry_at = now + 30s

SENT 超时未 ACK
  → Relay 重新投递
  → retry_count + 1

超过上限
  → DEAD
```

重复投递由消费方 `msg_id + biz_key` 幂等处理。

消费成功后批量 ACK：

```text
consumer 100~500 条一批
→ 一次 ACK RPC
→ t_local_message SENT -> CONSUMED
```

## 8. 分片

```text
t_local_message：按 biz_id
t_consume_record：按 msg_id 或 biz_id
t_idempotent：按 msg_id
```

生产形态：

```text
16 库 × 4 表 = 64 分片
1 主 2 从
写主库，状态查询走从库
延迟 > 500ms 回主库
```

## 9. 索引原则

```text
t_local_message：
  uk_event_key(event_key)
  idx_status_retry(status, next_retry_at)
  idx_biz_event(biz_code, biz_id, event_type)

t_consume_record：
  pk_msg_id(msg_id)
  idx_status_lease(status, lease_until)

t_idempotent：
  pk_msg_id(msg_id)
  uk_biz_key(biz_key)
```

禁止：

```text
select * 带出 payload
无分片键全表扫描
生产方表存消费租约
消费方远程写生产方表
```

## 10. 后续 TCC 表

```text
t_tcc_global
  xid PK
  request_id UK
  biz_code/biz_id
  status
  timeout
  retry

t_tcc_branch
  xid + branch_id PK
  UNIQUE(xid, resource_key)
  status
  retry

t_branch_barrier
  xid + branch_id PK
  resource_type/resource_key
  action_name
  status
  version
  lease_until
```

TCC 的 `lease_until` 是协调器/参与方自己的租约，和消费租约不是同一个东西。
