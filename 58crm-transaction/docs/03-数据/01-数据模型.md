# 数据模型

> 读完你能做什么：知道每张表属于谁、主键/唯一键是什么、分片键是什么，以及 Stream/PEL 的状态放在哪里。

## 1. 数据归属

```text
生产方业务 MySQL：
  业务表
  t_local_message

消费方业务 MySQL：
  t_consume_record
  t_idempotent
  t_message_attempt

协调器 MySQL：
  t_tcc_global
  t_tcc_branch

参与方业务 MySQL：
  t_branch_barrier

对账库：
  t_recon_diff
```

## 2. 生产方：t_local_message

```text
msg_id            PK
event_key         UK
biz_code
biz_id            分片键
event_type
payload / payload_ref
status            INIT / SENT / DEAD
retry_count       XADD 重投次数
next_retry_at     下次允许重投的时间
created_at
updated_at
```

字段含义：

| 字段 | 含义 |
|---|---|
| `msg_id` | 消息正本 ID |
| `event_key` | 业务事件唯一键，防重复发布 |
| `biz_code` | 业务线，决定 Stream key |
| `biz_id` | 业务单号，消息表分片键 |
| `event_type` | 事件类型 |
| `payload` | 小消息正文 |
| `payload_ref` | 大消息对象存储地址 |
| `status` | 生产方投递状态 |
| `retry_count` | XADD 重投次数 |
| `next_retry_at` | 下次允许重投时间 |
| `created_at` | 创建时间 |
| `updated_at` | 最后更新时间 |

状态：

```text
INIT    已写 MySQL，尚未 XADD
SENT    已 XADD 到 Stream
DEAD    XADD/重投超限
```

生产方不存：

```text
CONSUMED
lease_until
consumer_id
```

## 3. 消费方：t_consume_record

```text
msg_id            PK
biz_id
stream_entry_id   Stream entry ID
consumer_id
status            PROCESSING / CONSUMED / DEAD
lease_until
retry_count
next_retry_at
payload / payload_ref
created_at
updated_at
```

用途：

```text
记录消费租约
支持本地重试
关联 Stream pending
崩溃恢复
```

## 4. 消费方：t_idempotent

```text
msg_id     PK
biz_key    UK
status
created_at
```

用途：

```text
同一业务效果只执行一次
```

## 5. 消费方：t_message_attempt

```text
id          PK
msg_id
attempt_no
consumer_id
status
error_msg
created_at
UNIQUE(msg_id, attempt_no)
```

用途：

```text
记录消费尝试
排障和重试分析
不是多消费组账本
```

## 6. Redis Stream 键

```text
stream: tx:stream:{bizCode}
group:  tx-group-{bizCode}
```

消息字段：

```text
msgId
eventKey
bizCode
bizId
eventType
payload / payloadRef
```

## 7. 生产方重投

```text
INIT
  → XADD
  → SENT + next_retry_at = now + 30s

SENT 超时
  → Relay 重新 XADD
  → retry_count + 1

超过上限
  → DEAD
```

注意：

```text
SENT 只表示已写入 Stream
SENT 不代表消费成功
消费成功由 XACK/PEL 维护
```

## 8. 分片

```text
t_local_message：按 biz_id
t_consume_record：按 msg_id 或 biz_id
t_idempotent：按 msg_id
```

生产形态：

```text
16 库 × 4 表 = 64 分片
1 主 2 从
写主库，状态查询走从库
延迟 > 500ms 回主库
```

## 9. 索引原则

```text
t_local_message：
  uk_event_key(event_key)
  idx_status_retry(status, next_retry_at)
  idx_biz_event(biz_code, biz_id, event_type)

t_consume_record：
  pk_msg_id(msg_id)
  idx_status_lease(status, lease_until)

t_idempotent：
  pk_msg_id(msg_id)
  uk_biz_key(biz_key)
```

禁止：

```text
select * 带出 payload
无分片键全表扫描
生产方表存消费租约
消费方远程写生产方表
trim 掉未 ACK 的 pending
```

## 10. 后续 TCC 表

```text
t_tcc_global
  xid PK
  request_id UK
  biz_code/biz_id
  status
  timeout
  retry

t_tcc_branch
  xid + branch_id PK
  UNIQUE(xid, resource_key)
  status
  retry

t_branch_barrier
  xid + branch_id PK
  resource_type/resource_key
  action_name
  status
  version
  lease_until
```

TCC 的 `lease_until` 是协调器/参与方自己的租约，和 Stream PEL 不是同一个东西。
