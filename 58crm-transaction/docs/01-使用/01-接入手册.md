# 使用手册：线索分配

> 读完你能做什么：给一个业务服务接入 TCC、发可靠事件、写下游消费者。
> 本文只讲“怎么用”，不讲框架实现。

## 1. 业务场景

```text
线索服务把一条线索分配给销售
同时扣减销售配额
成功后通知搜索/通知等下游
```

参与方：

```text
LeadService   线索服务
QuotaService  配额服务
NotifyService 下游消费者
```

## 2. 业务方只需要五样东西

```text
@TccParticipant
TccAction
TccTransactionTemplate
OutboxPublisher
@TxMessageListener
```

底层 `prepare/commit/cancel/query` 由 SDK 封装，业务方不直接调用。

## 3. 实现参与方

```java
@TccParticipant(
    resourceType = "lead",
    resourceKey = "lead:#{leadId}"
)
public class LeadTccAction implements TccAction {

    @Override
    public TryResult tryAction(BusinessActionContext ctx) {
        Long leadId = ctx.arg("leadId", Long.class);
        Long salesId = ctx.arg("salesId", Long.class);

        // 只预占：状态 ASSIGNING，记录目标销售
        // 不写最终 owner
        return TryResult.success();
    }

    @Override
    public ConfirmResult confirmAction(BusinessActionContext ctx) {
        // 最终落库：owner_id = salesId，状态 ASSIGNED
        // 同一本地事务写 Outbox：LEAD_ASSIGNED
        return ConfirmResult.success();
    }

    @Override
    public CancelResult cancelAction(BusinessActionContext ctx) {
        // 回到 NEW，清掉目标销售
        return CancelResult.success();
    }
}
```

配额服务同理：

```java
@TccParticipant(
    resourceType = "quota",
    resourceKey = "quota:#{salesId}"
)
public class QuotaTccAction implements TccAction {
    // Try 预占，Confirm 扣减，Cancel 释放
}
```

## 4. 发起 TCC

```java
TccResult result = tccTemplate.execute(
    TccRequest.builder()
        .bizCode("lead")
        .bizId(leadId)
        .requestId(requestId)
        .timeout(Duration.ofSeconds(30))
        .arg("leadId", leadId)
        .arg("salesId", salesId)
        .build(),
    ctx -> {
        leadBranch.tryAction(ctx);
        quotaBranch.tryAction(ctx);
    }
);
```

语义：

```text
execute 的回调是 Try 阶段
所有 Try 成功 → 协调器 Confirm
任意 Try 失败 → 协调器 Cancel 已成功分支
同一个 requestId 重试 → 返回同一个 xid
```

## 5. Confirm 后发事件

```java
outboxPublisher.publish(
    BusinessEvent.builder()
        .eventKey("lead-assigned:" + leadId + ":" + assignmentId)
        .bizCode("lead")
        .bizId(leadId)
        .eventType("LEAD_ASSIGNED")
        .payload(payload)
        .build()
);
```

必须在 Confirm 的同一个本地事务：

```text
业务表更新
+ barrier 更新
+ t_local_message 插入
COMMIT
```

不能：

```text
Try 阶段发 LEAD_ASSIGNED
Confirm 后另开线程直接发通知
事件只写 Redis
```

## 6. 写消费者

```java
@TxMessageListener(
    bizCode = "lead",
    eventType = "LEAD_ASSIGNED"
)
public class LeadAssignedConsumer
        implements MessageHandler<LeadAssignedEvent> {

    @Override
    public void handle(BusinessMessage<LeadAssignedEvent> message) {
        // 搜索索引 / 通知 / 业绩同步
        // 框架负责：幂等、重试、状态回写
    }
}
```

## 7. 业务方需要保证

```text
Try 只预占，不写最终结果
Confirm 写最终结果
Cancel 能撤销 Try
三个方法都幂等
resourceKey 稳定
eventKey 带 assignmentId/version
```

## 8. 业务方看到的结果

```text
正常：
  ASSIGNED
  配额扣减
  LEAD_ASSIGNED 最终送达

Try 失败：
  已成功分支被 Cancel
  线索回 NEW
  配额释放

Confirm 超时：
  协调器重试
  最终成功或人工处理

重复请求：
  requestId 返回同一个 xid
  不重复分配

消息重复：
  msgId 幂等拦截
```

## 9. 业务方不需要做

```text
不写协调器
不写状态机
不写 Redis BLPOP
不写消息表扫描
不写重试调度
不写幂等表
不关心分库分表
不关心消息路由
```

## 10. 配置

业务方只配：

```yaml
tx:
  app-name: lead-service
  coordinator-url: http://tx-coordinator
  timeout: 30s
  retry:
    max-attempts: 5
  queue-prefix: tx:queue
```

平台侧负责：

```text
Nacos：注册/配置
Sentinel：8W 流控/熔断
ShardingSphere：64 分片/读写分离
Redis Cluster：队列分片
Prometheus/Grafana：监控
```
