# C-001.2 Stream 发送端 Review

> 结论：结构方向对了，但当前版本不能进入 C-001.3。  
> 已知问题不是测试覆盖率，而是 Stream 语义和失败路径还不正确。

## P0 正确性

### 1. SENT 被当成“超时重投”候选

位置：

```text
MybatisLocalMessageRepository.findRelayCandidates
```

当前查询：

```text
INIT
或 SENT + next_retry_at <= now
```

问题：

```text
Stream XADD 成功后，消息已经进入 Stream
生产方没有 ACK 回执
再把 SENT 当候选重投
→ 每 30 秒重复 XADD 同一条消息
→ 消费方幂等能挡住业务
→ 但 Stream 里消息无限重复
```

Stream 模式下：

```text
SENT 应是生产方终态
findRelayCandidates 只查 INIT
```

如果 Redis 数据丢失，靠独立的重放任务从 MySQL 重建，不是扫描 SENT 无限重发。

### 2. XADD 失败没有 retry_count / DEAD

位置：

```text
OutboxSender.sendOnce
```

失败路径：

```text
publisher.publish 抛异常
→ 状态保持 INIT
→ 没有 retry_count + 1
→ 下一轮继续
→ DEAD 永远到不了
```

需要：

```text
失败 → INIT/SENT + retry_count + 1 + next_retry_at
超过上限 → DEAD
```

不能：

```text
失败后 10ms 立刻重试
```

### 3. serializer/partitioner 异常会泄漏 inFlight

位置：

```text
OutboxSender.sendOnce
```

当前：

```text
interceptors.onSend 有异常隔离
但 serializer.serialize / partitioner.route 在 try 外
```

如果序列化或路由抛异常：

```text
异常抛出 sendOnce
→ finally 没执行
→ inFlight 不移除
→ 消息永久卡在内存集合
→ 扫描线程永远跳过
```

必须把：

```text
interceptor
partitioner
serializer
publisher
markSent
```

全部放进 try/finally，统一释放 inFlight。

### 4. 文档状态机与代码冲突

文档仍写：

```text
SENT 超时重投
retry_count + 1
```

但 Stream 模式下：

```text
SENT 已 XADD，不能靠超时重投
消费确认由 PEL/XACK 维护
```

文档必须改成：

```text
INIT --XADD成功--> SENT（终态）
INIT --XADD失败--> INIT + retry/backoff
超限 -> DEAD
```

## P1 性能/结构

### 5. linger 没有真正形成窗口

当前：

```text
buffer.poll(linger)
→ 有第一条立即 drain
```

这不是 Kafka linger 语义。

Kafka：

```text
第一条进入 batch 后
再等 linger 时间或 batch 满
```

当前会：

```text
第一批很小就发送
高 QPS 下仍产生更多小 batch
```

需要：

```text
取到第一条后等待 linger
期间继续 drain
或者用时间轮/延迟队列
```

### 6. Buffer 是全局队列，不是按 bizCode 分桶

当前：

```text
ArrayBlockingQueue<OutboxRecord>
```

后果：

```text
一个业务线积压会占满整个 buffer
其它业务线被饿死
无法按 List 独立背压
```

Kafka 是：

```text
按 partition 的 Deque
```

应改为：

```text
ConcurrentHashMap<bizCode, Deque>
总容量/每业务线容量
```

### 7. Buffer 按条数，不按字节

当前：

```text
bufferCapacity = 50_000 条
```

如果 payload 1KB~64KB：

```text
50k × 64KB = 3.2GB
```

会 OOM。

需要：

```text
按字节限制
或者大 payload 只存 payloadRef
```

### 8. RedisStreamPublisher 没有检查 pipeline 单命令结果

当前：

```text
executePipelined 后直接返回
```

需要：

```text
检查每条 XADD 的返回值/异常
区分连接级失败和单命令失败
```

同时缺少：

```text
MAXLEN / XTRIM 策略
Stream 长度和内存告警
```

## P2 可维护性

### 9. 拦截器可能返回 null

`OutboxInterceptorChain.onSend` 当前会把 null 传给下一个拦截器。

应改为：

```text
null 视为不修改，继续使用上一条 record
```

### 10. 没有 OutboxProducer 生命周期测试

缺少：

```text
start 两次
close
扫描阻塞
sender 中断
buffer 满
```

### 11. 没有真实 Redis Stream 测试

当前只有 fake：

```text
OutboxSenderTest
```

没有验证：

```text
XADD field
XGROUP
XREADGROUP
XACK
XPENDING
XAUTOCLAIM
```

## Review 结论

```text
方向正确：
  Scanner + Buffer + Sender
  Interceptor / Partitioner / Serializer
  Redis Stream

但不能继续：
  SENT 重投逻辑错误
  XADD 失败无退避/DEAD
  序列化异常泄漏 inFlight
  文档状态机冲突
```

## 下一步

先修 P0：

```text
findRelayCandidates 只查 INIT
XADD 失败计入 retry/dead
sendOnce 全路径 finally 释放 inFlight
状态机文档统一
```

再修 P1：

```text
per-bizCode buffer
字节容量
真正 linger
pipeline 错误检查
Stream 长度策略
```

最后进入 C-001.3 StreamConsumer。
