# 阅读指南

> 读完你能做什么：知道该先看哪篇、每篇解决什么问题、什么时候去看代码。

## 1. 为什么按使用顺序读

先看内部实现，容易记住类名，但不知道框架解决什么问题。  
先看使用方式，再看内部，才能把代码和业务语义对上。

推荐顺序：

```text
业务场景
  → 业务方怎么用
  → 框架保证什么
  → 数据怎么落
  → 失败怎么恢复
  → 代码在哪里
```

## 2. 三条阅读路线

### 业务开发

```text
README
→ 01-使用/01-接入手册
→ 04-验证/01-测试与验收
→ 05-代码讲解/00-代码地图（只看 tx-demo）
```

目标：

```text
会写 TccAction
会发起 TCC
会发事件
会写消费者
```

### 框架开发

```text
README
→ 02-设计/01-核心模型
→ 03-数据/01-数据模型
→ 05-代码讲解/00-代码地图
→ change.md
→ 测试
```

目标：

```text
能改状态机
能改 Outbox/Relay/Consumer
能补测试
```

### 运维/排障

```text
README
→ 02-设计/01-核心模型
→ 03-数据/01-数据模型
→ 04-验证/01-测试与验收
```

目标：

```text
看懂状态
知道消息卡在哪里
知道怎么重放/对账
```

## 3. 文档结构

| 文档 | 回答什么 |
|---|---|
| `README.md` | 项目是什么、边界是什么 |
| `01-使用/01-接入手册.md` | 业务方怎么接入 |
| `02-设计/01-核心模型.md` | TCC/Outbox/Redis/MySQL 各自负责什么 |
| `03-数据/01-数据模型.md` | 表、键、状态、分片 |
| `04-验证/01-测试与验收.md` | AC 怎么测、故障怎么验 |
| `05-代码讲解/00-代码地图.md` | 从哪个类开始读 |
| `05-代码讲解/C-001.1-OutboxPublisher.md` | C-001.1 的逐类讲解 |
| `.harness/changes/` | 本次变更做什么、不做什么 |

## 4. 每篇文档的写法

```text
读完你能做什么
一个具体例子
怎么用
内部怎么做
失败会怎样
对应代码/测试
```

不写：

```text
没有业务例子的抽象概念
和当前变更无关的未来设计
只有类名没有调用链的“源码分析”
```

## 5. 代码阅读顺序

```text
tx-demo 的入口
  → tx-participant 的 TccAction
  → tx-coordinator 的状态机
  → tx-outbox 的 Relay/Consumer
  → 对应测试
```

先看一次成功链路，再看失败链路。
